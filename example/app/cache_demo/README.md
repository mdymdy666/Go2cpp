# cache_demo —— 7 种淘汰策略 × 3 个场景的命中率对比

用 `go2cpp::cache::Workload` 生成三组**逐请求相同**的负载，让 7 种策略
（LRU / LRU-2 / 2Q / W-TinyLFU / GDSF / ARC / CLOCK）在完全相同的输入上
跑一遍，打印对象命中率、字节命中率与淘汰统计。

## 三个场景

| 场景 | 访问模式 | 考察点 |
| --- | --- | --- |
| `hotspot` | 80% 请求落在 1000 个热点 key，20% 落在 10 万冷 key | 基线命中率与 recency |
| `scan` | 每 2000 个热点请求插入 2000 条顺序扫描 | 抗扫描污染（scan resistance） |
| `weighted` | 20% 请求带 `weight=1000` 的大对象，其余为 1 | 权重/大小感知淘汰 |

负载由固定 seed（默认 `0x5DEECE66D`）生成，同一组参数下 7 种策略看到的
请求序列完全一致，不存在「负载不同导致的不公平」。容量默认 1000 条，
热点 key 数也取容量，因此「刚好装满热点」是基线。

## 构建与运行

```sh
# 仓库根目录
cmake -S . -B .build-bento-wsl -DGO2CPP_BUILD_EXAMPLES=ON
cmake --build .build-bento-wsl --target go2cpp_cache_demo -j8

./.build-bento-wsl/example/app/go2cpp_cache_demo
# 可选参数
./.build-bento-wsl/example/app/go2cpp_cache_demo --ops 500000 --capacity 2000 --seed 42
```

`cache` 是 header-only 模块，示例只依赖 `include/go2cpp/cache/`，不链接额外库。

## 怎么读这些数字

- **hotspot**：LRU/CLOCK 只有 ~55%，因为 1000 个热点 key 与容量相同，20%
  的冷尾请求会不断把热点挤出；LRU-K(2) 要求「二次访问」才升级，冷尾大多
  只访问一次，因此主缓存几乎不被污染（79%）。2Q 的 A1out 只挡住一部分，
  ARC/TinyLFU 介于两者之间。
- **scan**：顺序扫描每次都是新 key，LRU/CLOCK 被彻底冲掉（~19.5%）；
  LRU-K、ARC、W-TinyLFU 把扫描挡在准入队列/窗口之外，保持在 ~39%。
- **weighted**：`weight` 只被 GDSF 消费（见 `cache.hpp` 的「权重语义」），
  其余策略按条目数淘汰，所以命中率与 hotspot 接近。GDSF 按
  `cost / size × freq` 的收益密度淘汰，倾向于保留小对象，因此**对象命中率
  不占优、淘汰次数更少**；字节命中率也略低于按条目淘汰的策略。它的目标
  函数是「单位字节的取回收益」，不是纯命中率，参数需要与对象大小分布匹配。
- **LRU-K 的条目/容量是 2000/1000**：LRU-2 除主缓存外还有历史队列
  （ghost），`Stats().size` 把两者都算进去，这不是超容量泄漏。

## 参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--ops` | `200000` | 每个场景的请求数 |
| `--capacity` | `1000` | 条目容量；同时决定热点 key 数 |
| `--max-weight` | `5000` | GDSF 的权重预算（仅 weighted 场景生效） |
| `--seed` | `0x5DEECE66D` | 负载随机种子；同种子结果可复现 |

## 边界与取舍

- 所有策略都在**单线程**下运行：示例比较的是算法本身，不含
  `ThreadSafeCache` 的锁开销；并发场景用 `ThreadSafeCache` 或 `ShardedCache`；
- 只覆盖 3 个场景；`workload.hpp` 还提供 `cdn`（Zipf 视频 + 分片）与
  `mixed`（热点+扫描+突发），需要时把 `WorkloadKind` 换掉即可；
- 值只存 `std::to_string(key)`，不模拟真实对象的内存布局；
- weighted 场景的 `weight` 与 key 热度独立，所以大对象本身也大多是冷 key；
  这是该负载的定义，不是策略缺陷。
