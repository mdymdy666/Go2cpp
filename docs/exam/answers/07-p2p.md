## Q01

**答**：四测试各答一个问题：Test I 是否有 NAT；Test II 是否允许任意 IP+端口入站；Test III 是否允许任意端口（同 IP）；Test IV 映射是否随目标变化（Symmetric 的直接证据）。污染机制：Test IV 让内网主机先向备用服务器发包，端口受限/对称 NAT 的过滤表会为备用地址建「已通信」记录；此后再做 Test II/III，来自备用地址的响应会被放行，于是把 Port Restricted 误判成 Full Cone / Restricted Cone。正确顺序必须 II → III → IV，且 Test II 只在 `alternate_changes_ip` 为真时有意义。单服务器部署无法区分锥形与 Symmetric，只能报 `Unknown`（不猜）。这是 RFC 3489 类型学，不是 RFC 8445 ICE 行为发现，结果只用于选路建议。

## Q02

**答**：三段预算：信令 ≤ `timeout/2`（`min(deadline, started+half)`），直连 ≤ 总预算的 70%（有中继候选时 `direct_deadline = min(deadline, started+0.7*timeout)`；无中继候选时直连拿满），中继用剩余 30%，且只在直连完全失败后才 `TryRelay`。是**串行降级不是并行竞速**，总耗时可能接近三段之和。信令给一半：候选交换是双向的（双方都要先 Send 再 Recv），给太少慢信令直接失败、给太多挤压连通性检查。候选按远端 priority 降序（host > prflx > srflx > relay）。失败语义：信令失败立即 Failed 不进入直连；直连失败但中继成功是 `Relayed` 不是 `Connected`；两者都失败才 Failed。

## Q03

**答**：keepalive **无后台线程**，由 `Recv()` 驱动：每轮才取时钟、调 `MaybeSendKeepalive`、检查 `PeerTimedOut`；两者都关闭时连 `steady_clock::now()` 都跳过。触发条件：状态 Connected/Relayed、`keepalive_interval>0`、距上次超过间隔。只发不收的两层后果：应用层 `keepalives_sent` 不增长；NAT 设备上 UDP 映射/过滤表因无出站包过期，对端后续包被丢弃。`peer_timeout` 也只在 `Recv()` 里检查：不调 `Recv()` 永远不判失联，状态一直 `Connected`（假活）。正确用法：只上传的循环也要周期性 `Recv(0ms)`（仍走一轮 keepalive 与 poll，不是空操作）。RTT 是「最后一次发送到收到 ACK」，`m_has_pending_keepalive` 是单布尔量，连续两个未 ACK 时后一个覆盖前一个时间戳。

**代码证据**：

```text
src/p2p/p2p_channel.cpp:1120-1123  m_last_receive_ns / m_last_keepalive_ns / m_has_pending_keepalive{false}
```

**自证**：代码核对；未写「只 Send 不 Recv → keepalives_sent=0」探针。

## Q04

**答**：服务端过期是**硬到期**：`ExpireAllocations()` 只看 `expires`，到期就 `close(fd)` 并从表里 erase，**与是否有数据流量无关**；`HandleAllocate` 设置 `expires = now + allocation_lifetime`（默认 60000 ms）。客户端缺失续期路径：`P2PChannel` 没有定时器，也没有在 `Send/Recv` 里检查 `lifetime_ms()` 并 `Refresh`；`TryRelay` 只在 `!relay->allocated()` 时 `Allocate` 一次；`grep -rn 'Refresh(' src/p2p` 除 `turn_client.cpp` 定义与服务端 `HandleRefresh` 外没有 `P2PChannel` 调用者。故障现象：约 60s 后状态仍是 `kRelayed`、`IsRelayed()` 仍 true，但 `Send` 的对端收不到；`relayed_packets_sent` 仍增长（发给了服务端）。修法：按 `lifetime/2` 周期 `Refresh`（需要驱动源）或服务端在转发时顺延 `expires`（改 TURN 语义）。测试盲区：中继用例只跑秒级，跨不过 60s。

**代码证据**：

```text
src/p2p/p2p_channel.cpp:985-987  if (!relay->allocated()) { ... Allocate(&error) ...
```

**我没答出的**：没有把 `allocation_lifetime` 改成 200ms 做静默断流探针。

## Q05

**答**：这是 simultaneous open 的代价，不是纯 bug：NAT 只放行「内部先发过包」的目标，双方同时打洞时对端可能先收到我们的包、我们还不知道它的地址；不接收入站请求就没有 peer-reflexive 候选，打洞失败。但入站 `kRequest` 分支**不校验**事务号/对端身份：回 Success 后直接 `Establish(source, false)`，不检查 `pending`、不比对远端候选；只有 `kSuccessResponse` 分支才检查 `pending.Contains(transaction_id)`。风险：任何能到达本地 UDP 端口的第三方发一个格式合法的 Binding 请求就能把状态推到 `Connected` 并把 `peer` 设成攻击者地址；没有 MESSAGE-INTEGRITY、没有 nomination、对端身份不绑定。后果：后续数据发到攻击者端点（数据面明文）；真正对端被晾在一边；攻击者只发一次请求就停，连接假活到 `peer_timeout`（也只在 `Recv` 检查）。缓解：应用层对数据帧做端到端身份校验/加密，或引入 ICE username/password + MESSAGE-INTEGRITY + nomination（未实现，改造成本高）。

**代码证据**：

```text
src/p2p/p2p_channel.cpp:968-971  if (klass() == kSuccessResponse && pending.Contains(transaction_id)) { ... Establish(source, false);
src/p2p/p2p_channel.cpp:1043-1044  Bump(connectivity_checks_received); Establish(source, true);  // 中继检查同样直接 Establish
```

**自证**：代码路径核对；未写第三方发 Binding 请求把状态推到 Connected 的探针。
