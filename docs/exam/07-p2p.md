## 一、类型探测与候选

### Q01 【L3 陷阱】NAT 类型探测为什么 Test IV 必须最后做？顺序颠倒会误判成哪一类？

- **痛点**：把四个测试当成彼此独立；不知道 Test IV 会「污染」NAT 的过滤表，导致后续
  `CHANGE-REQUEST` 的响应本该被丢弃却被放行。
- **追查位置**：
  - `src/p2p/stun_client.cpp:262-270`（代码注释明确写出顺序：Test II 换 IP+端口 → Test III 换端口
    → Test IV 向备用服务器；并解释 Test IV 会把备用服务器地址记为「已通信」）
  - `src/p2p/stun_client.cpp:271-297`（Test II / Test III 的实现与判定）
  - `src/p2p/stun_client.cpp:299-316`（Test IV：向 `alternate_server` 发普通 Binding，比较映射是否变化）
  - `src/p2p/stun_client.cpp:320-326`（只有单个服务器时保守返回 `Unknown`，不猜）
  - `include/go2cpp/p2p/stun_client.hpp` 的 `NatDetectionConfig`（primary + alternate 两个地址）
- **验收标准**：
  1. 说清四个测试各自回答什么问题：Test I 是否有 NAT；Test II 是否允许来自任意 IP+端口的入站；
     Test III 是否允许任意端口（同 IP）；Test IV 映射是否随目标变化（Symmetric 的直接证据）。
  2. 说清污染机制：Test IV 让内网主机先向备用服务器发包，端口受限/对称 NAT 的过滤表会为
     备用地址建一条「已通信」记录；此后再做 Test II/III，来自备用地址的响应会被放行，
     于是把 Port Restricted 误判成 Full Cone / Restricted Cone。
  3. 说出正确顺序必须是 II → III → IV，且 Test II 只有在 `alternate_changes_ip` 为真时才有意义。
  4. 说出单服务器部署的边界：无法区分「锥形」与 Symmetric，只能报 `Unknown`，不能瞎猜。
  5. 指出这套检测是 RFC 3489 的 NAT 类型学，不是 RFC 8445 的 ICE 行为发现；结果只用于选路建议，
     不能当作连通性保证。
- **怎么自证**：`cmake --build .build-bento-wsl -j"$(nproc)" --target p2p_test_stun && ./.build-bento-wsl/p2p_test_stun`。
  用例用 `tests/p2p/mock_nat.hpp` 模拟四种 NAT，逐一断言 `Detect()` 的结果与 detail 文本。
  再做一个反证探针：把 Test IV 提到 Test II 之前（只改探针，不改仓库），用 Port Restricted 模拟器跑
  → 期望得到 Full Cone 误判。报告里贴两次 `NatDetectionResult.detail`。
- **常见错误答案**：「四个测试顺序无所谓，最后看哪个成功」「有备用服务器就一定能判 Symmetric」
  「单服务器也能靠猜区分 Full Cone 和 Restricted」——零分。

### Q02 【L4 陷阱】`Connect()` 的 10 秒预算里，直连到底有几秒？为什么信令只给一半？

- **痛点**：以为 `timeout` 是「直连超时」，或以为中继会和直连并行尝试；实际信令先吃掉 50%，
  直连再吃掉剩余预算的 70%，中继只剩 30%，且中继只在直连完全失败后才开始。
- **追查位置**：
  - `src/p2p/p2p_channel.cpp:387-394`（信令交换 deadline = `min(总deadline, started + timeout/2)`；
    失败直接 `SetFailed`）
  - `src/p2p/p2p_channel.cpp:395-407`（远端候选按 `kRelay` 与其他分成 `relay_targets` /
    `direct_targets`；直连按远端 priority 排序）
  - `src/p2p/p2p_channel.cpp:409-427`（有中继候选：`direct_deadline = min(deadline, started + 0.7*timeout)`；
    没有中继候选：直连拿满预算；直连失败后才 `TryRelay(relay_targets, deadline, started)`）
  - `src/p2p/p2p_channel.cpp:978-991`（`TryRelay` 先 `EnsureRelay`，未分配才 `Allocate`）
  - `src/p2p/p2p_channel.cpp:428-432`（两者都失败 → `SetFailed("连接超时：直连与中继均未成功…")`）
- **验收标准**：
  1. 复述三段预算：信令 ≤ 50%，直连 ≤ 剩余到 70% 总预算，中继用剩下的 30%；无中继候选时直连拿满。
  2. 说清这是**串行**降级不是并行竞速：直连失败返回 false 后才会进 `TryRelay`，所以总耗时可能
     接近三段时间之和，而不是最小值。
  3. 说出为什么信令给一半：候选交换是双向的，双方都要先 Send 再 Recv；给太少会在慢信令上
     直接失败，给太多会挤压连通性检查。代码用 `min(deadline, half)` 保证不会超过总超时。
  4. 说出候选排序：`SortEndpointsByRemotePriority` 按远端候选的 `priority` 降序，host > prflx >
     srflx > relay（`include/go2cpp/p2p/candidate.hpp:8-14` 的 RFC 8445 公式）。
  5. 指出失败语义：信令失败是「立即失败」，不进入直连；直连失败但中继成功是 `Relayed`，不是
     `Connected`；两者都失败才 `Failed`。
- **怎么自证**：`cmake --build .build-bento-wsl -j"$(nproc)" --target p2p_test_p2p && ./.build-bento-wsl/p2p_test_p2p`。
  用例覆盖「Symmetric 失败→中继」「纯中继」「超时」。自己加日志（或 `strace -e trace=sendto,recvfrom -T`）
  记录 `Connect(500ms)` 在「有 relay 候选 + 直连黑洞」场景下的时间分布：信令段、直连段、relay 段
  应分别落在 0–250ms、250–350ms、350–500ms 量级；报你测到的值，不要抄文档。
- **常见错误答案**：「timeout 是直连超时，中继另算」「直连和中继同时打，谁先通用谁」
  「有中继候选就一定能在 timeout 内成功」——零分。

## 二、数据面与保活

### Q03 【L3 陷阱】只发不收的连接，为什么 NAT 映射会过期？keepalive 到底由谁驱动？

- **痛点**：以为 keepalive 有后台线程；写一个「只上传」的循环，从不调用 `Recv()`，几十分钟后
  对端失联，还以为是 NAT 设备问题。
- **追查位置**：
  - `src/p2p/p2p_channel.cpp:496-506`（`Recv()` 每轮才取时钟、调 `MaybeSendKeepalive`、
    检查 `PeerTimedOut`；两者都关闭时连 `steady_clock::now()` 都跳过）
  - `src/p2p/p2p_channel.cpp:778-805`（`MaybeSendKeepalive`：状态必须是 Connected/Relayed，
    距上次超过 `keepalive_interval` 才发；用接收侧 scratch 构造帧）
  - `src/p2p/p2p_channel.cpp:1121-1127`（`m_last_keepalive_ns`、`m_has_pending_keepalive`、
    `m_keepalive_sequence` 的所属线程/原子性）
  - `user/docs/07-p2p.md:89-99`（线程模型：keepalive 无后台线程，由 `Recv()` 驱动；
    只发不收必须周期性 `Recv(0ms)`）
- **验收标准**：
  1. 说出 keepalive 的三个触发条件：状态已连接、`keepalive_interval > 0`、距上次发送超过间隔；
     没有独立线程/定时器。
  2. 说清「只发不收」的两层后果：应用层 `keepalives_sent` 不增长；NAT 设备上 UDP 映射/过滤表
     因无出站包而过期，对端后续包被丢弃。
  3. 说出 `peer_timeout` 也只在 `Recv()` 里检查：不调 `Recv()` 就永远不会判失联，状态会一直
     停在 `Connected`（假活）。
  4. 说出正确用法：任何只上传的循环都要周期性 `Recv(0ms)`；`Recv(0ms)` 仍会走一轮
     `MaybeSendKeepalive` 和一次 `poll`，不是空操作。
  5. 指出 keepalive 的 RTT 统计是「从最后一次发送到收到 ACK」，`m_has_pending_keepalive` 是
     单布尔量；连续两个 keepalive 未 ACK 时后一个会覆盖前一个的时间戳，RTT 只反映最近一次。
- **怎么自证**：`ctest --test-dir .build-bento-wsl -R '^p2p_test_p2p$' --output-on-failure` 先过基线。
  再写探针：`keepalive_interval=50ms`、`peer_timeout=200ms`，只调 `Send()` 不调 `Recv()`，跑 1 秒，
  打印 `stats().keepalives_sent` → 期望 0；改成每 10ms 调一次 `Recv(0ms)` → 期望约 20 次。
  同时用 `ss -u -a -n` 观察本地 UDP  socket 的最近活动时间。
- **常见错误答案**：「keepalive 是后台线程定时发的」「只要一直 Send，NAT 映射就不会过期」
  「`Recv(0ms)` 什么都没做」——零分。

### Q04 【L4 陷阱】中继模式的长连接，为什么会在 allocation 生命周期到点时静默断流？

- **痛点**：以为 `Allocate()` 一次就永久有效，或以为有数据流量就会自动续期；实际上
  `P2PChannel` 里没有任何地方调用 `RelayClient::Refresh()`，服务端到点直接关 fd。
- **追查位置**：
  - `include/go2cpp/p2p/turn.hpp:55-56`（`allocation_lifetime{60000}`，注释写明「客户端需要在此之前
    Refresh」）
  - `src/p2p/turn_server.cpp:456-470`（`ExpireAllocations()`：`now >= expires` 就 `close(fd)`、
    `m_fd_to_client.erase`、`m_allocations.erase`，**与是否有数据流量无关**）
  - `src/p2p/turn_server.cpp:251-281`（`HandleAllocate` 在新建/已存在时设置
    `expires = now + allocation_lifetime`）
  - `src/p2p/p2p_channel.cpp:985-991`（`TryRelay` 只在 `!relay->allocated()` 时 `Allocate` 一次）
  - `src/p2p/turn_client.cpp:183-212`（`RelayClient::Refresh` 存在并会更新 `m_lifetime_ms`）
  - `grep -rn 'Refresh(' src/p2p`：除 `turn_client.cpp` 的定义/服务端 `HandleRefresh` 外，
    **没有任何调用者**
- **验收标准**：
  1. 说出服务端的过期是硬到期：`ExpireAllocations` 只看 `expires`，不因转发数据而顺延；
     到期后 relay fd 被 close，后续包发到已关闭的端口/被丢弃。
  2. 说出客户端缺失的续期路径：`P2PChannel` 没有定时器，也没有在 `Send`/`Recv` 里检查
     `lifetime_ms()` 并 `Refresh`；`EnsureRelay`/`TryRelay` 只在连接建立阶段跑。
  3. 推导故障现象：约 `allocation_lifetime`（默认 60s）后，状态仍是 `kRelayed`、`IsRelayed()` 仍
     返回 true，但 `Send` 的对端收不到；`stats().relayed_packets_sent` 仍增长（只是发给了服务端）。
  4. 说出至少两种修法：按 `lifetime/2` 周期调用 `Refresh`（需要驱动源，如 `Recv` 的时钟或后台
     定时器），或让服务端在转发数据时顺延 `expires`（但那改变了 TURN 语义，需文档确认）。
  5. 指出测试盲区：`p2p_test_p2p` 的中继用例只跑秒级，不会跨过 60s；所以全绿不代表长连接可用。
- **怎么自证**：先静态确认 `grep -rn 'Refresh(' src/p2p` 只有定义/服务端处理、没有 `P2PChannel` 调用。
  再跑动态探针：起 `RelayServer` 时把 `allocation_lifetime` 设为 200ms，客户端走纯中继
  （`enable_relay=true`、直连候选全黑洞），连接成功后每 20ms `Send` 一次并 `Recv`，打印
  `server.stats().allocations_expired` 与 `channel.stats().relayed_packets_sent`：
  期望在约 200ms 后 `allocations_expired` 增加，而客户端状态仍 `Relayed`、发送计数继续涨。
  把探针改成每 100ms 调一次 `Refresh()`，同样的 1 秒窗口内 `allocations_expired` 保持 0。
- **常见错误答案**：「Allocate 一次就永久有效」「有数据经过中继就会自动续期」
  「`Close()` 会 Release，所以不用 Refresh」——零分。

## 三、建连语义与边界

### Q05 【L4 陷阱】一个陌生 UDP Binding 请求就能把状态推到 `Connected`：这是 bug 还是 simultaneous open 必需？

- **痛点**：只看「检查成功」四个字，没注意入站请求分支**不校验**事务号/对端身份；或者反过来，
  以为这是纯粹的安全漏洞，删掉后双方同时打洞就再也连不上。
- **追查位置**：
  - `src/p2p/p2p_channel.cpp:957-967`（`TryDirect` 收到 `kRequest`：回 Success 后**直接**
    `Establish(source, false)`，不检查 `pending`、不比对远端候选）
  - `src/p2p/p2p_channel.cpp:968-972`（只有 `kSuccessResponse` 分支才检查
    `pending.Contains(transaction_id)`）
  - `src/p2p/p2p_channel.cpp:1044-1051`（中继检查同样：入站请求直接 `Establish(source, true)`）
  - `src/p2p/p2p_channel.cpp:840-867`（连接后收到重传检查包时只回 Success，不再改状态）
  - `user/docs/07-p2p.md:296-308`（已知限制：无 ICE nomination、数据面无加密、候选可伪造）
- **验收标准**：
  1. 说出「接受入站请求」的必要性：NAT 只放行「内部先发过包」的目标，双方同时打洞时，对端可能
     先收到我们的包、我们还不知道它的地址；不接收入站请求就没有 peer-reflexive 候选，打洞失败。
  2. 说出风险：任何能到达本地 UDP 端口的第三方，发一个格式合法的 Binding 请求就能把状态推到
     `Connected`，并把 `peer` 设成攻击者地址；没有 MESSAGE-INTEGRITY、没有 nomination、没有
     对端身份绑定。
  3. 区分两种匹配：请求分支看「谁发来的」就信谁；响应分支必须匹配自己发过的 transaction id。
     这是本实现与完整 ICE 的核心差距。
  4. 说出后果：后续数据发到攻击者端点（数据面明文）；真正的对端被晾在一边；如果攻击者只发一次
     请求就停，连接会假活到 `peer_timeout`（而 `peer_timeout` 也只在 `Recv` 里检查）。
  5. 给出至少两个缓解方向：应用层对数据帧做端到端身份校验/加密；或引入 ICE 的
     username/password + MESSAGE-INTEGRITY + nomination（当前未实现，改造成本高）。
- **怎么自证**：`./.build-bento-wsl/p2p_test_p2p` 先过 Full Cone / Port Restricted / 纯中继基线。
  再写探针：A 调 `Connect()` 进入 `Connecting`，第三方 socket 向 A 的本地端口发一个
  `BuildBindingRequestWire` 格式的包；观察 A 的 `state()` 变成 `Connected`、`peer` 是第三方地址，
  且 `stats().connectivity_checks_received` 增加。把探针里的请求改成非法 magic → 状态不变。
  报告里说明这是「simultaneous open 的代价」还是「必须修的安全问题」，并给出你的判据。
- **常见错误答案**：「收到请求直接连是 bug，应该只认自己发过的 transaction」
  「有 STUN 就说明对端身份可信」「数据面没加密但 ICE 会鉴权」——零分。
