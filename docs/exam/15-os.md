### Q01 【L4 陷阱】PTY 模式下三条 stdio 是同一个 fd，父进程为什么只能 close 一次？

- **痛点**：把 `child_stdin/child_stdout/child_stderr` 当成三个独立 fd，按三条流各 `close` 一次。单线程下只是 `EBADF`；并发 `Spawn` 时，第一次 close 释放的 fd 号可能立刻被另一个线程的 `posix_openpt/open` 复用，后两次 close 就会误关别人刚打开的 fd。
- **追查位置**：
  - `src/os/proc.cpp:1093`（`if (use_pty)`：PTY 分支单独处理父侧关闭）
  - `src/os/proc.cpp:1094`（注释：三条流是**同一个**从端 fd，必须只关闭一次）
  - `src/os/proc.cpp:1095`（注释：并发 Spawn 时多余 close 会误关别的线程复用的 fd）
  - `src/os/proc.cpp:1098`（注释引用了 `tests/os/test_os_pty.cpp 场景 4`——该文件**已不在树里**）
  - `src/os/proc.cpp:1100`（`pty.ReleaseSlave()`：把所有权转移出来，Pty 析构不再重复关闭）
  - `src/os/pty.cpp:193`（`Pty::ReleaseSlave`：交出 slave fd 并置空）
  - `include/go2cpp/os/pty.hpp:18`（从端全关后 master `read` 返回 `EIO`，不是 EOF；`FdChannel::Pull` 把它映射成关闭）
- **验收标准**：
  1. PTY 模式只创建一个从端，三条流共享它；`SpawnedProcess` 里三个 fd 字段值相同（不是 dup 出来的三个）。
  2. 父进程用 `ReleaseSlave()` 先把 fd 所有权从 `Pty` 对象里取走，再 `close` 一次；否则 `Pty` 析构会再关一次。
  3. 单线程重复 close = `EBADF`，看起来无害；并发下是 fd-reuse 竞态：编号被复用后，多余的 close 命中的是**别人的** fd。
  4. 父侧读 master 时，从端全部关闭得到 `EIO`（不是 `read==0`）；本库在 `Pty::Read` 里把它转成 `kClosed`，否则会把正常退出当 I/O 错误。
  5. 这条路径没有回归测试（注释引用的 `tests/os/test_os_pty.cpp` 不存在），只能靠代码审查和并发压测。
- **怎么自证**：`ls tests/os/` 只有 `test_os_file.cpp`、`test_os_dir.cpp`、`test_os_hook_conflict.cpp`，`grep -rn "test_os_pty" tests/ cmake/` 只命中 `src/os/proc.cpp:1098` 的注释——测试缺失本身可复核。`strace -f -e trace=close,openat,ioctl ./go2cpp_os_test` 看不到 PTY 路径（os 测试不覆盖 Spawn+PTY），所以这题以**读代码 + 自己写并发 Spawn 复现**为主，属于定性题。
- **常见错误答案**：「三条流一定是三个 fd，各关一次最安全」「close 一个已经关闭的 fd 只会 EBADF，不可能影响别人」「PTY 关闭时 read 返回 0（EOF）」——零分。

### Q02 【L4 陷阱】`WritevAll` 的慢路径为什么要复制一份 iovec？部分写的推进错在哪会重复数据？

- **痛点**：把 `writev` 当成「要么全写要么全不写」。它允许只写前几个 iovec 的一部分就返回；下一次必须从「写到哪里」继续。直接重发整个 iovec 数组会把已写过的段再写一遍（数据重复），而只跳过整个 iovec 又会丢尾部字节。
- **追查位置**：
  - `src/os/file.cpp:568`（注释：`readv`/`writev` 的固定成本与批量收益，数字是历史实测，需自测）
  - `src/os/file.cpp:572`（注释：`writev` 允许部分写，下一次必须从写到的位置继续，不能重发）
  - `src/os/file.cpp:577`（`kMaxIov = 1024`：Linux `IOV_MAX`，超过内核 `EINVAL`）
  - `src/os/file.cpp:591`（`AdvanceIov`：跨 iovec 消耗 `consumed`，必要时前移 `iov_base`、减小 `iov_len`）
  - `src/os/file.cpp:657`（`WritevAll`：快路径一次写满、不分配；慢路径才复制 iovec）
  - `src/os/file.cpp:683`（慢路径 `std::vector<iovec> rest(iov, iov+iovcnt)`，热路径不付这个代价）
  - `src/os/file.cpp:731`（`ReadvAll`：`got==0` 是 EOF，返回已读字节而不是 -1）
  - `tests/os/test_os_file.cpp:684`（`ScenarioVectoredIo`：1024×8B、EOF 只剩 100B、1025 段 EINVAL、全零 iovec）
- **验收标准**：
  1. 单次 `Writev` 返回值可能小于所有 `iov_len` 之和；要写全用 `WritevAll`，它循环到 `want` 或写不动。
  2. `AdvanceIov` 处理三种情况：整段被消耗（下标前进）、部分消耗（base 前移 + len 减小）、全部消耗（返回 `iovcnt`）；重发时必须用推进后的数组。
  3. `iovcnt` 必须在 `1..1024`；`nullptr`、`0`、`1025` 都返回 `EINVAL`，不能把 `1025` 截断成 1024 偷偷写。
  4. `ReadvAll` 在 EOF 返回**已读字节数**（可能小于 `want`），一开始就 EOF 返回 0；`Readv` 单次则可能返回 0。
  5. 全零 iovec 合法：返回 0、`last_error=0`；混合零长段按顺序拼接，不能因为某个 `iov_len==0` 提前结束。
  6. 慢路径 `bad_alloc`：`WritevAll` 返回已写字节并置 `ENOMEM`，`ReadvAll` 返回 -1；不能假装成功。
- **怎么自证**：`cd .build-bento-wsl && ./go2cpp_os_test` → `[os][场景14]` 的 `ScenarioVectoredIo` 通过（WritevAll 写满、EOF 读回 100 字节、1025 段 `EINVAL`、零长 iovec 返回 0）；再加 `ScenarioSizeBoundaries` 看边界。要观察部分写，可把输出接到一个慢管道（`| sleep`/小 buffer socket）并用 `strace -e trace=writev` 数每次返回的字节数。
- **常见错误答案**：「writev 是原子的，返回值一定等于总长」「部分写时重发整个数组最简单」「IOV_MAX 是建议值，超了内核会帮你截断」——零分。

### Q03 【L4 陷阱】ProcessPool 缩容后为什么必须 `notify_all`？`notify_one` 会坏在哪？

- **痛点**：把 `notify_one` 当纯性能优化。缩容后 worker 的等待谓词包含 `index < target_workers`；被裁的 worker 被唤醒后仍不满足条件、继续睡。若 `notify_one` 恰好选中它，新任务就没人消费，直到下一次 Submit/Resize/Shutdown 才可能被捞起来——表现为 `SubmitAndWait` 偶发超时。
- **追查位置**：
  - `src/os/pool.cpp:155`（注释：必须 `notify_all`，不能 `notify_one`，并写出等待谓词）
  - `src/os/pool.cpp:159`（注释：历史实测「缩容后提交的任务会滞留到 SubmitAndWait 超时（单机约 10%）」——**历史数字，需自测**）
  - `src/os/pool.cpp:161`（`work_cv.notify_all()`）
  - `src/os/pool.cpp:261`（`WorkerLoop` 的 `work_cv.wait(lock, [this, index]{...})` 谓词）
  - `src/os/pool.cpp:279`（`index >= target_workers` 时决定退出）
  - `src/os/pool.cpp:340`（`Resize` 先 `target_workers.store(workers)` 再补线程）
- **验收标准**：
  1. 等待谓词不是「队列非空」一条，而是「队列非空 **且** 本 worker 的 index 仍在新目标内」（外加 stopping）。
  2. 缩容不立即杀线程：只是降低 `target_workers`，worker 下次醒来且队列空时自行退出；这期间 `index >= target` 的线程仍在等待。
  3. `notify_one` 可能唤醒一个「将被裁」的线程，它检查谓词失败后继续睡；新任务留在队列里，没有有资格的线程被唤醒。
  4. `notify_all` 是**正确性**要求（惊群换正确），不是「更保险的性能选择」。
  5. `Resize` 的补位必须逐槽检查 `threads[slot].joinable()`，不能只看 `alive_workers`（它包含即将退出的线程）。
- **怎么自证**：`cd .build-bento-wsl && ./go2cpp_os_test` 不覆盖 `ProcessPool`，仓库里也没有 pool 的 ctest；这题目前只能读 `src/os/pool.cpp` 并用 `SubmitAndWait` 写压力复现（反复 `Resize(1)`/`Resize(4)` + 提交短任务，统计超时率）。属于定性题；注释里的 10% 是历史实测，**不要当验收数字**。
- **常见错误答案**：「notify_one 更省 CPU，语义一样」「缩容会立刻杀掉多余线程，所以不会有等待者」「谓词只看队列是否为空」——零分。

### Q04 【L4 陷阱】`sendfile` 的 offset 到底由谁推进？为什么拷过一段之后就不能回退到 read+write？

- **痛点**：以为 `sendfile(out, in, &offset, n)` 会像 `read` 一样移动 `in` 的文件偏移。显式传 `&offset` 时内核只更新 `offset` 变量，**不动** `in_fd` 的偏移；不补 `Seek`，下一次 `Tell/Read` 就从错位置继续。更隐蔽的是回退条件：一旦已经拷过字节，混用 sendfile 与 read+write 会让「已拷贝多少」无法推理。
- **追查位置**：
  - `src/os/file.cpp:745`（`File::CopyTo`：先 `Tell()` 拿 offset，`have_offset` 决定是否传 `&offset`）
  - `src/os/file.cpp:771`（单次 `sendfile` 限制在 1 MiB，避免一次卡太久）
  - `src/os/file.cpp:775`（`SYS_sendfile` 调用：显式 offset 指针）
  - `src/os/file.cpp:781`（注释：只有**一字节都没拷**时才允许回退，混用两条路径会让已拷贝量难以推理）
  - `src/os/file.cpp:806`（`if (have_offset && Seek(offset, SEEK_SET) < 0)`：补上 in_fd 偏移）
  - `src/os/file.cpp:816`（回退路径：普通 `Read`+`Write` 64 KiB 循环，语义一致但多一次拷贝）
  - `tests/os/test_os_file.cpp:780`（`ScenarioCopyTo`：8 MiB、offset 前进、4096 截断、空文件、坏句柄）
- **验收标准**：
  1. `have_offset = Tell() >= 0`；传 `&offset` 时 `in_fd` 的偏移不变，循环结束后必须 `Seek(offset, SEEK_SET)`，让 `CopyTo` 的语义与连续 `Read` 一致。
  2. `result == 0` 是 EOF，不是错误；`result < 0` 且 `total == 0` 且 errno ∈ {EINVAL, ENOSYS, EXDEV, EOPNOTSUPP, ENOTSUP} 才允许 `fallback`。
  3. 已经拷过字节（`total > 0`）后任何错误都直接返回 `kIoFailed` + `*copied = total`，**不回退**——否则会重复或丢失。
  4. `max_bytes` 是硬上限（`limit`），空文件返回 `copied=0` 且成功；坏句柄返回 `kInvalidHandle/EBADF` 并把 `copied` 归零。
  5. `sendfile` 绕过用户态，不能用于需要加密/改写的数据（TLS、压缩）；对端慢读会让调用阻塞/部分写，库用 1 MiB 分块限制单次停顿。
- **怎么自证**：`cd .build-bento-wsl && ./go2cpp_os_test` → `[os][场景15] ScenarioCopyTo` 通过（8 MiB 逐字节一致、`in.Tell()` 前进到末尾、4096 截断、坏句柄）。`strace -f -e trace=sendfile,lseek,read,write ./go2cpp_os_test 2>&1 | grep -A2 sendfile` 可直接看到 `sendfile` 返回值与随后的 `lseek` 回写。
- **常见错误答案**：「sendfile 会自动推进 in_fd 偏移」「0 返回值表示对端关闭，应当报错」「拷到一半失败就回退 read+write 最稳」——零分。

### Q05 【L4 推演】`fork` 之后为什么连 `close` 都要用裸 syscall？error fd 为什么必须先搬到 `>=10`？

- **痛点**：在子进程里继续用 libc/iostream/`std::string`。`fork` 在多线程进程里只复制调用线程，子进程若调用任何可能拿锁/分配内存的函数，可能死锁在「锁的持有者已经不存在」的状态。另一个隐蔽点是 fd 编号：父进程 stdio 关闭时，`pipe2` 可能把 error pipe 分配到 0/1/2，与后面 `dup2` 的目标冲突。
- **追查位置**：
  - `src/os/proc.cpp:6`（文件头注释：fork 之后全部用裸 syscall，子进程不分配、不加锁）
  - `src/os/proc.cpp:704`（注释：error fd 可能在 0..2，先 `F_DUPFD_CLOEXEC` 到 `>=10`）
  - `src/os/proc.cpp:714`（注释：三条源 fd 也可能 <=2，先搬到 `>=10`，避免 `dup2` 顺序互相覆盖）
  - `src/os/proc.cpp:734`（`dup2(temporary[index], index)` 把三条流装到 0/1/2）
  - `src/os/proc.cpp:738`（error fd 固定到 3，`close_range` 从 4 开始，不会误关它）
  - `src/os/proc.cpp:749`（`close_range(4, ~0u, 0)`；不支持时按 `close_limit` 逐个关）
  - `src/os/proc.cpp:766`（`setrlimit` 循环：在 exec 前设置，失败走 `ChildFail`）
  - `src/os/proc.cpp:813`（`execve`；失败落到 `ChildFail` 写 errno 后 `_exit_group(127)`）
  - `src/os/proc.cpp:1016`（父进程 `pipe2(error_pipe, O_CLOEXEC)`：exec 成功时内核自动关写端）
  - `src/os/proc.cpp:1124`（父进程读 error pipe：读到 4 字节 errno = 失败，读到 EOF = 成功）
  - `src/os/proc.cpp:1143`（失败路径 `waitpid` 回收子进程，再返回 `kExecFailed + errno`）
- **验收标准**：
  1. 错误回传协议：父建 `O_CLOEXEC` 管道 → fork → 子 exec；exec 成功内核关写端，父读到 0 字节 EOF；失败子写 `int errno` 再 `_exit_group(127)`，父据此返回 `kExecFailed` 并回收僵尸。
  2. `fork` 后子进程只调用 `SYS_*` 裸 syscall（`fcntl/dup2/dup3/close_range/setsid/chdir/umask/setrlimit/setpriority/sched_*` 等），不 malloc、不碰 `std::mutex`、不跑析构。
  3. error fd 若落在 0..2，先复制到 `>=10`；三条源 fd 若 <=2，也复制到 `>=10`；否则后续 `dup2` 会互相覆盖（例如 stdin 源是 0、先 dup2 到 0 没事，但 stdout 源也是 0 时就被覆盖）。
  4. error fd 最终固定到 3（`dup3` 带 `O_CLOEXEC`，失败回退 `dup2`+`F_SETFD`），`close_range` 从 4 开始；不能把 3 关掉，否则错误回传静默丢失。
  5. `setrlimit` 在 exec 前逐条设置，任何一条失败都通过 error pipe 回传，不会「部分 limit 生效但 exec 继续」。
  6. 子进程失败路径用 `exit_group(127)`，不会执行 atexit/静态析构（那些可能拿锁）。
- **怎么自证**：`cd .build-bento-wsl && ./go2cpp_os_test` → `[os][场景9] Args`、`[os][场景10] 压测与随机` 通过，证明 `Process`/`Run` 的主路径可用。要看 fd 重排：`strace -f -e trace=clone,dup2,dup3,close_range,execve ./go2cpp_os_test 2>&1 | head -40`，观察子进程在 `execve` 前有一串 `dup2/dup3` 且 `close_range` 从 4 开始。注意该测试不覆盖「父 stdio 关闭」的极端场景，那需要自己写复现。
- **常见错误答案**：「fork 后可以用 printf/malloc，只要不抛异常」「error pipe 不需要 CLOEXEC，父进程自己关就行」「fd 编号是稳定的，0/1/2 一定留给 stdio」——零分。
