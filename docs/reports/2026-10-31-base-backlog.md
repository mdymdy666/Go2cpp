## 1. 口径与证据

### 1.1 为什么可以判定「非 bug」

三条判据同时成立才写「物理/口径，非 bug」：

1. **正确性断言全绿**：同一批压测里，顺序/计数/互斥/取消/关闭竞态/Fiber-local
   等真实断言 0 失败（`2026-10-31-verify-final.md` §2.1，3×10^9 混合操作）；
2. **成本可解释**：差距能落到具体物理路径（futex 系统调用、上下文切换、
   执行模型差异、分配/池化），不是「说不清为什么慢」；
3. **消除代价高于收益**：要逼近 Go 需要改执行模型或引入 handoff 等高风险改动，
   而收益只在基准里可见。

## 2. 并发 6 项（全部：物理/口径，非 bug）

### 2.1 ConditionVariable 1P1C：2.8×

| 项 | 值 |
|---|---|
| 本机 | 187.22 ns/wait（三轮 min） |
| Go | 78.21 ns/迭代（load 666 下测得） |
| 倍数 | **2.8×**（本轮区间 2.4–2.9×） |
| 历史 | `2026-10-30-performance.md` 记录 CV 1P1C 503.4→397.7 ns（−21%，Go 100.2 ns） |

**为什么是物理/口径**：Go 的 `sync.Cond` 在 `Signal` 里做直接交接（把锁交给等待者），
Bento 的 `sync::Mutex` 正常模式要 `Unlock` + 重新 `Lock` 两次状态字迁移，且
`ConditionVariable::Wait` 返回时必须重新持锁；另外 Go 的分母是「每迭代」，
两者不是严格同口径。这是**锁交接协议差异 + 测量口径**，不是丢失唤醒。

**关闭条件**：若「≤1.1× Go」硬标准重启，按 10-31 计划做 Mutex 侧 handoff
（Notify 直接交锁）；否则以「口径对齐 + 本文档记录」关闭。

### 2.2 RWMutex 读 4t：1.26×

| 项 | 值 |
|---|---|
| 本机 | 10.37 ns/op（4 线程只读） |
| Go | 8.03 ns/op（`sync.RWMutex`） |
| 倍数 | **1.26×**（另一轮快照 1.29×） |
| 同族 | 写 4t 40.49 vs 14.83 = 2.73×（仍高，单独观察） |

**为什么是物理/口径**：读侧是原子计数 + 缓存行争用；4 线程读同一把锁的原子
`fetch_add` 在 x86 上就是缓存行乒乓，1.26× 已接近该拓扑的下限。写侧 2.73×
是写者优先 + 队列交接的成本，属另一项，不混入本条的「读 4t」结论。

**关闭条件**：读 4t 进入 1.1× 需要读者计数分片（改数据结构、收益 <10 ns），
不建议为基准改；标记为「已知物理差」关闭。

### 2.3 Context `WithCancel`：1.77×

| 基准（1 万次循环，median） | Go | 本机 | 倍数 |
|---|---:|---:|---:|
| `WithCancel + cancel + destroy` | 76.0 ns | **134.2 ns** | **1.77×** |
| `WithTimeout(1h) + cancel + destroy` | 293 ns | 236.7 ns | 0.81× ✅ |
| `WithDeadline(far) + cancel + destroy` | 273 ns | 239.9 ns | 0.88× ✅ |
| `IsDone()` 未取消 | 6.24 ns | 0.45 ns | 0.07× ✅ |

**为什么是物理/口径**：本轮已做「单次分配 + 控制块池化」（稳态 malloc 从 5–6 次
降到 0），剩下的 58 ns 是取消传播 + 引用计数 + `DoneSignal` 状态机的纯 CPU 成本；
`WithTimeout/WithDeadline` 已达标，说明框架本身没问题，差的是 `WithCancel` 这条
最短路径的固定开销。**不是泄漏、不是错误语义**。

**关闭条件**：若要 ≤84 ns，需要把 cancel 传播再降一层（例如取消工作栈批量化），
属优化项；当前按「1.77× 且已从 3.5× 降下来」记录关闭。

### 2.4 通用 `Channel`：2.8–7×

| 场景 | Bento | Go | 倍数 |
|---|---:|---:|---:|
| SPSC cap0 | 233.0 ns | 82.92 ns | 2.81× |
| SPSC cap64 | 145.2 ns | 20.83 ns | 6.97× |
| SPSC cap1024 | 104.4 ns | 19.83 ns | 5.27× |

**为什么是物理/口径**：通用 `Channel<T>` 为「Context/超时/取消/select/调试」付固定
成本，Go 的 `chan` 由编译器特化（`chansend/chanrecv` 快路径）；两者执行模型也不同
（Bento 走 `ParkingCondition` 的 park/wake，Go 走 `gopark`）。这是**架构差异**，
不是丢唤醒——压测里 FIFO/计数/关闭断言全绿。

**缓解已存在**：`FastChannel` 0.46–0.62×、`FastSpscChannel` 0.35–0.83×（均快于 Go）；
热点路径应换用 Fast 系列，通用 Channel 不再追基准。

**关闭条件**：热点场景迁移到 FastChannel 即关闭；通用 Channel 保持现状。

### 2.5 跨执行体唤醒：50–100 µs/op

| 模型 | 实测 | 说明 |
|---|---:|---|
| f2f（Fiber→Fiber） | 49.7 ns/op | 调度器 park/wake，不陷内核 |
| t2t（Thread→Thread） | 195–237 ns/op | futex，无竞争先自旋 |
| **f2t（Fiber→Thread）** | **75–100 µs/op** | futex WAIT/WAKE + 两次上下文切换 |
| **t2f（Thread→Fiber）** | **20–44 µs/op** | 同上，随负载放大 3–5× |
| WaitGroup（native 等） | 65–83 µs/op | futex 唤醒 + 重新调度 |

**为什么是物理/口径**：跨执行体必须让内核参与，`FUTEX_WAIT`/`FUTEX_WAKE` 的
系统调用 + 上下文切换 + 调度选核 + 缓存失效，单次 5–50 µs 是内核正常量级；
本机共享负载下 50–100 µs 属「物理 + 环境」。**无法在保持两个真实执行体的前提下消除**，
Go 里也没有 thread 执行体可比。

**使用约束（已写入 [`docs/modules/concurrency-usage.md`](../modules/concurrency-usage.md) §3）**：
拓扑对齐（f2f 优先）、批量搬运、一次性 Future、分片去共享、固定边界池、
按 50–100 µs/次做容量规划。

**关闭条件**：以「使用约束文档化 + 压测按此预算设计」关闭；不追求消除。

### 2.6 死锁：1e10 量级未复现

| 项 | 值 |
|---|---|
| 复现规模 | `stress_final` 1e9 混合 ×26 次（10 次 4 核 + 1 次高抢占 + 15 次单核）+ 20 亿单类别 Mutex |
| 总操作量 | ≈**2.8×10^10** |
| 结果 | **0 次 watchdog / 0 次 rc=3** |
| 审计 | 10 条候选死锁环（Mutex 唤醒令牌、饥饿交接、native futex、Scheduler enqueue、FastChannel 等）逐条排除 |
| 昨日现场 | 1 次挂起（worker 停在 shard 0 的 mutex/fast-mpmc），当时 loadavg 2.9→**555** |

**判定**：无证据支持「代码死锁」；最可能是**极端负载饥饿**（worker 被饿死 180 s）。
watchdog 只看「进度不变」，无法区分饥饿与死锁——本轮已在测试程序里补
`fibtask state/queued/lastP` 与 `scheduler runnable` 现场（只改测试文件，不碰运行路径）。

**关闭条件**：低负载（loadavg <5）下 `--ops 1e9 --rounds 3` ×30 次全过，
且增强 watchdog 无触发，即关闭为「环境饥饿」。

## 3. 网络 5 项

### 3.1 SOCKS5 建连 p99 51.7 ms（未定位）

| 指标 | 值 |
|---|---|
| 吞吐 | 45 conn/s（握手 + CONNECT IPv4 + 关闭） |
| p50 | 831.94 µs |
| p99 / p999 | **51,682 / 51,896 µs** |
| 中继 | 911 MB/s（不受影响） |

现象：约 2% 连接出现 ~50 ms 停顿，与「Nagle + 延迟 ACK」的 40 ms 量级吻合
（`2026-10-31-http-perf.md` §6.1 的 WS 现场：服务端 `Send-Q` 卡 32 B）。

**已合入的相关修复**：

- `419786e`：`Socket::accept` 后统一设 `TCP_NODELAY`（自测 44 ms→0.15 ms，292×）；
- `socks5.cpp:759-760`：SOCKS5 自己 `::accept` 后手动补 `SetTcpNoDelay`；
- `Socket::SetTcpNoDelayDefault()` 默认 true。

**状态**：修复已合入，但**没有用同一基准复测 p99**。不能凭「修了 NODELAY」就宣布关闭。

- **优先级**：P2（建连延迟被非协议因素主导，引用时必须带 p99 说明）。
- **关闭条件**：`bento_bench_protocols --perf --only=socks5` 复测 p99 < 5 ms；
  若仍 >50 ms，按「accept 轮询 100 ms + 线程调度」继续定位。
- **复现**：`taskset -c 2,3 ./.build-bento-wsl/bento_bench_protocols --perf --only=socks5`。

### 3.2 raw accept 的 `TCP_NODELAY`（3 条路径）

`Socket::accept` 已自动设 NODELAY，但仍有 3 条路径直接 `::accept`，绕过了这层：

| # | 路径 | 现状 | 风险 |
|---|---|---|---|
| 1 | `src/bento/net/socks5.cpp:738` | **已补**（`:759-760` 手动 `SetTcpNoDelay`） | 无 |
| 2 | `src/bento/net/tcp_proxy.cpp:291` | **未补** | 中继小包可能被 Nagle 压 40 ms |
| 3 | `src/bento/net/tcp_transport.cpp:353` | **未补** | Bento 传输链路小帧同样风险 |

`include/go2cpp/network/socket.hpp:94` 已明确注释：「直接用 `::accept` 的协议实现
需要自行调用」——所以这是**契约内的待办**，不是隐藏 bug。

- **优先级**：P2（一处一行，回归成本低）。
- **建议改法**：3 处 `::accept` 成功后统一 `if (Socket::TcpNoDelayDefault())
  (void)Socket::SetTcpNoDelay(fd);`，并补一个「raw accept 也生效」的断言。
- **状态**：**2/3 未修**（本轮边界只改文档，不改代码）。
- **关闭条件**：两处补齐 + ctest 85 项全绿 + 小包中继基准无 40 ms 尖峰。

### 3.3 CoAP 客户端随机种子固定

`CoapClientConfig::random_seed` 默认 `0x636f61705f636c69`（服务端 `0x7365727665725f31`），
两个新客户端会生成相同 `(Message ID, Token)`，被服务端去重缓存判定为重复，
**返回上一个请求的响应**（基准里表现为 PUT 返回了上一个 GET 的 2.05）。

**权衡**：固定种子让测试可复现是合理默认；但多实例共存必须显式换种子
（基准用 `NowNs() ^ 常量`）。

- **优先级**：P3（正确用法可规避，且已在基准文档里记录）。
- **状态**：**已文档化，默认值未改**；建议在示例/测试模板里强制显式 seed。
- **关闭条件**：文档 + 示例补齐显式 seed，即关闭；不改默认值。

### 3.4 大包走 bufio：0.81×

| 报文 | 单写 | bufio(4KB) | 倍数 |
|---|---:|---:|---:|
| 大消息 4096B | 151,121 ops/s | 122,721 ops/s | **0.81×（慢 19%）** |
| 小包 64–120B | 14.4–18.6 万 ops/s | 333–507 万 ops/s | 21–33×（收益） |

原因：4096B 已 ≥ 缓冲容量，bufio 退化为「直写 + 一次内存拷贝」，系统调用数仍是
1/msg，白白多一次拷贝；应**按长度绕过 bufio 直接 `send`/`writev`/`sendfile`**。

- **优先级**：P2（默认配置下大响应白白慢 19%）。
- **状态**：**策略建议已给，自动旁路未实现**；当前需调用方按长度选择。
- **关闭条件**：协议层加「≥ 缓冲容量自动旁路」阈值（默认 4 KB）+ 基准确认
  4096B 不再回退；已有 `Socket::send_file` 可用于零拷贝。

### 3.5 UDP 批量：约 1.4×（环境）

`Socket::send_batch`（`sendmmsg`）在回环 UDP 上相对逐条 `send` 只有约 **1.4×**，
远低于 TCP bufio 的 21–33×。

原因：回环没有队列压力、单包路径已很短，`sendmmsg` 的批量收益被内核逐段处理
开销吃掉；**这是环境/口径**，不代表真实弱网无收益。另注意 UDP 批量语义是
「每段一条数据报」，必须用 `datagram=true`，不能照搬 TCP 的 `writev`。

- **优先级**：P3（回环结论不可外推到真实网络）。
- **状态**：环境相关，**待真实网络/高包速率复测**；不改默认。
- **关闭条件**：真实网络复测收益 <1.5× 则确认「仅回环如此」并关闭；
  若收益显著，把 `datagram=true` 写进 CoAP/Link 默认配置。
