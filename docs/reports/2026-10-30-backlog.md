## 2. 跨模块问题

### 2.1 channel 解耦不达标（P1-C1）

`channel.so` 的 NEEDED 闭包含 scheduler/fiber/log，最小消费者要链 6 个库。根因是
`Channel<T>` 为 `CanSpinWait` 内联判断去调 `Scheduler::current_task_ptr()` 与 Fiber 归属。
三条可选路径：① 把 parking/调度判定下沉到独立轻量目标；② 改为编译期钩子（函数指针注入）；
③ 接受耦合但在文档写明「channel 属并发栈，不是独立基础层」。当前审计建议 ①/②，未定稿。
影响面：任何想把 channel 单独复用的下游。

### 2.2 scheduler 8 MiB VA 预留（P1-2）

每个 G 预留 8 MiB 虚拟地址（初始仅提交 1 页），导致：
- 1000 parked G 峰值 VmSize 8.08 GB；10 万 G 819.7 GB、约 20 万个 VMA；
- 默认 `vm.max_map_count=65530` 时约 3 万并发 G 触顶（本机 1048576 才跑通 10 万）；
- 小内存/容器还需评估页表开销。
建议二选一：在 `SchedulerConfig`/文档固化「每 G 8 MiB VA、并发上限 ≈ max_map_count/2」的部署约束；
或提供更小的 `fiber_stack_reserve_size` 默认值/按需策略。当前**未修**，属部署文档级风险。

### 2.3 MCP 未自动 Register

SocketDebug 的 `SocketRegistry` 需要业务显式 `Register(fd,label,&err)` 才纳入白名单；
`socket_close` 对未登记 fd 一律拒绝。要真正覆盖业务 socket，必须改 `src/network`
（在 `Socket`/`accept`/`socket()` 创建点自动登记）。这被审计明确列为「待接入」，
也是 MCP 工具从「可演示」到「可运维」的分界线。当前**未做**。

### 2.4 审计 P2 的四个共性模式

按 26 份文档的 P2 归类，重复出现的是四类，而不是 118 个孤立缺陷：

| 模式 | 典型条目 | 影响 |
|---|---|---|
| 测试有效性（假通过） | 恒真断言（scheduler）、SKIP 逃逸（fetch/pairing/channel C5）、墙钟阈值（channel C9）、未注册 ctest（channel C2）、随机量不足（channel C6） | 回归给出虚假安全感，优先级应高于普通 P2 |
| 文档/实现漂移 | timer 对象池注释、channel `kAlreadyClosed`/`Range`（今日已修）、pairing `kAlreadyPaired`、session-table `kExpired`、bento-modules 计数 | 用户按文档写代码会错，成本低、收益直接 |
| 头文件依赖泄漏 | sync P2-3/P2-4、frame P2-6、relay P2-5、session-table P2-5、transport P2-7、heartbeat P2-2 | 编译时间与「自包含」结论失守，多为一行改动 |
| 安全边界 TOCTOU | command PATH/cwd、fetch 临时名/重定向、file-browser NUL、keystore 符号链接、mcp close fd 复用 | 仅在不可信输入下成立，需按部署形态定级 |

## 3. 优先级建议

### P0（0 项，库内）

今日无崩溃、无数据丢失、无未定义行为可直接触发。唯一「准 P0」是 **Bento 全链路无加密**
（`net-scenarios` E1：15/22 场景要求安全，当前帧头无 MAC、载荷明文、可伪造 STREAM 帧注入）。
它不属于「现存缺陷」，但**任何公网/半可信内网部署前必须先做**，否则其余 P1/P2 都无意义。

### P1（4 项 + 1 项部署前置）

| # | 项 | 理由 | 代价 |
|---|---|---|---|
| 1 | channel 解耦（C1） | 架构承诺「只依赖 base」已破，影响所有下游复用 | 中（需拆 parking 目标或注入钩子） |
| 2 | channel C2 注册 ctest | 817 行压测零覆盖，是当前最大的回归盲区 | 小（CMake 一行 + 小规模用例） |
| 3 | MCP 自动 Register | 决定 MCP socket 工具能否用于真实业务 | 中（改 `src/network` 创建点） |
| 4 | scheduler 8 MiB VA 部署约束 | 默认内核参数下 3 万并发即触顶，属可用性边界 | 小（文档/默认值），大（栈 arena） |
| 5 | Bento 安全基座 E1（准 P0） | 公网部署前置 | 大（与 E2/E3 合并改线格式） |

### P2（121 条，按主题分组排序）

1. **测试有效性**（最高价值）：scheduler 恒真断言/场景名不副实、channel C5–C8、sync P2-2、
   fetch P2-8、pairing P2-8、timer T4/T7——先修「会骗人的测试」。
2. **并发/生命周期正确性**：transport P2-4（fd 竞争/TOCTOU）、udp P2-5、network FdManager、
   relay 异常不 Close、scheduler P2-2 observer 口径。
3. **文档与 API 契约**：channel C3 测试侧、pairing P2-6、session-table P2-1、session P2 八条、
   bento-servers 状态同步——多数是半小时级改动。
4. **性能/资源**：network P2-2（O(n²)）、session-table 拷贝、relay 预分配、udp P2-1/2、
   timer T6、scheduler P2-8（文档化即可）。
5. **安全边界**：command P2-4/5/6/7、fetch P2-3/4/5、file-browser P2-4、keystore P2-5、
   crypto P2-4/5/6/7——按部署形态决定是否上移。
6. **Bento 协议验收**：6 个骨架的压测/随机/5 场景/audit，是 roadmap 任务 3 的唯一出口。

### P3（14 条）

测试时序去 sleep 化（channel C9/C10/C11、timer T8/T9）、注释与注册一致性（sync P3-1/2/3/4）、
fiber 覆盖缺口、`.clang-format` 落地（frame P2-7 / heartbeat P2-5，二者应合并为一次全局引入）、
zip 弱断言。建议随对应模块的下一次改动顺带清理，不单独排期。
