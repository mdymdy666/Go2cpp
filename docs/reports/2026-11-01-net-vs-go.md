# 网络性能对标 Go：TCP / UDP / HTTP / WebSocket / MQTT / CoAP（2026-10-31）

> 目标：同一台机器、同一负载下，把 go2cpp 的协议实现与 **Go** 对比，
> 要求「我们的耗时 ≤ Go 的 1.1 倍」（等价于吞吐 ≥ Go / 1.1）。
> 本文所有数字均为本机实测，不是引用外部典型值。

---

## 1. 环境与口径

| 项 | 值 |
|---|---|
| 机器 | WSL2 on Windows，AMD Ryzen 9 8945HX，12 硬件线程 |
| 绑核 | 服务端 `taskset -c 2,3`；压测客户端 `taskset -c 4,5,6,7` |
| Go | go1.27.1 linux/amd64，服务端 `GOMAXPROCS=2` |
| C++ | GCC 13，Release `-O3 -DNDEBUG`，`.build-bento-wsl` |
| 负载 | 回环 `127.0.0.1`，64B 消息，客户端串行 ping-pong（不流水线） |
| 客户端 | 同一份手写 Go 压测器测两边（每个协议一个最小客户端） |
| 统计 | 每连接独立 goroutine，建连 + 预热后同时起跑；`ops / 实际耗时` |
| 负载水平 | 各轮 `loadavg` 0.5-1.5（共享机器，未发现重负载） |

**为什么必须本机测 Go**：任务书给出的「Go 典型 50k-100k HTTP / ~1M TCP」
是原生 Linux 数字。本机 WSL2 的回环 RTT 约 110µs（单连接串行 ping-pong
的物理上限约 9k msg/s），**Go 在本机单连接也只有 5-7k**。因此本报告只与
「本机实测 Go」比较；单连接差距主要来自回环 RTT，多连接才反映服务端
CPU/调度效率。

## 3. 优化前（bento 线程模型）

| 场景 | 实现模型 | 1 连接 | 4 连接 | 16 连接 |
|---|---|---:|---:|---:|
| TCP echo | 每连接一 OS 线程 + poll | 8,178 | 28,168 | 116,595（16 线程） |
| UDP echo | 单线程 poll 循环 | 8,901 | 31,976 | 120,526 |
| HTTP | accept 线程 + 4/16 worker 池 | 7,184 | 25,463（4 worker） | 95,306（16 worker） |
| WS | accept 线程 + 4/16 worker 池 | 6,869 | 23,891（4 worker） | 79,367（16 worker） |

**这不是同资源对比**：TCP/UDP 用「每连接一线程」，HTTP/WS 用与连接数相同的
worker。把资源压到与 Go 相同的 2 个 OS 线程后，问题立刻暴露：

- HTTP 2 worker × 4 连接：**120 秒跑不完 4 万请求**——worker 被前两条
  keep-alive 连接独占，后两条连接在队列里饥饿；
- WS 2 worker × 4 连接：同样饥饿（60 秒超时）。

根因：accept 线程 + 固定 worker 池的模型里，**连接数 > worker 数就会饥饿**，
因为空闲的 keep-alive 连接始终占着 worker。

## 4. 优化项

### 4.1 `bento::HttpServer`：每连接一 Fiber

`Start()` 改为创建 `io::IOManager`（P/M 数 = `worker_threads`），accept 循环
本身是一个 Fiber，每接受一条连接再起一个 Fiber 跑「读请求 → handler → 写响应」。
连接数不再受线程数限制，与 Go `net/http` 的 goroutine-per-connection 同构。
读缓冲提升为连接级 16KB 堆缓冲（原来 8KB 栈数组会在 4KB 初始 Fiber 栈上触发
栈增长）。

### 4.2 HTTP 解析/序列化快速路径（`src/network/http.cpp`）

- `Response::to_string()`：去掉 `std::ostringstream`，改为一次 `reserve` +
  直接 `append`，状态码/长度用 `std::to_chars`；
- `Parser::feed_impl()`：起始行去掉 `std::istringstream`，改为手写三段切分；
  header 解析改用 `string_view`，不再为每行 `substr` 分配临时 string。

### 4.3 `bento::WsServer`：每连接一 Fiber

与 HttpServer 同构：IOManager + accept Fiber + 每连接 Fiber，握手缓冲改为
连接级堆缓冲。

### 4.4 WebSocket 帧热路径（`src/network/websocket.cpp`）

- **一帧一次 recv**：`read_exact` 增加 16KB 预读缓冲，逐字段读
  （2B 头 → 扩展长度 → 4B 掩码 → payload，最多 4 次 `recv`）改为一次
  `recv` 取回整帧；
- **小帧一次 write**：`write_frame_unlocked` 对「服务端 + payload ≤ 512B」
  的帧把 header 与 payload 拼接后一次 `write`（原来固定 2 次）。

### 4.5 UDP 批量收发（`tests/network/net_perf_server.cpp`）

UDP echo 用 `recvmmsg(2)`/`sendmmsg(2)` 批量收发（每批最多 64 条），
一次系统调用处理多条数据报；socket 与 Fiber 调度由 `net::Socket` +
`io::IOManager` 提供。

### 4.6 MQTT / CoAP 接入 Fiber 基准

同一套 IOManager：MQTT 每连接一 Fiber + 每连接一个 `MqttBroker`；
CoAP 一个 Fiber 串行 `recv_from` → `CoapServer::Handle` → `send_to`。

## 5. 优化后（每连接一 Fiber，服务端只用 2 个 OS 线程）

| 场景（2 线程公平口径） | 1 连接 | 4 连接 | 16 连接 |
|---|---:|---:|---:|
| TCP echo 64B | 8,220 | 25,296 | 110,501 |
| UDP echo 64B（批量） | 8,614 | 28,781 | 176,202 |
| HTTP GET /hello | 7,124 | 23,074 | 92,875 |
| WebSocket echo 64B | 8,110 | 25,432 | 96,835 |
| MQTT QoS0 回环 | 7,903 | — | — |
| CoAP CON GET | 8,325 | — | — |

### 倍数表（我们 / Go，>1 表示我们更快）

| 场景 | 1 连接 | 4 连接 | 16 连接 |
|---|---:|---:|---:|
| TCP echo | **1.23×** | **1.18×** | **1.22×** |
| UDP echo | **1.39×** | **1.22×** | **2.90×** |
| HTTP | **1.36×** | **1.10×** | **1.35×** |
| WebSocket | **1.23×** | **1.25×** | **1.07×** |
| MQTT | **1.20×** | — | — |
| CoAP | **1.14×** | — | — |

### 达标判定

要求是「我们耗时 ≤ 1.1 × Go 耗时」，即吞吐 **≥ 0.909 × Go**。

- **14/14 个场景全部达标**；
- 最差一项为 WebSocket 16 连接（1.07×，仍快于 Go），其余 1.10-2.90×；
- 共享机器典型波动 ±5%，最差两项仍在达标侧。

### 关键改善对比（优化前 → 优化后）

- HTTP 2 线程 × 4 连接：**>120s 跑不完** → 23,074 req/s（饥饿问题消失）；
- HTTP 16 连接：95,306（16 worker）→ 92,875（**2** worker），线程数降为 1/8；
- WS 16 连接：79,367（16 worker）→ 96,835（**2** worker，+22%）；
- WS 单连接：6,869 → 8,110（+18%，来自一帧一次 recv/一次 write）；
- UDP 16 连接：120,526（单线程）→ 176,202（+46%，recvmmsg/sendmmsg）；
- TCP 16 连接：116,595（16 线程）→ 110,501（**2** 线程，线程数 1/8，-5%）。

## 8. 局限

1. **单连接数字受回环 RTT 限制**（WSL2 ≈110µs），不反映 CPU 效率上限；
   多连接口径才用于判定服务端效率。
2. 客户端与服务端同机共享 12 个硬件线程，客户端占用 4 核，测量含其调度
   干扰；两边用同一客户端，因此对比是公平的。
3. MQTT/CoAP 只做单连接口径（与既有基准一致）：多连接时自订阅回环的
   路由放大/去重会混入客户端读放大，不能直接比较。
4. UDP 批量服务端依赖 `net::Socket::recv_batch/send_batch`（既有 API），
   本轮只把基准服务端接上，未改 `bento::UdpTransport`。

## 9. 复现

```sh
# 我方（.build-bento-wsl 已构建）
g++ -O3 -DNDEBUG -std=c++17 -I include -o /tmp/netbench/bin/nfs \
    tests/network/net_perf_server.cpp \
    -Wl,-rpath,$PWD/.build-bento-wsl -L .build-bento-wsl \
    -lgo2cpp_bento_omni -lgo2cpp_bento_ws -lgo2cpp_bento_socks -lgo2cpp_bufio \
    -lgo2cpp_bento_transport -lgo2cpp_channel -lgo2cpp_bento_http -lgo2cpp_bento \
    -lgo2cpp_hash -lgo2cpp_network -lgo2cpp_io -lgo2cpp_sync -lgo2cpp_context \
    -lgo2cpp_scheduler -lgo2cpp_fiber -lgo2cpp_log -lgo2cpp_error -lpthread -ldl
taskset -c 2,3 /tmp/netbench/bin/nfs http 0 2          # 打印 READY port=N
taskset -c 4-7 /tmp/netbench/bin/go-client -mode http -port N -conns 16 -count 5000

# Go 基线
go build -o go-server server.go && taskset -c 2,3 ./go-server -mode http -workers 2
```

压测程序：`/tmp/netbench/go/{server,client,ws,mqtt,coap}.go`（不入库）。
