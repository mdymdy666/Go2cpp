  单轮 256 帧 ≈333 KB 突发）；③ 单 Link = 单对端（架构级）；④ 无组播；⑤ 协议语义不归 Bento；⑥ 可观测不归 Bento。
- 优先级：**P0 三项**（安全基座、低延迟可靠恢复、实时流抗丢包）、P1 六项（首位多对端扇出）、P2 九项、P3 四项。

### 4.2 OmniNetServer 架构设计（`48d061e` + `b2eadb3`，[omni-net-design.md](../research/omni-net-design.md)，1069+3 行）

- 定位：不是「支持所有协议的服务器」，而是把**传输 / 协议 / 并发**拆成可替换部件，用 `Channel<T>` 把业务与网络解耦的组合式门面。
- 五条关键决策：组合不继承（5 个 `final` 类型化视图，无 `INetServer` 巨类）；`Channel<T>` 是唯一收发面；
  `mode` 与 `concurrency` 正交（`Blocking+Poll` 在 `Create()` 拒绝）；嗅探只在首包发生一次；分阶段 M0–M4（LinkServer → HTTP/SSE → WS/Raw → TLS）。
- 三个明确不做：单一巨虚类、运行时切换 fd 阻塞模式、把 relay/集群/服务发现塞进门面。
- 现状勘误（`b2eadb3`）：`transport`/`relay`/`session` 三层**尚未落代码**，按待建层处理；设计基线过时、待复核。

### 4.3 Socket Debug 模式调研（`def30b1`，[socket-debug-mode.md](../research/socket-debug-mode.md)，467 行）

- 推荐方案 D（A+B 混合）：热路径 per-socket 计数、事件复用既有事件环、视图复用 `debug::View`。
- 关闭近零：编译期 OFF 全宏空展开；运行时 Disable 仅 1 次 relaxed 读 + 1 分支。
- 七条盲区（G1–G7）：连接账本、字节/调用账本（`kIoRead/kIoWrite` 的 bytes 恒 0）、EAGAIN 与超时不可区分、
  100 ms 分片不可数、fd 复用导致归属丢失、关闭期不可观测、第三方 fd 无覆盖。
- 三条工程硬约束：拆零依赖目标、不要逐 socket 注册进 4096 资源表、socket 事件必须跳过栈捕获。

### 5.1 HTTP / SSE Server（`32ff39b`）

- 3 文件 1307 行；`Listen`（port=0 内核分配）、`OnRequest`、`AsSse`、`Start`、`Stop`（幂等）；
  复用 base `http::Request/Response/Parser`、`sse::Stream/Event`、`net::Socket`，未复制协议实现。
- 并发：默认 `Blocking`（1 accept + 4 worker，每连接串行，keep-alive）；`NonBlocking` 为预留枚举，
  `Start()` 显式返回 `UnsupportedModel`（不静默降级）。
- 关闭：置停止标记 → 关队列 → `shutdown(SHUT_RDWR)` 全部活动连接 → join accept → 关监听 → join worker → 兜底；
  返回后端口可立即重绑。
- 限制：无 TLS/HTTP2/路由参数/流式请求体/连接限流；解析错误直接断连；handler 内不要 `Stop()`。

### 5.2 WebSocket Server（`bad224b`）

- 3 文件 1701 行；复用 base RFC 6455 对象：`http::Parser` 读 Upgrade → `WebSocket::ValidateUpgradeRequest()` 校验 →
  `AcceptWithPending()` 写 101 并接管，Parser 多读的首帧不丢；非法请求回 400。
- 数据面 `OnConnection` / `OnMessage`；Ping/Pong 由 base 自动应答，Close 走 base 关闭握手；
  `WsConnection::Ptr` 可跨线程发送，`Stats()` 给计数。
- 限制：无 wss/TLS、permessage-deflate、子协议协商、鉴权、广播表、连接限流、逐片回调（base 已重组）。

### 5.3 LinkServer（`280e38e`）

- 3 文件 2029 行；同一端口 1:N 接入，同时承载 STREAM（可靠、自动分片约 330 KB）与 DATAGRAM（≤1300 B、不重传）。
- 内部只持一个 `PeerHub`；`Send` 不内部排队，窗口满（256 条 / 1 MiB）返回 `kWouldBlock`，由调用方重试或降级。
- 回调在 `RunOnce` 线程同步执行；`Stop()` 在同线程只置标志，确定性关闭需从其他线程调用。
- 限制：无多 socket 分片与迁移加固、无限流；`Listen/Start/Stop` 必须串行。

### 5.4 MQTT 3.1.1（`5b80e86`）

- 3 文件 3520 行，只依赖 C++17 标准库；九种控制报文、VLQ（上限 268435455）、流式解码（粘包/半包，非法帧清空缓冲）、
  订阅路由（`+`/`#`，`$` 开头不被吞）、QoS 0/1（含 PUBACK）、keepalive 1.5× 判定、遗嘱投递。
- 同批修复 **broker 路由哨兵 bug**（提交信息明确）；`MqttBroker` 要求先 `OpenSession`，client_id 不一致返回 `kProtocolViolation`。
- 限制：QoS 2 返回 `kUnsupported`；无持久会话（session present 恒 false）、retained、TLS/WS、用户名密码/ACL、共享订阅；
  非线程安全，调用方串行供字节流。

### 5.5 CoAP（`42b70b0`）

- 3 文件 2810 行；RFC 7252 线格式（Version/Type/TKL/Code/Message ID、选项 delta+length、Payload Marker）、CON/NON/ACK/RST。
- 客户端：单请求在途、自动 MID/Token、重传字节与首发一致、`ack_timeout_ms=2000` 起严格翻倍、最多 4 次（无抖动）。
- 服务端：CON 回 piggyback ACK、NON 回新 MID NON；按 (MID, Token) 去重命中后重发响应且不重复调 handler。
- 限制：无 DTLS/OSCORE、Observe、Blockwise、Proxy；去重缓存默认 8 条且无 247 s EXCHANGE_LIFETIME；非线程安全。

### 5.6 SOCKS5（`04372cb`）

- 4 文件 2833 行；分协议层（纯字节编解码）与服务端层（accept → 握手 → 拨号 → 中继）。
- 仅协商无认证 0x00（否则回 `05 FF` 并关闭）；ATYP 支持 IPv4/域名/IPv6；成功填 `getsockname` 的 `BND.ADDR/PORT`；
  半关闭传播；默认连接上限 128、握手 10 s、connect 5 s、空闲 60 s、缓冲 64 KiB；`Stats()` 给全量计数。
- 限制：无用户名密码/GSSAPI、BIND/UDP ASSOCIATE（回 0x07）、UDP 中继、TLS、ACL；DNS 在驱动线程同步 `getaddrinfo`。

### 5.7 TokenPairing（`c477095`）

- (key, token) 1:N 配对：三索引（token 主索引 + key→token 集合 + 回收计数）在同一把 `std::mutex` 内维护；
  8 字节随机 token → 16 位小写 hex；TTL 从 Pair 起算不续期；满容量先回收过期槽再拒绝，不淘汰活跃槽。
- 测试 13 用例 / **348,969 断言**（含 8 线程并发、固定种子 4000 步影子模型对拍、10 万串行压测）；
  TSan 0 race、ASan+UBSan+LSan 干净。
- 局限：非常量时间比较、Find/List 惰性回收（`size()` 可短暂含过期项）、无持久化、无按 peer 反查索引。

### 5.8 OmniNetServer M0（`7c77893`）

- 3 文件 2454 行 + cmake 恢复；`OmniNetConfig{mode, transport, protocols, concurrency, limits}`，
  `NetServer::Create()` 返回 `unique_ptr`，非法组合返回 `nullptr` + 中文诊断（固定 V1–V6 校验顺序）。
- M0 只接受 `Memory × Raw`：`MemoryTransport::CreatePair()` 回环 + `AttachConnection()`；每连接一对有界 `Channel<RawFrame>`
  （`Inbound()`/`Outbound()`）；`PollOnce()` 单驱动者：先排空 Outbound 再读传输，Inbound 满时暂停读并计
  `backpressure_events`（不丢帧）。
- 关闭：先关 Inbound → 写终值 `close_reason` → 关 Outbound → 关传输；`kGraceful` 一轮非阻塞排空后 `ShutdownWrite`，
  `kAbort` 直接 `Close`。
- 明确不做：真实 socket/bind/listen/accept、协议嗅探与 HTTP/SSE/WS/Link 数据面（`AsLinkServer()` 恒 invalid）、
  分帧（一帧 = 一次 `Read()`）、Fiber/线程池、优雅等待对端排空、`Port()` 恒 0、重启（`Stop` 终态）。
- 测试 8 用例 / **994 断言**（配置矩阵 20 组合、生命周期、Raw 回环、Channel 契约、多连接、统计、反压、边界），0 警告。

## 七、队列对比（channel / muduo / 无锁 SPSC）

> 状态：独立的 `channel_spsc` 对比报告**尚未落到 `docs/reports/`**（写作时该目录仅本文件与 16:40 版总结；
> 对比实验在 `/tmp/channel_bench` 与工作树 `tests/concurrency/bench_channel_opt.cpp` 进行中）。
> 下列数字来自该对比任务的结论，最终以该任务报告为准。

| 实现 | 单次操作开销 | 备注 |
|---|---:|---|
| muduo `BlockingQueue` 同构（mutex + deque + CV） | **38.5 ns** | 阻塞队列基线 |
| 无锁 SPSC 环形队列 | **4.1 ns** | 单生产者/单消费者、无阻塞语义 |
| `go2cpp::Channel`（无缓冲配对） | **15 µs** | 每次收发要经过调度器 park/unpark，含等待者唤醒 |

解读要点：

- 三者**口径不同**：前两者是「队列操作」成本，Channel 是「配对 + 调度」成本，不能直接相减；
  Channel 的吞吐口径（659,216 msg/s ≈ 1.52 µs/op）与本表的 15 µs 也不是同一测量方式（批量流水 vs 单次配对往返）。
- 结论方向：调度器介入使 Channel 比纯队列贵 2–3 个数量级，与 channel 审计「解耦不达标（依赖 scheduler/fiber）」
  是同一根因的两面；若后续要降低 Channel 单次延迟，应减少无缓冲配对的 park/unpark 次数，而不是改队列数据结构。
