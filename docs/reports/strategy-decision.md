# 战略决策：Go2Cpp 到底应该做什么

> 输入：`docs/reports/market-research.md`（354 行，外部市场）+ `docs/reports/capability-gap.md`（350 行，内部能力）。
> 方法：把外部机会与内部能力交叉，只保留「外部有需求 + 内部撑得住」的交集。
> 日期：2026-11-04。

## 一、两份报告的核心结论

### 外部（市场）

| 场景 | 胜算 | 依据 |
|---|---|---|
| C++ 实时长连接网关（WS/SSE/WebTransport） | **高** | Centrifugo PRO 商业版验证需求；C++ 侧无对位产品 |
| AI token 流式代理 | 中高 | Channel/Context 天然匹配；可能被推理引擎内置吞掉 |
| C++ 服务「Go 式并发」改造层 | 中 | 能力空位大；工具型难收钱 |
| 小内存边缘 | 中低 | Go 内存下限是硬事实；依赖/交叉编译是硬伤 |
| 帧同步/行情 p99 | 低 | 客户自研意愿强，无差异化 |

外部硬事实：Go 官方承认 20%+ CPU 在 GC；Seastar 承认复杂异步「notoriously difficult」；CISA/NSA 75% 在野 CVE 是内存安全。
**反面意见**：C++ 侧空白「可能不是蓝海而是墓地」。

### 内部（能力）

| 维度 | 事实 |
|---|---|
| 能做 | Linux 单机 API/短视频后端；**实时长连接（WS/房间）**；组件库嵌入现有 C++ 服务 |
| 做不了 | **跨平台**（仅 Linux/x86_64，CI 无 Windows）；**多机分布式**（孤岛/fencing 回退，16.5 人天）；**高写并发**（SQLite 单写者）/ CPU 密集（协作式调度） |
| 台账 | 19 条中明确达标仅 3（15.8%）；不达标 2（M03/M16 调度器 2.21×） |
| 应用证据 | douyin 69 PASS、feed 10.6k QPS/p99 4.2ms；bilibili 有代码无验收脚本 |

## 二、交叉矩阵

| 外部场景 | 内部能做？ | 差什么 | 结论 |
|---|---|---|---|
| **A 长连接网关** | ✅ 实时长连接是「能做」项 | 缺「规模数据」（20 万连接 RSS/p99）与「30 分钟上手」 | **首选，但要先用数据验证** |
| D AI 流式代理 | ✅ HTTP/SSE/Channel 齐全 | 缺流式背压/续传的专门实现 | 次选（复用 A 的流式基础） |
| B 改造层 | ✅ 组件库可嵌入 | 缺「嵌入指南 + cgo 规范」（已有 cgo 调研） | 可作为副线 |
| C 小内存边缘 | ⚠️ 依赖/交叉编译是硬伤 | 需要交叉编译 + 裁剪 + 依赖瘦身 | **与跨平台任务合并** |
| E 帧同步/行情 | ⚠️ 协作式调度 + 2.21× 差距 | 需要抢占/更低延迟 | 不做 |

## 三、决策：三件事，按顺序

### 1. 先用数据验证 A（2 周，最高优先）

**做什么**：20 万 idle WS 连接压测，对比 Go（Centrifugo 最小实现或自写 Go echo）。

| 指标 | 为什么关键 |
|---|---|
| RSS（每连接字节数） | Go 的 goroutine 栈 + GC 堆是硬成本；Go2Cpp 的 Fiber 栈固定，可能更省 |
| 心跳 p99 | Go 的 GC 停顿会在 p99 暴露；无 GC 是 Go2Cpp 的卖点 |
| CPU 占用 | 空闲连接下的调度开销 |

**判据**：如果 RSS 或 p99 明显优于 Go → A 方向成立；否则重新选。
**产出**：`docs/reports/ws-200k-bench.md` + 可复现脚本。

### 2. 并行补跨平台（用户今天第 2 点，也是 C 方向的前提）

**做什么**：Windows 构建（MSVC）+ 正确性分析（socket/文件/线程/时间/IO 多路复用的平台差异）。
**为什么**：内部盘点明确「仅 Linux/x86_64」是硬伤；用户也把跨平台列为今天任务。
**产出**：Windows CI job（真实构建，不是 continue-on-error）+ `docs/reports/platform-diff.md`。

### 3. 分布式 P0 作为长期基础（不阻塞 A）

**做什么**：NodeId + metrics + Trace（已在进行），后续 P1（MetadataStore + 快照持久化，修 fencing）。
**为什么**：内部盘点说多机分布式 16.5 人天、fencing 回退是「静默破坏正确性」；但 A（长连接网关）单机就够，分布式不阻塞它。
**产出**：P0 交付 + 三件套。

## 四、明确不做（至少现在）

| 不做 | 原因 |
|---|---|
| 游戏服务器 | 需要游戏框架（AOI/战斗/匹配），业务太厚 |
| 机器人遥操作 | 无真实硬件/场景，模拟 demo 价值虚 |
| HFT/帧同步 | 协作式调度 + 2.21× 差距，且客户自研意愿强 |
| 高写并发数据层 | SQLite 单写者，PostgreSQL/MySQL 客户端都没有 |

## 五、风险与诚实边界

1. **A 可能是墓地**：C++ 长连接网关要跟 Centrifugo/Nginx/Envoy 竞争，且运维面（部署/监控/热更新）我们几乎没有——所以先做压测，数据不好就不做；
2. **跨平台是大工程**：Windows 的 socket/文件/线程/时间差异会暴露很多隐藏假设，2 周只是「能构建 + 基础测试」，不是「生产可用」；
3. **台账达标率 15.8%**：说明大部分模块只有「实测」没有「判据」，对外宣传时不能说「全部达标」。

3. 分布式 P0 交付验收（NodeId/metrics/Trace 三件套）。
