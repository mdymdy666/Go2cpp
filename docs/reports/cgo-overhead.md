# cgo 调用开销实测报告

> 目的：量化「用 Go2Cpp 生成 C++ 库、Go 通过 cgo 调用做热点加速」这条路的真实成本，
> 回答「cgo 本身也有开销吧」这一质疑。所有数字均在本机实测，环境与方法见第 2 节。

## 1. 结论

**cgo 的固定开销约 17–18 ns/次（批量分块场景实测 29–32 ns/次），相当于 55–100 个
CPU 周期；这笔开销与数据大小无关，只与调用次数成正比。**

因此：

- **不可行**：高频小调用。任何「每个元素 / 每个像素 / 每个事件调一次 C」的设计，
  单次调用只处理几十到几百字节时，cgo 开销会吃掉 30%–300% 的收益，甚至纯亏。
- **可行**：批量接口。单次调用处理 **≥ 4 KB**、且 C++ 侧确有 **≥ 2× 真实加速**时开始
  划算；单次 **≥ 64 KB** 时固定开销占比降到 0.1% 以下，几乎可以忽略。
- **前提**：C++ 必须真的更快。实测同样的标量算法，**C 反而比 Go 慢 4%–20%**
  （第 3.7 节），跨语言本身不带来加速；真正能到 **14–17×** 的是 SIMD / 手工优化 /
  算法级改写。Go2Cpp 的价值必须建立在这类优化上，而不是「换成 C++ 就快」。

## 2. 测试环境与方法

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen 9 8945HX（8 核 16 线程，实测绑定 2 个逻辑核） |
| 内存 | 19 GiB（WSL2） |
| OS | WSL2 Ubuntu 24.04（内核 6.x） |
| Go | `go1.27.1 linux/amd64`（`/usr/local/go/bin/go`） |
| GCC | `gcc 13.3.0`（Ubuntu 13.3.0-6ubuntu2~24.04.1） |
| CGO | `CGO_ENABLED=1`（默认值） |
| 命令 | `taskset -c 2,3 ./bench`，每项跑 3–5 轮取中位数 |
| 代码 | `/tmp/cgo-bench/`（`main.go` / `bridge.c` / `bridge.h` / `asmnoop/`），仓库零改动 |

为避免「测量了编译器优化」而非 cgo 本身：

- C 侧函数全部定义在独立编译单元 `bridge.c`，跨 TU 调用无法内联；
- Go 侧基线用 `//go:noinline` 与独立的 Plan9 汇编包对照；
- C 与 Go 使用**完全相同**的 FNV-1a / 求和算法，逐字节处理，排除算法差异。

三次独立运行（下文括号内为波动范围），下文表格取第三次为代表值。

## 3. 实测数据

### 3.1 调用开销基线（1e7 次空调用）

| 场景 | ns/op | 相对纯 Go | 说明 |
|---|---:|---:|---|
| `C.c_noop()`（cgo 空调用） | **18.35**（17.55–18.55） | 14.6× | `void noop(void){}`，无参数无返回值 |
| `//go:noinline` 空 Go 函数 | 1.26（1.19–1.26） | 1.0× | 同样循环体，无 cgo |
| Plan9 汇编空函数 | 1.13（1.11–1.13） | 0.9× | `TEXT ·Noop, NOSPLIT, MOVQ+RET` |

**cgo 固定开销 = 18.35 − 1.26 ≈ 17.1 ns**。这 17 ns 是 `runtime.cgocall` 进入 C、
切换栈、保存 G/M 状态、返回时恢复的全部成本，与 C 函数体做什么无关。

### 3.2 传切片：`[]byte` → C（零拷贝直接传指针）

C 侧与 Go 侧执行同一份 FNV-1a 逐字节循环，唯一差别是数据在哪个运行时里被处理。

| 数据大小 | cgo 调用 ns/op | 纯 Go ns/op | 差值 | C 吞吐 | Go 吞吐 | 固定开销占比 |
|---:|---:|---:|---:|---:|---:|---:|
| 64 B | 59.12 | 37.59 | +21.5 | 1.1 GB/s | 1.7 GB/s | **36%** |
| 4 KB | 3,178.65 | 3,089.30 | +89.4 | 1.3 GB/s | 1.3 GB/s | 2.8% |
| 64 KB | 49,976.93 | 49,904.03 | +72.9 | 1.3 GB/s | 1.3 GB/s | **0.15%** |
| 1 MB | 819,897.65 | 798,801.12 | +21,097 | 1.2 GB/s | 1.3 GB/s | 2.6%（缓存溢出噪声） |

关键：**4 KB 以上时，cgo 与纯 Go 的耗时差在测量噪声内**（差值来自 C 与 Go 编译质量的
微小差异，不是调用开销）。1 MB 的 +21 µs 是 L3/内存带宽抖动，重复运行符号会翻转。
只有一个稳定结论：64 B 的小调用里，17 ns 固定开销占 36%，是实打实的损耗。

### 3.3 cgo 回调（C → Go，`//export`）

| 场景 | ns/op | 说明 |
|---|---:|---|
| `C→Go` 单次回调 `go_cb` | **27.24**（24.80–30.77） | C 侧循环 1e6 次，每次进 Go |
| `Go→C→Go` 完整往返 | **45.62**（41.75–47.25） | `c_roundtrip()` 内部立刻回调 |

回调比正向调用贵约 1.5×（27 vs 18 ns），因为它要走 `crosscall2` + `cgocallback` 的
额外栈切换。**每一层回调都在 17–27 ns 的量级上叠加**，链式回调（C→Go→C→Go）会线性变贵。

### 3.4 批量摊薄：同样 64 KB 工作量，一次调 vs 分块调

| 场景 | 每轮 64 KB 耗时 | 相对 | 说明 |
|---|---:|---:|---|
| 1 次调用 `c_memcpy(64KB)` | **863.29 ns** | 1.00× | 一轮一个 C 调用 |
| 64 次调用 `c_memcpy(1KB)` | **2,899.07 ns** | **3.36×** | 同样总量，一轮 64 个 C 调用 |
| 计算密集对照：1 次 FNV 64KB | 50,250.93 ns | 1.00× | 计算主导 |
| 计算密集对照：64 次 FNV 1KB | 51,325.85 ns | 1.02× | 调用次数被计算淹没 |

由 (2899.07 − 863.29) / 63 得**每次调用的边际固定开销 32.31 ns/次**（含 1 KB 拷贝的
函数调用建立成本）。分块搬运时 64 次调用白白多花约 2.0 µs，是 1 次调用的 2.4 倍。
而当每次调用的计算量足够大（FNV 64 KB ≈ 50 µs）时，64 次 vs 1 次只差 2%，固定开销
完全被计算掩盖——**这就是「批量摊薄」的全部含义**。

### 3.5 GC 交互

| 场景 | 结果 | 说明 |
|---|---|---|
| cgo 空调用 p50（无 GC 压力） | 18.35 ns | 基线 |
| cgo 空调用 p50（GOGC=20 + 后台持续分配） | **14.33 ns** | 中位数不变 |
| cgo 空调用 p99（同上） | **431.74 ns**（149–832） | 尾部放大 30–45× |
| cgo 空调用 max（同上） | **761.77 ns**（492–1130） | 最坏 53× |
| `runtime.GC()` 前 p50 / p99 | 15.33 / 47.94 ns | — |
| `runtime.GC()` 后 p50 / p99 | **19.28 / 138.86 ns** | p50 +26%，p99 +190% |
| `Pinner.Pin` + cgo + `Unpin`（64 KB） | 49,479.75 ns | 对照未 pin 的 49,976.93 ns，**无额外开销** |
| `cgo.Handle` New+Delete（含一次 C 存取） | **121.91 ns**（120–129） | 跨语言传对象的推荐做法 |
| `GOEXPERIMENT=cgocheck2` 空调用 | 16.52 ns | 与常规 18.35 ns 无显著差异 |

解读：

- **中介数不受 GC 影响**，但**尾部会被放大 30–50×**：GC 期间 cgo 调用的 p99 从 18 ns
  涨到 0.4–0.8 µs。对延迟敏感的服务，这比平均开销更值得关注。
- `runtime.GC()` 之后的第一批调用 p99 从 48 ns 涨到 139 ns，是栈扫描 + P 状态重建的
  一次性别扭，会被后续调用摊平。
- **`runtime.Pinner` 在当前 Go 上几乎免费**：pin/unpin 一对操作的成本低于测量噪声。
  这说明「传 Go 指针给 C」本身不贵，贵的是语义风险（C 不能长期持有），不是 pin 动作。
- **`cgo.Handle` 约 122 ns/次**，比裸指针贵 6–7 倍，但换来跨 GC 的绝对安全。

### 3.6 数据转换成本

| 场景 | ns/op | 带宽 | 说明 |
|---|---:|---:|---|
| `C.CBytes(64KB)` + `free` | **816.01** | 80 GB/s | 多一次 malloc + memcpy |
| 直接传 `&buf[0]`（C 只读 1 字节） | **17.05** | — | 零拷贝，纯固定开销 |
| C 侧 `memcpy` 64 KB | 866.48 | 76 GB/s | `__builtin_memcpy` |
| Go `copy` 64 KB | 825.28 | 79 GB/s | 内建 copy |
| C 侧 `memcpy` 1 MB | 15,872.28 | 66 GB/s | — |
| Go `copy` 1 MB | 46,923.08 | 22 GB/s | 大块拷贝 Go 慢约 3× |

结论：**不要用 `C.CBytes`**。64 KB 数据一次 `CBytes` 就是 816 ns，比一次 cgo 调用本身
贵 48 倍；用 `&buf[0]` 传指针是 17 ns。只有在 C 侧需要**长期持有**并可能被 Go GC 回收
时才需要拷贝或 `Pinner`。

### 3.7 C 侧「真实加速能力」：标量 vs SIMD vs Go

同一份「逐字节求和」，三种实现：

| 数据大小 | Go 标量 | C 标量 | C AVX2 | AVX2 vs Go | AVX2 vs C 标量 |
|---:|---:|---:|---:|---:|---:|
| 4 KB | 856.09 ns | 931.39 ns | **59.59 ns** | **14.4×** | 15.6× |
| 64 KB | 12,329.88 ns | 14,212.17 ns | **745.65 ns** | **16.5×** | 19.1× |
| 1 MB | 206,232.23 ns | 237,453.71 ns | **11,879.57 ns** | **17.4×** | 20.0× |

**这是全篇最重要的对照**：

- 同样的标量循环，**C 比 Go 慢 4%–20%**（三次运行区间；Go 的编译器对这类循环生成了
  更紧凑的代码）。「用 C++ 重写」本身不会带来任何加速，反而可能更慢。
- 真正的 14–17× 来自 **AVX2 手工向量化**，与语言无关——Go 里手写 Plan9 AVX 汇编同样
  能做到（只是可维护性差很多）。
- 因此 Go2Cpp 的加速故事必须是「**把能向量化/能改写算法的热点搬到 C++**」，
  而不是「把 Go 代码翻译成 C++」。

### 3.8 cgocheck=2 对照

Go 1.27 已移除运行时 `GODEBUG=cgocheck=2`，直接设置会 `fatal error: cgocheck > 1 mode
is no longer supported at runtime`。必须 **`GOEXPERIMENT=cgocheck2` 编译期开启**。

开启后实测：空调用 16.52 ns、64 KB 传递 46,622.83 ns、回调 25.34 ns，与常规构建差异
在噪声内（≤10%）。**cgocheck2 适合调试期抓错误，不是性能负担。**

## 4. 开销分解

| 组成 | 量级 | 是否随数据量增长 | 备注 |
|---|---|---|---|
| 调用固定开销 | **17–18 ns/次** | 否 | `runtime.cgocall` + 栈切换 + G/M 状态保存 |
| 分块调用的边际成本 | **29–32 ns/次** | 否 | 含 C 函数建立、参数封送、短循环启动 |
| 数据拷贝（`CBytes`） | 12 ns/KB（80 GB/s） | **是** | 能避免就避免 |
| 数据拷贝（`copy`） | 12–45 ns/KB | **是** | 大块时 Go 的 `copy` 反而更慢 |
| GC 交互（中介数） | ≈0 | 否 | pin 免费，Handle 122 ns |
| GC 交互（尾部） | **+0.4–0.8 µs (p99)** | 否 | 对延迟敏感场景才是真问题 |
| 回调（C→Go） | **+27 ns/次** | 否 | 比正向贵 1.5×，链式回调线性叠加 |

**没有「隐藏的线程切换」**：Go 1.14 之后 cgo 调用不再需要把 P 交给其他 goroutine 太久，
实测空调用 18 ns 已经包含了全部调度成本。真正的线程成本出现在「C 侧长时间阻塞」时——
那会占住一个 M，但不会阻塞 Go 调度器，属于 cgo 的优点而非缺点。

## 5. 适用边界（阈值）

判据有两个，缺一不可：

**(a) 开销占比判据**（更实用）：单次调用的工作量要让 17–18 ns 的固定开销占比足够小。

| 单次处理 N | 纯 Go 耗时（按 1.3 GB/s） | cgo 开销占比 | 判定 |
|---:|---:|---:|---|
| 64 B | 49 ns | **36%** | 不可行 |
| 512 B | 394 ns | 4.4% | 勉强，需 k ≥ 2 |
| 4 KB | 3.15 µs | **2.8%** | 可行 |
| 64 KB | 50 µs | **0.15%** | 免费 |
| 1 MB | 807 µs | 0.002% | 免费 |

按「开销占比 ≤ 5%」反解：**单次处理 ≥ 440 字节**；按「≤ 1%」：**≥ 2.2 KB**。
若目标热点的 Go 实现远慢于 1.3 GB/s（图像处理常只有 100–300 MB/s），同样占比对应的
字节数同比下降，但那时 C++ 侧也更容易拿到高 k，两者大致抵消。

**(b) 收益判据**：C++ 必须真的更快。设加速比为 k，则过桥的净收益为

```
净收益 = t_go × (1 − 1/k) − 17 ns − 拷贝成本
```

以 t_go = 0.77 ns/字节（1.3 GB/s）代入，理论回本点：

| C++ 加速比 k | 理论最小 N（无拷贝） | 说明 |
|---:|---:|---|
| 1.1×（几乎没优化） | 243 B | 收益太薄，任何抖动都会吃掉 |
| 1.5× | 66 B | 回本但无余量 |
| 2× | 44 B | 算术上很早回本，但见下方工程余量 |
| 5× | 28 B | — |
| 10×（SIMD 级） | 25 B | SIMD 场景下调用开销可忽略 |

理论回本点很小（几十字节），但**不能照此设计**，因为：测量抖动、GC 尾部（p99 放大
30–50×）、缓存局部性、以及小分块根本喂不饱 SIMD 单元。工程阈值应在此基础上留余量：

- **单次处理 ≥ 4 KB**：cgo 开销 ≤ 3%，可以放心用；
- **单次处理 ≥ 64 KB**：开销 ≤ 0.15%，等于免费；
- **单次处理 < 512 B**：无论 C++ 多快都不划算，逻辑留在 Go 里；
- **调用频率 > 10 万次/秒**：17 ns × 1e5 = 1.7 ms/s，仅调用占 0.17% CPU，尚可；
- **调用频率 > 100 万次/秒**：纯调用开销 ≥ 1.7% CPU，且 GC 尾部会被高频放大，必须批量化。

## 6. 替代方案对比（结论 + 依据，未全部实测）

| 方案 | 调用开销 | 适用性 | 依据 |
|---|---|---|---|
| **cgo**（本报告） | 17–32 ns/次 | 批量接口、低频大块 | 实测 |
| **纯 Go 汇编**（Plan9） | **1.1 ns/次** | 极致热点、SIMD 内核 | 实测 1.13 ns，比 cgo 快 16×，但可维护性差、需按架构分文件 |
| **`//go:noescape`** | 与普通调用同 | 只是免掉逃逸分析/堆分配，**不消除 cgo 开销** | 语义保证，非性能银弹 |
| **Rust FFI** | 与 cgo 同量级 | 同 cgo，安全性更好 | Rust 的 `extern "C"` 调用同样要过 `crosscall2`，无本质差异 |
| **WASM**（wazero/wasmtime） | **µs 级** | 沙箱/插件，不适合热点 | 解释或 JIT 边界成本比 cgo 高 1–2 个数量级 |
| **gccgo** | 同 Go 调用 | 无跨界成本，但 GC/生态受限 | 纯 Go 编译，无 cgo 边界，代价是工具链与标准库兼容性 |

结论：**能用纯 Go（含手写汇编）解决就别开 cgo**；必须用 C++ 生态时，cgo 是当前最优解，
Rust FFI 与它同量级，WASM 不适合本场景。

## 7. 对本项目（Go2Cpp）的建议

1. **批量接口是唯一正确的形态**。所有导出函数都应接受 `(ptr, len)` 或「任务数组」，
   一次调用处理整块/整批数据。禁止逐元素、逐像素、逐事件的导出函数。
2. **零拷贝传指针**：用 `unsafe.Pointer(&buf[0])` + 长度，禁止 `C.CBytes`（816 ns/64KB）。
   缓冲区由 Go 侧预分配并复用，避免每次调用 malloc。
3. **禁止回调**：C→Go 回调 27 ns/次，链式回调线性叠加。若 C 侧需要「回调通知进度」，
   改成一次性返回结果数组，由 Go 侧遍历。
4. **用 `cgo.Handle` 而不是裸指针**：需要跨调用传对象时（122 ns/次），
   `cgo.NewHandle`/`Delete` 保证 GC 安全；裸 `unsafe.Pointer` 在 C 长期持有时是 UB。
5. **只在 SIMD / 算法级改写时启用 C++ 加速**：标量跨语言无收益（实测 C 反而慢 8–19%）。
   Go2Cpp 的编译产物应当成为「向量化内核」的载体，而不是「Go 的另一种写法」。
6. **按帧调度**：若目标是音视频处理，每帧一次调用（1080p RGBA = 8.3 MB/帧），
   cgo 开销占比 < 0.001%，可以忽略；帧内所有像素级工作都放在 C++ 侧一次做完。
7. **不要为了「也许更快」而引入 cgo 边界**：cgo 会让构建变慢、交叉编译变难、
   二进制变大（动态链接 libc）。这些成本不在本报告的 ns 表里，但真实存在。

## 8. 复现命令

```bash
# 一次性编译
cd /tmp/cgo-bench && go build -o bench .

# 主实验（绑定 2 个逻辑核，跑 3–5 轮取中位数）
taskset -c 2,3 ./bench

# cgocheck2 对照（Go 1.27 必须编译期开启）
GOEXPERIMENT=cgocheck2 go build -o bench_cg2 .
taskset -c 2,3 ./bench_cg2 -scale=20

# 快速验证（迭代次数缩小 20 倍）
./bench -quick
```

实测原始输出保存在 `/tmp/cgo-bench/result.txt`（随 /tmp 清理而消失，数据已固化到本报告）。

## 9. 局限

- 绑定 2 个逻辑核（同一 CCX），未覆盖跨 NUMA / 跨 CCX 场景；跨核调度的 cgo 延迟可能更高。
- 仅测 amd64；ARM64 上 cgo 的寄存器保存更多，开销可能略高（未实测）。
- GC 尾部数据波动较大（p99 在 149–832 ns 之间），表中给的是范围而非单点。
- 未测「C 侧长时间阻塞（>10 ms）」对 Go 调度的影响，那属于 cgo 的优势场景而非开销。
