# 六协议正确性与性能统一基准（2026-10-31）

> 范围：HTTP/SSE、LinkServer、WebSocket、MQTT、CoAP、SOCKS5 六个协议 + OmniNetServer M1
> （AsLinkServer / AsHttpServer）。只新增 `tests/bento/bench_protocols.cpp` 与本文档，
> 未改动任何协议实现。
>
> 结论先行：**37 个真实场景 / 237 条断言 / 0 失败**；单连接吞吐 HTTP 7.7k req/s、
> WS 5.4k msg/s、MQTT 8.8k msg/s、CoAP 9.4k req/s、Link 可靠 8.3k msg/s、
> OmniNet 8.0k msg/s；SOCKS5 中继 911 MB/s。写路径三档对比显示**小包走 bufio
> 可把系统调用从 1 条/消息降到 1/32~1/64，吞吐提升 21~33 倍**，而 **≥4KB 的大包
> 用 bufio 反而慢 19%**——这是「最优配置」的核心分界线。

---

## 1. 环境与口径

| 项 | 值 |
|---|---|
| CPU | 12 硬件线程（WSL2 on Windows），`taskset -c 2,3` 绑 2 核 |
| 构建 | `.build-bento-wsl`，`Release`（`-O3 -DNDEBUG`），Ninja |
| 编译器 | `/usr/bin/c++`（GCC 13） |
| 网络 | 全回环（TCP `127.0.0.1` / UDP `127.0.0.1`），无外部依赖 |
| 计时 | `std::chrono::steady_clock`，纳秒采样后换算 µs |
| 负载 | 各批次 `loadavg` 1.39~2.23（共享机器，测量时已确认无重负载） |
| 轮次 | 每项 3 轮取最佳；每轮前有预热（不进统计） |

**延迟口径**：除特别注明，延迟是「发送前 → 收到完整响应」的单次往返（RTT），
含本进程调度与回环协议栈开销，**不是硬件 RTT**；横向比较有效，绝对值不可外推
到跨机场景。Link 的可靠通道额外区分「流水线端到端（含排队）」与「串行单程」。

**吞吐口径**：`ops / 实际耗时`（steady_clock），不是名义时长。HTTP/WS/MQTT/CoAP
的 ops 是完整请求-响应；Link 的 ops 是「发送方入队 → 对端回调」一条消息；
SOCKS5 的 ops 是「TCP 建连 → 握手 → CONNECT → 关闭」一条连接。

## 3. 性能统一基准表

> 单连接串行 = 一条 TCP/UDP 连接上严格「请求→响应→请求」；并发 = 每线程独立连接。
> 表中 `-` 表示该场景未采延迟样本（并发/带宽类场景只看吞吐）。

### 3.1 六协议主表

| 协议 | 场景 | 吞吐 | p50 (µs) | p99 (µs) | p999 (µs) |
|---|---|---|---|---|---|
| **HTTP** | GET /hello 单连接 keep-alive | **7,695 req/s** | 120.06 | 263.16 | 439.16 |
| HTTP | GET /hello 4 并发连接 × 1500 | **67,350 req/s** | - | - | - |
| HTTP | GET /big 16KB 单连接 | **6,809 req/s**（≈106 MB/s） | 132.61 | 285.69 | 309.38 |
| **WS** | 文本 32B echo 单连接串行 | **5,366 msg/s** | 162.62 | 370.46 | 527.33 |
| WS | 二进制 1KB echo 单连接 | **5,295 msg/s**（≈5.2 MB/s） | 171.13 | 353.73 | 542.78 |
| WS | 文本 echo 4 并发 × 400 | **9,044 msg/s** | - | - | - |
| **MQTT** | QoS0 PUBLISH 64B 自订阅回环（TCP） | **8,778 msg/s** | 100.15 | 238.33 | 463.86 |
| MQTT | broker 内存路由 64B（无 socket） | **4,877,505 ops/s** | - | - | - |
| **CoAP** | CON GET 串行（真实 UDP） | **9,449 req/s** | 97.63 | 207.51 | 237.25 |
| CoAP | NON GET 串行（真实 UDP） | **10,374 req/s** | 92.01 | 197.75 | 212.55 |
| **SOCKS5** | 握手 + CONNECT IPv4 + 关闭 | **45 conn/s** | 831.94 | 51,682 | 51,896 |
| SOCKS5 | 中继双向 4MB（64KB 块） | **911 MB/s** | - | - | - |
| **Link** | 可靠 STREAM 64B 单向 | **8,311 msg/s** | 77.57 | 139.76 | 139.76 |
| Link | 不可靠 DATAGRAM 64B 单向（节流） | **46,254 msg/s** | 12.71 | 102.11 | 312.95 |
| **OMNI** | AsLinkServer 可靠 64B 单向 | **8,021 msg/s** | 20,180¹ | 37,936¹ | 42,462¹ |
| OMNI | AsHttpServer GET 单连接 | **7,926 req/s** | 111.79 | 284.52 | 364.62 |

¹ OmniNet 的 Link 延迟是**流水线端到端**（2000 条一次性入队，含发送队列等待），
不是空载单程延迟；同一链路的空载单程参考独立 LinkServer 的串行采样 77.57µs。

### 3.2 读法与异常点

- **HTTP 4 并发 67k req/s**：2 核绑定时 4 worker 的聚合吞吐；单连接 7.7k 说明
  单连接受 RTT 支配（≈130µs/请求），并发才能吃满 worker。
- **WS 比 HTTP 低约 30%**：WS 每条消息多一层帧编解码与掩码校验；4 并发只到
  9k，因为服务端 `WsServer` 的回调是「读循环内同步 echo」，同一连接内无法流水线。
- **MQTT 内存路由 4.88M ops/s 与端到端 8.8k 差 550 倍**：这组数据说明 MQTT 的
  瓶颈完全在 TCP 往返，不在 broker 的会话表/通配符匹配。
- **CoAP 9.4k~10.4k**：UDP 无连接建立、单请求在途；NON 略快于 CON（无需 ACK 等待）。
  注意本机另一次低负载运行曾测到 50.6k req/s，差异来自共享机器调度（同一二进制、
  同一负载模型），报告采用与其他协议同时段的批次，跨次比较请以同一批次为准。
- **SOCKS5 建连 45 conn/s 但 p99 51.7ms**：`p50=832µs` 说明多数连接很快，约 2%
  的连接出现 ~50ms 停顿（疑似 accept 轮询/线程调度，未深入定位）。中继吞吐
  911 MB/s 不受影响。**这是本次基准里唯一一个「吞吐被非协议因素主导」的指标**，
  引用时请带上 p99 说明。
- **Link 可靠 8.3k vs 不可靠 46k**：可靠通道有 ACK/重传/拥塞窗口，不可靠通道
  直写 UDP；两者相差 5.6 倍，符合设计预期。

## 4. 写路径三档对比（单写 / bufio / bufio+batch）

> 场景：一条回环 TCP 连接，客户端连续写 N 条协议真实报文（HTTP 响应 120B、
> WS 帧 64B、MQTT PUBLISH 96B、CoAP 响应 64B、大消息 4096B），对端独立线程
> 排空。每档 3 轮取最佳。`syscalls` 来自 `SocketBatchWriter` 的
> `send_calls/writev_calls` 计数，是「批量是否真的生效」的硬证据。

| 报文 | 单写 send | bufio(4KB,kHybrid) | bufio+batch(64,writev) | 单写 syscall/msg | bufio | batch |
|---|---|---|---|---|---|---|
| HTTP 响应 120B | 144,433 ops/s | **3,335,649**（23.1×） | **3,925,869**（27.2×） | 1.000 | 0.029 | 0.031 |
| WS 帧 64B | 186,480 ops/s | **5,072,555**（27.2×） | **6,181,102**（33.1×） | 1.000 | 0.016 | 0.016 |
| MQTT PUBLISH 96B | 181,607 ops/s | **3,906,118**（21.5×） | **3,886,612**（21.4×） | 1.000 | 0.023 | 0.031 |
| CoAP 响应 64B | 183,892 ops/s | **5,099,062**（27.7×） | **4,988,958**（27.1×） | 1.000 | 0.016 | 0.016 |
| 大消息 4096B | **151,121 ops/s** | 122,721（0.81×） | 146,702（0.97×） | 1.000 | 1.000 | 1.000 |

**结论（最优配置的分界线）**：

1. **小包（< 缓冲容量，典型 <4KB）**：bufio 把 32~64 条消息合并成 1 次系统调用，
   吞吐提升 **21~33 倍**；`bufio+batch` 与纯 bufio 在同一量级（4KB 缓冲已经能攒满
   64 段，writev 的额外收益在 64B 档最明显 +22%，在 120B/96B 档基本持平）。
2. **大包（≥ 缓冲容量，如 4096B）**：bufio **反而慢 19%**——每条消息都超过/等于
   缓冲，退化成「直写 + 一次内存拷贝」，系统调用数仍是 1/msg。此时应**绕过 bufio
   直接 `send`/`writev`**，或走 `sendfile` 零拷贝。
3. **batch 的真实价值**：不是「比 bufio 快多少」，而是**把「何时成批」从调用方
   的手工 buffer 变成可配置策略**（`max_batch`/`threshold`/`interval`/4 种
   `FlushPolicy`），并在 UDP 上走 `sendmmsg`（每个段一条数据报，与 TCP 的
   `writev` 语义不同）。

## 5. 最优配置建议（按协议）

| 协议 | 推荐写路径 | 理由 |
|---|---|---|
| **HTTP/SSE** | 小响应（<1KB）走 `bufio::Writer(4KB, kHybrid)`；16KB 级响应直写（`writev`/`sendfile`） | 3.1 表里 16KB 只有 6.8k req/s，瓶颈是「每条响应一次 write + 一次拷贝」；SSE 事件小且频繁，bufio 收益最大 |
| **WS** | 接 bufio；`max_batch=64`、4KB 缓冲 | 64B 帧 33× 提升；WS 帧本身短，服务端 echo 场景几乎全是小包 |
| **MQTT** | 接 bufio；broker 侧 outbound 批量 `FlushBatch` | PUBLISH 96B 有 21× 提升；broker 内存路由已达 4.9M/s，写路径是唯一瓶颈 |
| **CoAP** | UDP 模式 `SocketBatchWriter(datagram=true)` + `sendmmsg` | 64B 响应 27×；UDP 批量语义与 TCP 不同（每段一条数据报），必须用 datagram 模式 |
| **SOCKS5** | 中继走大块直写（64KB 块已 911 MB/s），握手阶段无优化价值 | 握手是 3 次 2~10B 往返，受 RTT 支配；中继是大块流，bufio 无收益 |
| **Link** | 可靠通道批量入队 + `sendmmsg`；不可靠通道需要**发送节流**（否则丢包率 >90%） | 8.3k（可靠）/46k（不可靠）都受单条系统调用限制；不可靠直写会撑爆内核接收缓冲 |
| **OmniNet M1** | 复用后端建议；HTTP 视图注意 `max_requests_per_connection` 默认 100 | 基准里 keep-alive 100 请求后服务端主动关连接，吞吐测试必须放宽 |

**全局建议**：
- **服务端 accept 后设 `TCP_NODELAY`**（见第 6 节，当前实现的缺口）；
- 协议层默认 **bufio 开启、阈值 4KB、kHybrid**；大消息按长度阈值自动旁路；
- worker 数 4 在 2 核绑定时足够（HTTP 并发 67k req/s），更多线程只增加调度开销。

## 6. 关键发现与踩过的坑（都是实测，不是推测）

### 6.1 服务端 accept socket 没有 `TCP_NODELAY`（实现层可优化）

WS 串行 echo 基准最初**跑到约 100 条后整段挂住**。`ss -tinp` 现场显示：

```
服务端 fd=5  Send-Q 34  notsent:32  unacked:1
客户端 fd=4  Recv-Q 0   Send-Q 0
```

服务端有 32 字节（echo 帧）卡在 `Send-Q` 未发出，客户端在 `recv` 等。原因是
**服务端 accept 出来的 socket 没设 `TCP_NODELAY`**，小包被 Nagle 压住，而客户端
Linux 默认延迟 ACK 40ms——一次 40ms，2000 次就是 80 秒，看起来像死锁。

基准侧的解法：客户端每次读前设 `TCP_QUICKACK`（一次性开关，强制立即 ACK），
单次 `setsockopt` 约 1µs，可忽略。**产品侧的正确解法是在 `WsServer`/`HttpServer`/
`Socks5Server` accept 后设 `TCP_NODELAY`**——这也是本报告对实现层的唯一硬建议。
SOCKS5 建连的 p99 51.7ms 很可能同源（握手是 2~10B 小包往返）。

### 6.2 CoAP 客户端默认随机种子固定，会导致跨客户端「假重复」

`CoapClientConfig::random_seed` 默认是固定值，两个新客户端会生成相同的
`(Message ID, Token)`，被服务端的去重缓存判定为重复请求，**返回上一个请求的响应**。
基准里表现为「PUT 返回了上一个 GET 的 2.05」。修复方式：每个客户端用不同种子
（基准用 `NowNs() ^ 常量`）。这是协议客户端的合理默认值（可复现），但多实例
共存时必须显式换种子。

### 6.3 Link 可靠通道的延迟必须串行采样

流水线发 2000 条时，若有样本取自「发送队列」，p50 会变成 20ms（排队时间），
完全掩盖真实延迟。基准改为**吞吐用流水线、延迟单独串行 30 条**，得到 77.57µs。

### 6.4 不可靠通道不节流 = 测丢包率，不是吞吐

直写 UDP 连续发 3000 条 64B，到达率跌到个位数百分比（内核接收缓冲溢出）。
每 16 条让出 100µs 后稳定在 46k msg/s、到达率 >95%。**报告任何不可靠通道吞吐
都必须带到达率**。

### 6.5 `bufio::Writer::Write` 的返回值是「接受字节数」，不是「已写出」

大消息（4096B）档必须循环写剩余部分，否则会被误判为失败。同理 `Socket::send`
会部分写，`SingleWrite` 档也做了补齐循环。

## 7. 复现

```sh
# 构建（工作树根目录）
cmake -S . -B .build-bento-wsl -DGO2CPP_WITH_BENTO=ON -DCMAKE_BUILD_TYPE=Release
ninja -C .build-bento-wsl bento_bench_protocols

# 正确性（37 场景 / 237 断言；ctest 也会跑这一部分）
taskset -c 2,3 ./.build-bento-wsl/bento_bench_protocols --correctness

# 性能（分协议或全量；建议绑核并确认 loadavg < 4）
taskset -c 2,3 ./.build-bento-wsl/bento_bench_protocols --perf
taskset -c 2,3 ./.build-bento-wsl/bento_bench_protocols --perf --only=http,ws,mqtt,coap
taskset -c 2,3 ./.build-bento-wsl/bento_bench_protocols --perf --only=socks5,link,omni,write
```

退出码：0 = 全部场景通过；1 = 有断言失败（失败项打印在 stderr）。

## 8. 未覆盖 / 已知限制

1. **SOCKS5 建连 p99 的 50ms 停顿未定位到根因**（怀疑 accept 轮询与线程调度），
   只给出实测值与中继带宽；未做内核参数（`tcp_tw_reuse`、`somaxconn`）调优对比。
2. **TLS/DTLS、HTTP/2、MQTT 5.0** 不在本次范围（协议实现本身未提供）。
3. **跨机数据缺失**：全部为回环，回环没有真实 RTT/丢包/带宽限制；跨机数字需重跑，
   结论（bufio 小包收益、大包旁路阈值）预计仍然成立，但绝对值会低一个量级。
4. **延迟只测了 RTT**，没有测服务端内部处理时间（handler 耗时）；SSE 只验证了
   推流正确性，没做长连接持续推流的吞吐。
5. 共享机器上的其它 agent 会周期性改动工作树（本次就遇到 `context.cpp` 处于
   中间态导致全量 ninja 失败，最终用独立目标编译 + 已有库手工链接绕过）。
