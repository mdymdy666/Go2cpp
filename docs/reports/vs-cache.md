## 0. 结论速览

| 维度 | 结果 | 判定 |
|---|---|---|
| 策略覆盖 | **7 种**（LRU / LRU-K(2) / 2Q / W-TinyLFU / GDSF / ARC / CLOCK） | 超过 Caffeine（其核心仅 W-TinyLFU + 变体） |
| 命中率（热点） | ARC 0.7817 / LRU-K 0.7904 / W-TinyLFU 0.7821 / GDSF 0.7693 vs LRU 0.5580 | **比 LRU 高 21–23 个百分点** |
| 命中率（扫描抗污染） | LRU-K 0.5197 / ARC 0.5104 / W-TinyLFU 0.5061 vs LRU 0.3674 | **高 13.9–15.2 个百分点** |
| 命中率（CDN 大对象） | GDSF 0.7483 vs LRU 0.4771 | **高 27.1 个百分点** |
| 单线程吞吐 | 28.39–33.95 Mops/s（LRU/CLOCK），12.07–25.68（其他） | 见 §3 与 Caffeine 折算对比 |
| 相对自身优化前 | **逐策略 1.04–2.80×，几何 1.91×**（另有复算 2.03×，见 §2.2） | 全部提升 |
| 堆分配 | **每次操作 → 0 次堆分配**（命中率逐位一致） | 汇编级成果 |
| vs Caffeine 吞吐 | Caffeine 官方 Read(100%) 8t 181.7 M / 16t 382.4 M ops/s | **口径不同，只能算同量级**（见 §3.2） |
| vs Ristretto / groupcache | 官方仓库无公开命中率/吞吐数字 | **未测/待补** |

**一句话**：命中率层面我们有完整证据（7 策略 × 5 场景，比 LRU 高 21–27 个百分点，与 Caffeine 论文结论方向一致）；
吞吐层面自身优化 1.91× 有汇总记录但**逐场景原始报告未入库**；
与 Caffeine 的跨语言对比只能到「同量级」，与 Ristretto/groupcache 无同口径数据。

## 2. 我们自己的优化数据（1.91× / 2.57× / 2.80×）

### 2.1 已落盘的汇总记录

`docs/reports/2026-11-01-plan.md` §二（2026-10-31 完成总账）原文：

> | **缓存** | **几何 1.91×**（LRU 2.57×/2Q 2.80×），堆分配→0，命中率逐位一致 |

`collab/go2cpp-offerings.md` §三 给出 7 策略逐项加速比：

| 策略 | 加速比 | 相对于 |
|---|---:|---|
| LRU | **2.57×** | 优化前实现 |
| LRU-K(2) | 1.97× | 同上 |
| 2Q | **2.80×** | 同上 |
| W-TinyLFU | 1.76× | 同上 |
| GDSF | 1.04× | 同上 |
| ARC | 2.58× | 同上 |
| CLOCK | 2.12× | 同上 |

### 2.2 几何均值复核（诚实标注差异）

按上表 7 个数复算几何均值：`(2.57 × 1.97 × 2.80 × 1.76 × 1.04 × 2.58 × 2.12)^(1/7) ≈ **2.03×**`，
与汇总记录的 **1.91×** 相差约 6%。

| 可能原因 | 说明 |
|---|---|
| 场景集合不同 | 1.91× 可能只取 5 场景中的 4 个（GDSF 1.04× 的拖累被不同权重处理） |
| 权重不同 | 几何均值 vs 按请求量加权 |
| 快照不同 | offerings 是后续汇总，可能含额外优化 |

**处理方式**：两个数都保留，**以 1.91× 作为对外口径**（有明确出处的汇总记录），
并在 §9 把「逐策略加速比的原始基准报告」列为待补——不把复算值伪装成实测值。

### 2.3 优化做了什么

| 项 | 优化前 | 优化后 | 影响 |
|---|---|---|---|
| 每操作堆分配 | 有（节点/迭代器/临时对象） | **0 次** | 消除 allocator 抖动，命中率逐位一致（可对拍） |
| LRU 吞吐 | 基准 | **2.57×** | 链表 + 索引的指针化 |
| 2Q 吞吐 | 基准 | **2.80×**（提升最大） | 三个 list + 三个 map 的读写路径收敛 |
| GDSF 吞吐 | 基准 | 1.04×（几乎不变） | O(log n) 堆 + 惰性删除的结构性成本，未做算法级替换 |
| 正确性 | — | **命中率逐位一致** | 优化不改语义，可逐请求对拍 |

### 3.5 与 Caffeine 的命中率结论是否一致

Caffeine 官方 Efficiency 页（`https://github.com/ben-manes/caffeine/wiki/Efficiency`）的公开结论：

> 「LRU 因简单与常见场景表现好而流行，但**在典型负载下并非最优，遇到全扫描时命中率可能很差**。
> Caffeine 采用 **Window TinyLfu**，因为它命中率高、内存占用低……W-TinyLFU 与 **ARC / LIRS 竞争**。」

我们的实测**方向一致**：扫描场景 LRU 0.3674 → W-TinyLFU 0.5061 / ARC 0.5104 / LRU-K 0.5197；
且 ARC 与 W-TinyLFU 在热点、扫描两个场景都处在同一档（0.78 vs 0.78、0.51 vs 0.51）。

**不一致的点（如实记录）**：Caffeine 论文/文档宣称 W-TinyLFU 通常优于 ARC/LIRS；
我们的 **mixed 场景 W-TinyLFU 只有 0.4997，低于 ARC 0.6399 与 LRU-K 0.6538**。
原因是我们的 mixed 突发是「新 key 连续 8 次后换新」，频率低 + 窗口只有 1%，
准入会拒绝这些 key（`cache-algorithms.md` §8.5 第 3 条）。**这是场景构造的差异，不是结论矛盾**。

### 4.2 Caffeine 官方基准（公开数据，Java / Xeon E5-2698B v3 16 核）

### 4.3 能不能比？——只能算同量级

| 换算 | 结果 | 结论 |
|---|---|---|
| Caffeine 8 线程 181.7 Mops/s ÷ 8 | ≈22.7 Mops/s/线程 | 我们 LRU 28.39、CLOCK 30.20 **数量级相同** |
| Caffeine 16 线程 382.4 Mops/s ÷ 16 | ≈23.9 Mops/s/线程 | 同上 |

**必须标注的不可比因素**：
1. Caffeine 是 **Java + JIT**、对象头 + GC 压力；我们是 C++ / `-O2` / 零分配；
2. Caffeine 基准机器是 16 核 Xeon E5-2698B v3 @2.0GHz；我们是 12 线程 Ryzen 9 8945HX（WSL2）；
3. Caffeine 的 Read(100%) 是无淘汰压力下的纯读；我们的 Mops 含 Put 与淘汰；
4. 我们是单线程，Caffeine 是 8/16 线程（**并发扩展性我们未测**）。

> 因此本表**不用于达标判定**，只用于「我们在同一数量级」这一结论。

## 5. 内存对比

| 策略 | 热点 KiB | 加权 KiB | CDN KiB | 约 B/条目 | 说明 |
|---|---:|---:|---:|---:|---|
| LRU | 143 | 143 | 143 | ≈73 | `list` + `map` |
| CLOCK | 174 | 174 | 174 | ≈89 | 槽位数组 + map |
| W-TinyLFU | 220 | 220 | 220 | ≈113 | 3 list + 3 map + 素描 + Bloom |
| 2Q | 226 | 226 | 226 | ≈116 | 3 list + 3 map + pending |
| ARC | 280 | 280 | 287 | ≈143 | 2 常驻 + 2 ghost + 4 map |
| LRU-K(2) | 380 | 380 | 380 | ≈195 | 主表 + corral（**2×**） |
| GDSF | 415 | **12,294** | 1,591 | ≈212 | 堆 + 惰性删除；weighted 场景条目数 44,618（LRU 的 22 倍） |

**结论**：LRU/CLOCK 最省内存（73–89 B/条目）；GDSF 在「按字节预算」场景会放大条目数与元数据
（**已知限制**，文档已给「条目上限」建议）；LRU-K 的 2× 是 corral 的设计代价。

**覆盖率判定（规范 §三要求 ≥80%）**：
- 淘汰策略维度：**7/7 = 100%**（工业库常见的 LRU/TinyLFU/ARC/LRU-K/2Q/GDSF/CLOCK 全覆盖）；
- 缓存容器能力维度（TTL/刷新/分布式）：**缺口 3 项**，按规范写明理由——
  TTL/刷新属业务语义（我们在文档 §8 限制里明确「不塞进缓存容器」），分布式属 groupcache 的定位差异，
  不在本模块范围。

## 7. 差距分析

| 项 | 事实 | 根因 |
|---|---|---|
| GDSF 只提升 1.04× | 堆 + 惰性删除，O(log n) 在命中路径上 push | 算法结构性成本；未做时间轮/侵入式树替换（plan §四 D2 已列「LRU-K 的 `std::map` → 时间轮/侵入式树，还能 +30%」） |
| LRU-K 吞吐最低（6.68 Mops） | `std::map` + corral，O(log n) | 同上；命中率最高（0.7904）是它的价值所在 |
| W-TinyLFU 混合场景 0.4997 | 窗口只有 1%，低频突发被准入拒绝 | 与 Caffeine 一致的取舍；我们的突发模型更苛刻 |
| 无并发扩展性数据 | 单线程基准 | 分片/锁竞争未测，是最大证据缺口 |
| 与 Caffeine 吞吐只能算同量级 | 语言/机器/线程数/淘汰压力四项都不同 | 需要同机同负载的对照（Java 侧也是跨语言，无法真正同机） |
| 1.91× 与复算 2.03× 差 6% | 汇总口径未记录细节 | 逐策略原始报告未入库（§9 待补） |
