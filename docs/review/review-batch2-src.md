## 3. 重点问题详述（P1）

### FETCH-01 HTTPS 的 URL（含 token）进入 curl argv
`PerformHttpsAttempt` 把 `BuildUrlText(url)` 作为最后一个 argv 元素（fetch.cpp:1284）。`os::proc::Run` 是 argv 直传、不经过 shell（backup.hpp:16-20 已说明），因此 URL 会原样出现在 `/proc/<pid>/cmdline` 与 `ps` 输出里。URL 的 query 常携带短期 token/签名（例如 `?token=...`、预签名 S3 URL），等于把凭据暴露给同机任意用户。
探针（假 curl 记录 argv）：日志中出现 `https://example.invalid/pkg.bin?token=SUPER_SECRET_TOKEN_123`。同仓 backup 的 Upload 用 `curl --config -` + `Run(process, config)` 从 stdin 传 `url`/`header`/token（backup.cpp:259-295、352-358），证明零依赖方案可行。**建议 fetch 与 backup 共用该 helper，并把「URL/token 不进 argv」写成回归断言。**

### FETCH-02 204/205 无 body 被当成 EOF 读取
`HttpGetToFile` 只在 `chunked`/`Content-Length` 时确定 body 长度，否则 `ReadUntilEof`（fetch.cpp:1201-1207）。RFC 7230 §3.3.2 规定 204/205 响应头结束后即结束。服务器在 204 后保持连接（合法，尤其忽略了 `Connection: close`）时，客户端只能等 `read_timeout_ms`（默认 15s）→ `kTimeout`（可重试，最多 4 次）→ 最终失败。
探针（本地 server 回 204 + 保持 800ms，`read_timeout=200ms`）：`[204] status=timeout http=204 elapsed=199ms msg=读取超时`。**建议在 body 分派前加 `status == 204 || status == 205` 的零长度分支，并补 204 keep-alive 单测。**

### SESS-01 部分写后重发整帧会破坏字节流
`Session::Flush` 用 `transport->WriteFull(帧)`；`ITransport::Write` 明确允许部分写（transport.hpp:180-188），`WriteFull` 在部分写后失败时返回 `bytes=累计写入量`（transport.hpp:222-231），`TcpTransport::Write` 在 `send` 部分成功后 poll 超时返回 `kTimeout + written`（tcp_transport.cpp:434-438）。`Flush` 对 `kTimeout` 一律 `push_front` 整帧重发（session.cpp:938-941），于是对端字节流出现「半帧 + 完整帧」：`FrameDecoder` 按 20B 头解析出的长度/CRC 必然错位，会话进入 `kProtocolError`。触发条件是「发送缓冲满 + 单次 `io_timeout_ms`（默认 50ms）内未写完整帧」，慢链路/大帧（最大 1MiB）下现实存在。
**建议：outbox 元素携带已写偏移，超时后只重发剩余字节；或把 `bytes > 0` 的写失败视为流不可恢复，直接 `Fail(kWriteFailed)`。** 现有 `TestWriteFailed` 只注入 `kError`，没有覆盖该路径。

| 正确性 | HTTP 主体正确（状态行/头/CL/chunked/重定向/截断/大小上限实现清晰），但 204/205 语义错误（FETCH-02）、未知 TE 会产出损坏文件（FETCH-04）、HTTPS 空文件误判成功（FETCH-03）。ZIP 结构解析边界检查扎实（EOCD/中央目录/本地头/CRC 全覆盖），但解压写入有 TOCTOU（ZIP-01）。Session 状态机主路径正确（测试 180 checks 覆盖配对/心跳/控制/关闭），部分写重发是确定缺陷（SESS-01）。UDP/X25519 正确性高（RFC 全向量 PASS）。 |
| 并发 | Session 明确单线程、无锁（与 `Link::RunOnce` 一致），但回调重入只有文档约束、无运行时防护（SESS-03）；`Flush` 部分写破坏字节流（SESS-01）；UDP 的「Close 与读并发需外部协调」已文档化（可接受）。 |
| 资源 | 无 fd 泄漏：fetch/file_browser/zip/udp 的失败路径均 close；fetch 临时文件 O_EXCL+O_NOFOLLOW、失败 unlink；zip 解压失败删除损坏文件。缺 fsync（rename 持久性），临时文件权限 0644（FETCH-10），x25519 栈上密钥未擦（X25519-01）。 |
| 错误处理 | 错误码分模块清晰（FetchStatus/ZipStatus/FileBrowserStatus/BackupStatus/UploadStatus/SessionError/UDP Result），探测类失败不抛异常；但 curl 退出码细分不一致（BAK-04 vs fetch），`getaddrinfo` 全部压成 EHOSTUNREACH（UDP-03），UDP 空操作顺序与文档冲突（UDP-01），upload 对 4xx 重试（BAK-02）。 |
| 安全 | 路径沙箱整体可靠（fetch 单段文件名 + canonical + `O_NOFOLLOW`；file_browser 逐段拒绝链接 + `O_NOFOLLOW`；zip 名字校验 + `weakly_canonical`、拒绝绝对/`..`/反斜杠/冒号/控制字符）。**但** HTTPS URL 进 argv（FETCH-01，P1）、zip 解压/写入的 TOCTOU 与 `ofstream(trunc)` 跟随链接（ZIP-01/ZIP-02）、Backup `.part` 固定名（BAK-01）需要修；file_browser 的 `local_path` 不受沙箱约束需在文档中显式声明（FBR-01）。X25519 低阶点（全零）拒绝、clamp、常数时间交换实现正确。 |
| 风格 | 头文件注释质量高（状态机图、帧格式表、取舍说明、线程模型俱全）；命名/RAII/`file:line` 可读性好。扣分项：5 份重复的小工具（DOC-02）、同层安全基线漂移（DOC-01）、capability 把「配置关闭」记为 degraded（CAP-04）、Backup 中英文错误串混用（BAK-05）。 |

## 6. 亮点

- **fetch 的路径沙箱与落盘**：单段文件名 + `weakly_canonical` + `lexically_relative` 双重校验，临时文件 `O_CREAT|O_EXCL|O_NOFOLLOW`，成功才 `rename`，失败全路径 unlink（`fetch.cpp:1094-1104,1480-1519,1622-1668`）；下载全程流式写盘 + 增量 SHA-256，不在内存攒整包。
- **zip 的解析防御**：EOCD 定位、中央目录长度/偏移/条目数四重边界检查，`compressed_size != uncompressed_size`、method/加密/描述符、条目名重复都显式拒绝；解压按 CRC 校验、失败删除损坏文件（`zip.cpp:839-1009,1187-1193`）。
- **file_browser 的「拒绝而非修复」**：`..` 在任何位置都拒绝（不做规范化放行）、逐段 `symlink_status` 拒绝链接、`O_NOFOLLOW` + 同目录临时文件 + `rename`，并在复制前后核对大小（`file_browser.cpp:110-146,197-227,332-355`）。
- **session 的确定性与可测性**：时间源/传输工厂/回调全部可注入，`Poll` 单入口驱动读→帧处理→定时器→发送，测试用假时钟复现配对超时/心跳/关闭窗口（`session.cpp:252-254,427-446`；测试 180 checks）。
- **x25519 的密码学正确性**：16×16-bit limb + TweetNaCl carry 技巧、常数时间 `Select`、固定求逆链；RFC 7748 官方向量与 1000 轮迭代全部通过（1160 checks），低阶点返回全零并清零输出。
- **capability 的只读探测设计**：`epoll_create1` 立即关闭、不写文件、不发起网络；每项带可操作 `reason` 与 `detail`，`ProbeOptions` 可注入假路径（`capability.cpp:296-309,489-515`）。
- **backup 的 token 处理**：`curl --config -` 经 stdin 传 url/header/token（`backup.cpp:248-297,351-358`），是 fetch 应复用的正确范式。

## 7. 未覆盖与限制

- **未做**：Session 部分写的动态复现（需真实 TCP 发送缓冲打满 + 逐字节时序，构造成本高；结论基于 `ITransport::WriteFull` 契约 + `TcpTransport::Write` 返回值 + `Flush` 代码路径）；zip 解压 TOCTOU 的并发攻击复现（需与解压线程竞态）；Backup `.part` 符号链接攻击的动态复现（结论来自 `ofstream` 语义与代码路径）。
- **未审查**：`os::proc` 的内部实现（只核对 `Run(process, config)` 的 argv/stdin 用法与退出码语义）；`PairingSession`/`Heartbeat`/`SessionControl` 的内部状态机（仅在与 Session 交互处引用其契约，上一批 `review-p1-modules-src.md` 已单独审过 SessionControl/PeerHub）。
- 探针在 WSL 回环/本地文件系统运行，未覆盖跨设备 rename、NFS、只读根文件系统等部署差异；capability 的实机结果（12 available / 3 degraded）取决于当前 WSL 环境，不代表所有发行版。
- 测试全绿只代表已覆盖路径；本表 P1/P2 中的 FETCH-01/02、ZIP-01/02、SESS-01/02、BAK-01/02 均无对应回归用例。
