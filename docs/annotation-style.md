# Go2Cpp 注释规范（2026-10-19）

> 本文件是本轮全项目注释工作的**唯一格式依据**。所有 agent（主 agent 与子 agent）
> 都按本文件写注释；与已有注释冲突时，以「已有文件里已经写得很好的那部分」为准
> （例如 `include/go2cpp/concurrency/scheduler/scheduler.hpp` 的文件头与类注释）。

## 0. 铁律

1. **只加注释，不改代码**。不改逻辑、不改签名、不改格式、不删原有注释。
2. 每改完一批文件必须能编译通过（`cmake --build build-quality --target <库>`）。
3. 注释用**简体中文**；代码/API 名保持原文。
4. 不写「显而易见」的复述（`// 返回 count`）；写**为什么**、**谁在用**、**不这样会怎样**。

## 1. 文件头（.hpp / .cpp 开头，`/** ... */`）

参考 `scheduler.hpp` 的写法，固定四段：

```cpp
/**
 * @file <相对路径>
 * @brief 一句话说明本文件是什么。
 *
 * ## 模块定位
 * 这个文件在整条调用链的哪一层、上下游是谁、被谁使用。
 *
 * ## 本文件定义什么
 * - `Xxx`：一句话 + 它在协议/状态机里的角色；
 * - `Yyy`：……
 *
 * ## 阅读建议
 * 先看什么、再看什么（帮助后来者建立心智模型）。
 *
 * ## 边界与陷阱
 * 反直觉行为、不能怎样、以及为什么（如果本文件有）。
 */
```

## 2. 类注释（`class` / `struct` 之前）

```cpp
/**
 * @brief 这个类是什么（一句话）。
 *
 * ## 定位
 * 属于哪一层、解决什么问题、**向哪些上层服务提供能力**（点名具体模块/类，
 * 例如「被 `Scheduler::worker_loop` 用来……」「供 `http::Connection` 调用」）。
 *
 * ## 生命周期与线程模型
 * 谁创建/销毁、在哪个线程上被调用、是否线程安全（如适用）。
 *
 * ## 状态机
 * 如果本类是有状态的状态机（≥3 个状态、或状态间有明确事件驱动），**必须**：
 *   1. 在本注释里写明「状态转化表见 `docs/state-machines/<Name>.md`」；
 *   2. 在该 md 里给出转化表（格式见 §5），并注明源文件相对路径与关键函数；
 *   3. 简单状态机（≤2 个状态）直接在注释里用一行 `A -(fn)-> B` 表达即可，不必建 md。
 *
 * ## 不变量
 * 该类的恒真条件（例如「running G 一定持有 execution_claim 且不在队列里」）。
 */
```

## 3. 成员变量注释

每个**非平凡**成员变量（含 `m_*` 与私有 struct 的字段）都要有行尾或上一行注释，
至少说明三件事中的两件：

```cpp
std::mutex m_mutex;          ///< 保护 m_fd/m_connected；被 begin_operation/end_operation 使用
std::atomic<bool> m_closing; ///< 关闭中标记；由 release() 置位，由 is_closing() 读取
std::deque<NodePtr> m_readers; ///< 读等待队列（FIFO）；register_wait 入队、process_event 出队
```

格式：**定位（是什么）+ 使用者（哪些函数读写）+ 必要的并发语义**。
纯常量/纯计数器也要一句话说明它在什么条件下变化。

## 4. 复杂成员函数注释

「复杂」指：> 30 行、或包含锁/park/循环/多分支、或调用链跨越两个以上模块。

```cpp
/**
 * @brief 一句话说明这个函数完成什么。
 *
 * ## 步骤
 * step1. 取锁并校验代际（为什么要校验）；
 * step2. 把等待节点挂到 条带队列，登记 deadline；
 * step3. 调 update_interest_locked 做 EPOLL_CTL_ADD/MOD；
 * step4. 释放锁后 tickle，唤醒可能在 epoll_wait 的 worker。
 *
 * ## 并发/失败语义
 * 哪些情况下返回空、哪些情况下节点已被唤醒（调用方还要不要再 park）。
 */
```

**函数体内**：在关键步骤前用 `// step2: ...` 标注，与上面的步骤一一对应。
不要把每一行都标一遍，只标**步骤边界**与**反直觉的地方**。

## 5. 状态机 md（`docs/state-machines/<Name>.md`）

```markdown
# <类名> 状态机

- 源文件：`src/xxx/yyy.cpp`（类定义在 `include/go2cpp/...`）
- 关键函数：`Foo()`、`Bar()`

| 当前状态 | 触发（函数） | 下一状态 | 说明 |
|---|---|---|---|
| Idle | `start()` | Running | 启动 worker 与 poller |
| Running | `stop()` | Draining | 停止接新任务 |
| Draining | 最后一个 G 终态 | Stopped | 唤醒所有等待者 |

## 不变量
- ……

## 非法转化
- Draining -> Running：被 `assert` 拒绝 / 直接忽略（说明实际行为）
```

**要求**：一行一个转化；「触发」列写**函数名**（不是事件名），这样代码可以直接对照。

## 6. 优先级（时间有限时按此顺序）

1. **类注释 + 成员变量**（理解成本最高）；
2. **状态机 md**（排查并发问题的第一手材料）；
3. **复杂函数的 step 概述**（其次）；
4. 函数体内的逐步标注（最后）。

## 7. 完成后自检

```bash
flock /tmp/go2cpp_build.lock cmake --build build-quality --target <你的库> -j 8
```

- 编译零错误（警告不新增即可）；
- `git diff --stat` 里只有 `+`（注释），不应出现代码行的 `-`/`+` 配对；
- 抽查 2~3 个类：是否回答了「定位 / 上层调用方 / 成员被谁用」。
