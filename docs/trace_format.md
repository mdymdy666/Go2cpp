# Go2Cpp Trace 格式设计（C-L1 详细设计）

> 产出轮次：方向分析第 12 轮
> 地位：`docs/direction_plan.md` 阶段 1（C-L1）的实现细节
> 触发原因：第 11 轮把阶段 1 与阶段 2 由串行改为并行后，trace 不再只需记录调度，
> 还要承载业务状态转换。格式若一开始没定好，阶段 2 会被迫返工。

---

## 一、核心区分：输入事件 vs 输出事件

**这是整个设计里最重要的一个决定。**

一次执行里所有非确定性，都来自"运行时向外界询问"的时刻。把这些时刻的答案录下来，
下次原样喂回去，执行就会重演。因此 trace 里的每条记录必须明确归属：

| 类别 | 定义 | 重放时的处理 |
|---|---|---|
| **INPUT** | **运行时的提问，外部给的答案** | **把录下的答案喂回去**（并校验提问与记录一致） |
| **OUTPUT** | **运行时产生的可观察行为** | **与录下的行为逐条比对，不一致即报分歧点** |

**只有做了这个区分，"逐字节比较"才是有意义的** —— 否则拿输出比输出，
等于自证，发现不了任何问题。

## 二、记录格式

**选择文本行格式，而不是二进制**，理由就是目标本身：要**人可读、可 grep、可 diff**。

```
# go2cpp-trace v1
# seed=0x5f3a91  platform=linux-x86_64  fiber_backend=native  procs=1
# BEGIN

#1  INPUT  SEL   gid=-       cand=[3,7,9]      pick=7
#2  OUTPUT SPAWN gid=7       task=0x7f3a
#3  OUTPUT PARK  gid=3       reason=chan_wait  chan=0x55c1
#4  INPUT  TICK  now=+10ms
#5  OUTPUT WAKE  gid=3       by=gid=7
#6  OUTPUT ENQ   gid=3       queue=p0          pos=tail
#7  INPUT  IO    ready=[{fd=9,ev=read}]
#8  OUTPUT FIRE  timer=42    gid=11
#9  INPUT  SEL   gid=-       cand=[3,7]        pick=3
#10 OUTPUT NOTE  gid=7       tag=fsm.transition from=Created to=Paid cause=-
#11 OUTPUT EXIT  gid=7       state=kDead

# END
```

**逐字段说明**：

| 字段 | 含义 |
|---|---|
| `#N` | **单调递增序号**，重放的主键。**不用时间戳做序** —— 虚拟时钟下多条记录可能同刻 |
| `INPUT`/`OUTPUT` | 见上一节 |
| 事件名 | 见第三节 |
| 键值对 | **每条记录必须自包含**，重放时不依赖外部状态 |

## 三、事件类型

### INPUT（非确定性来源，共 4 类）

| 事件 | 何时产生 | 记录内容 |
|---|---|---|
| **`SEL`** | 调度器要从就绪集里挑一个 G | **候选列表 + 选中项**（★ 候选也要记，否则无法验证重放时做了同样选择） |
| **`TICK`** | 虚拟时钟被推进 | 新的 `now` |
| **`IO`** | `epoll` 返回就绪事件（模拟模式由脚本给出） | `fd` + 事件类型的列表 |
| **`RND`** | 任何需要随机数的地方（`select` 的公平随机） | 抽到的值 |

### OUTPUT（运行时行为，共 6 类）

| 事件 | 含义 |
|---|---|
| **`SPAWN`** | 新建 G |
| **`PARK`** | G 挂起（含原因） |
| **`WAKE`** | G 被标记可唤醒 |
| **`ENQ`** | **G 真正进入就绪队列** —— ★ **第 9 轮实测发现：`WAKE` 只标记，`ENQ` 才有顺序**，因此这两件事必须分开记 |
| **`FIRE`** | 定时器触发 |
| **`NOTE`** | **业务层注记（见第五节）** |
| **`EXIT`** | G 终止（含终态：`kDead` / `kCancelled` / `kFailed`） |

## 四、重放协议

```
replay(trace):
    rt = 构造运行时（沿用 trace 头里的 seed / procs / backend）
    for rec in trace:
        if rec 是 INPUT:
            actual = rt.下一步向外界询问的内容()
            if actual != rec.提问:  报「提问不一致」，定位到 #N
            rt.喂入(rec.答案)
        else:
            produced = rt.产生下一条输出()
            if produced != rec:     报「行为分歧」，定位到 #N
    if rt 还有未消费的输出:         报「trace 截断」
```

**关键点**：**分歧报告必须给出那条记录的序号**。否则"重放失败"对调试毫无价值 ——
而"在第 N 条分歧"直接指向现场。

## 五、与 FSM 层的解耦（本节是格式设计的核心约束）

**trace 格式不硬编码任何业务概念。** FSM 的状态转换走通用的 `NOTE`：

```
#10 OUTPUT NOTE gid=7  tag=fsm.transition  from=Created  to=Paid  cause=-
```

**为什么这样设计**：

- 调度层（`Scheduler` / `Fiber` / `Channel` / `Context`）**不需要知道状态机的存在**；
- FSM 层**只需要调用一个 `TraceNote(tag, kvs...)`**，不需要改调度层的任何代码；
- 阶段 3 的作品、以及未来任何业务（协议握手、会话管理）**都能复用同一个通道**。

**这条约束直接决定了第 9 轮那份埋点清单可以保持"4 类、约 47 行"** ——
如果 trace 要为 FSM 定制事件类型，埋点就会蔓延到业务层，成本立刻失控。

## 六、版本与兼容

```
# go2cpp-trace v1
# seed=0x5f3a91  platform=linux-x86_64  fiber_backend=native  procs=1
```

- **`v1`**：格式版本。字段增删必须升版本，**不允许静默改变语义**；
- **`seed` / `platform` / `fiber_backend` / `procs`**：重放环境的必要条件 ——
  **换后端（native ↔ Boost.Context）或换 P 数量，调度序列本就该不同**，
  因此这些不是"元数据"，而是**重放能否成立的前提**。

## 七、验收标准（可执行）

1. **同一 seed 跑两次，OUTPUT 序列逐字节相同** —— 证明确定性。
2. **用录下的 trace 重放，全部 `INPUT` 提问与记录一致、全部 `OUTPUT` 逐条相同** —— 证明可重放。
3. **人为篡改一条 `INPUT` 的答案，重放必须报出「行为分歧」并定位到正确序号** ——
   证明它真的在验证，而不是自证。
4. **篡改一条 `OUTPUT`，比对必须失败** —— 同上，反向验证。
5. **一个 FSM demo 的状态转换以 `NOTE` 形式出现在 trace 里，且重放后序列一致** ——
   证明业务层与调度层确实解耦。

## 八、尚未决定的问题（如实留白）

| 问题 | 现状 |
|---|---|
| **trace 的体量控制** | 一个高并发服务每秒可能产生大量调度事件。是否需要对 `SEL`/`ENQ` 做采样或环形缓冲，**尚未设计** |
| **生产环境是否常开** | 第 10 轮实测"关闭时开销 +1.06%"，说明**常开是可行的**；但**写入 trace 本身的 I/O 成本未测** |
| **跨版本重放的兼容策略** | 目前只写了"必须升版本"，**没有设计迁移工具** |
| **`RND` 的粒度** | 是记录每次抽样，还是只记种子由运行时重演随机序列 —— **两种方案各有取舍，未定** |
