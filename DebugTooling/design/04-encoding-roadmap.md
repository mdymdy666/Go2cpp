# design · 04 编码走向（目标第 2 步）

> 根据前面 5 轮的源码结论，给出**编码走向**：分层、模块划分、插件协议、
> 多插件与多机形态、阶段划分与依赖，以及**必须留活的设计点**。
> 本文件是**设计**，不含实现；每个结论都标出所依据的源码事实。

## 0. 三条不可违反的既有约束（来自项目自身注释）

| # | 约束 | 出处 |
|---:|---|---|
| 1 | 观察者「**不能通过事件回调控制当前 G 的执行权**」 | `scheduler.hpp:140-183` |
| 2 | 「**不会从另一个线程强行切断任意 C++ 调用栈**」 | `scheduler.hpp:399-400,409-412`、`enable_sysmon` 注释 |
| 3 | `Fiber::resume` 必须**串行**；同一时刻只有一个 M 进入同一个 Fiber | `fiber.hpp:90-93`、`scheduler.hpp:330-333` |

**由此推出的第一条设计原则**：**观测面与控制面必须分成两套接口**，
且控制面**默认关闭**。

## 1. 分层设计（每层职责单一，层间可替换）

```
┌─────────────────────────────────────────────────────────────┐
│ L5 工具形态   CLI(dump) │ HTTP 端点 │ 库 API │ gdb 脚本        │
├─────────────────────────────────────────────────────────────┤
│ L4 传输插件   stdio │ 文件 │ 环形缓冲 │ 网络 topic(Stratum 式) │
├─────────────────────────────────────────────────────────────┤
│ L3 序列化     text │ ini │ json │ (未来) protobuf             │
├─────────────────────────────────────────────────────────────┤
│ L2 快照层     枚举/过滤/一致性标注（只读）                     │
├─────────────────────────────────────────────────────────────┤
│ L1 采集层     SchedulerObserver(已有) │ 快照接口(新增)          │
├─────────────────────────────────────────────────────────────┤
│ L0 探针(可选) 安全点断点 │ 锁事件钩子 │ 元数据注册              │
└─────────────────────────────────────────────────────────────┘
```

**关键点**：L1 的观察者**已经存在且不持有调度器**（`scheduler.hpp:140-183`），
L2/L3/L4/L5 完全可以放在**独立库**里，对调度器**零改动**即可产出 dump 与事件流。

## 3. 插件协议（如何做到"不了解多场景绝不写死"）

现有唯一的插件边界是 `SchedulerObserver::OnEvent`（推送）。设计上**新增两个更窄的接口**，
而不是扩大 `Observer` 的职责：

```cpp
// 设计：输出后端（sink）—— 只管"把一条已渲染或结构化记录送出去"
class DebugSink {
public:
    virtual ~DebugSink() = default;
    virtual void Write(const DebugRecord& record) noexcept = 0;   // 必须非阻塞
    virtual void Flush() noexcept {}
};

// 设计：记录来源（source）—— 事件流 / 周期快照 / 手动触发 三类
class DebugSource {
public:
    virtual ~DebugSource() = default;
    virtual void Poll(std::chrono::steady_clock::duration budget) = 0;
};
```

**为什么这样切**：
- `SchedulerObserver` 的回调**在 worker 线程上同步执行**（`scheduler.cpp:1104-1122`），
  所以 sink 的 `Write` 必须**非阻塞**（典型实现：写入无锁环形缓冲后立即返回）；
- 真正的重活（格式化、写文件、发网络）由**独立线程**的消费者完成；
- 这样 stdio / 文件 / topic **共享同一条记录管道**，新增后端不动上游。

## 4. 需要向核心增加的"只读"接口（低风险，先做）

依据第 5 轮的源码结论（`task_registries` 强持有全部非终态 G）：

| 接口（设计） | 用途 | 依据 |
|---|---|---|
| `std::vector<TaskSnapshot> Scheduler::snapshot_tasks() const` | 枚举全部 G | `scheduler.cpp:1529,1792-1805`；遍历范式 `1694-1705` |
| `std::vector<GId> Scheduler::processor_queue(PId) const` | 某 P 队列明细 | `Processor::queue`，`scheduler.cpp:1020` |
| `FiberContextSnapshot Task::context_snapshot() const` | 某 G 的调用链 | 转发 `fiber.hpp:210` |
| `FiberExecutionBinding Task::execution_binding() const` | 某 G 的 M/P 绑定 | 转发 `fiber.hpp:215` |
| `Scheduler::metrics()` 等（**已有**） | 指标 | `scheduler.hpp:599` |

**一致性约束（必须写进接口文档）**：分片之间不是原子的（16 个分片逐把加锁），
快照必须自带"分片级一致、全局非原子"的标注。

## 5. 需要向核心增加的"受控"接口（高风险，后做，默认关闭）

依据第 6 轮的三处实现确认：

### 5.1 替换函数（B2）—— 结论：**能做的比使用者预期少**

`Task::run()`（`scheduler.cpp:830-905`）的实际语义：

```cpp
auto created_fiber = Fiber::AcquireForScheduler(
    [this] {
        auto body = std::move(m_function);   // ★ 首次进入时把函数移出
        if (body) { body(); }
    }, ...);
```

- `m_function` 在 **Fiber 首次进入时**被移出（移出后为空）；
- `release_callable()`（`126-130`）就是"加锁取出并清空"，其 6 个调用点
  （`888/2020/2032/2059/2086/2145`）全部是**放弃执行**的清理路径。

**因此**：
- ✅ 只对 **`m_fiber == nullptr`（尚未首次 run）** 的 G 替换有意义；
- ❌ 对已运行的 G 替换 = 无效（函数已被移走）；
- ✅ 使用者真正想要的"中途换行为"，正确做法是 **`replace_pending`（延迟替换）**：
  登记新函数，等当前主体返回后由调度器**再入队执行一次** —— 这**不需要改 `Task`**，
  用现有 `Scheduler::spawn` 即可实现，属于 **L0 探针层**的封装。

### 5.2 跨 M 迁移（B3）—— 结论：**基础已存在，但语义要收窄**

`requeue_to_processor`（`2527-2574`）已经能把任务**追加进指定 P 的本地队列**
（带失败回滚 `runnable.fetch_sub(1)` + `clear_queued()`，且唤醒策略克制：
仅当 `running == 0` 或「队列 ≥16 且有空闲 M」才 `notify_one`）。

**但**它的前置是 `task->try_mark_queued()` 成功 —— **即任务当前未入队**。
→ 迁移语义收窄为：**只接受"当前未在任何队列中"的 G 的迁移请求**；
已在队列中的 G 若要迁移，需要"先从原 P 队列摘除"（需持原 P 锁），
这属于**新增**能力，且必须处理与 work stealing 的竞态。

**安全边界**：只对未在执行（`m_execution_claim == false`）且非终态的 G 生效。

### 5.3 插队（B4）—— 插入点已定位

`processor.queue.push_back(task)`（`scheduler.cpp:2547`）是**唯一的本地入队点**；
队列是 `std::deque`，支持中间插入。
→ 插队接口的形态：`enqueue_before(GId moving, GId target)`，
**必须持 `processor.mutex`**，且**默认关闭**（破坏 FIFO 公平性）。

## 6. 多插件与多机形态（对应目标第 2 步的明确要求）

### 6.1 基础信息面（stdio / 文件）

- **stdio**：`--format=text` 直接打印；管道场景下（`--output=-`）需保证**单条记录原子写出**；
- **文件**：`--output=<file>`，需要考虑**多进程同时写**（建议 per-pid 文件 + 时间戳命名）、
  **轮转**与**原子追加**；
- **环形缓冲（内存）**：供 `--events=N` 与"崩溃时转储"使用，容量有界、写入非阻塞。

### 6.2 Stratum 式 topic 传输（多机调试）

设计要点（**不是实现**）：

| 问题 | 设计取向 |
|---|---|
| 消息模型 | 每个**事件/快照**是一条独立 message，带 `schema` 版本与 `source`（host/pid/scheduler） |
| topic 命名 | `go2cpp.debug.<host>.<pid>.scheduler.<name>.<kind>`（kind ∈ events/snapshot/locks） |
| 与 Stratum 的关系 | 本模块**只依赖一个"发布一条 message 到 topic"的最小接口**，具体由 Stratum 插件适配；不绑定其内部实现 |
| 背压 | 发布端**必须可丢弃**（调试通道不能拖慢运行时）：有界队列 + 丢弃计数 + 周期上报 |
| 多机同步 | ⚠️ **时钟是前提问题**：`SchedulerEvent::timestamp` 是 `steady_clock`（`scheduler.hpp:130-137`），**跨机不可比**。多机联合时间线需要额外机制（见 §7） |
| 安全 | 调试通道默认**关闭**；开启需显式环境变量/配置，且应支持只读模式 |

### 6.3 向上提供工具（形态）

| 形态 | 适用 | 备注 |
|---|---|---|
| **库 API**（`go2cpp::debug`） | 嵌入式使用、自定义 sink | 最重要，其余形态都基于它 |
| **CLI**（`Go2Cpp dump scheduler ...`） | 运维排障、现场抓取 | 使用者明确要求的形态 |
| **HTTP 端点**（可选） | 远程查看、与现有面板集成 | 需评估是否引入 HTTP 依赖 |
| **gdb 脚本**（线程↔G 映射） | 与 gdb 混合调试 | 依赖符号导出（§8） |

## 7. 必须先解决的设计点（**不写死**原则的体现）

| # | 待定问题 | 为什么不能现在写死 |
|---:|---|---|
| 1 | 元数据（名字/描述/函数/行号）走**转译期注入**还是**运行期注册** | 取决于 Go2Cpp 转译器能否提供符号信息（**未确认**）；手写 C++ 场景又必须支持运行期注册 → 倾向**两者共存 + 可覆盖** |
| 2 | 多机时间**统一方案** | `steady_clock` 不可跨机；可选：记录 `(steady, wall)` 双时间戳、或引入 NTP/PTP 同步假设、或以"事件序号 + 单机时间"重建部分顺序 —— **需使用者定方向** |
| 3 | 断点**安全点**的分布与粒度 | 只能停在协作挂起点；安全点数量决定精度。数量未统计前无法承诺精度 |
| 4 | 调试通道的**开关与开销**保证 | 必须能量化"关闭时零开销"（观察者为空时 `emit_event` 只花一次加锁 + 一次 `shared_ptr` 拷贝，`scheduler.cpp:1104-1122`） |
| 5 | `SchedulerConfig` 是否加**运行期 setter** | 结构类字段注释明确禁止动态修改（`scheduler.hpp:163-165`）；只能做观测/节律类 |

## 8. gdb 混合调试（E4）的可行边界

- **gdb 能做的**：停在任意行、看 OS 线程栈、看内存；
- **gdb 看不到的**：G 的逻辑身份、G→M→P 绑定、Fiber 父链、锁等待关系；
- **本模块能做的**：把 `FiberExecutionBinding`（`fiber.hpp:36-48`）与
  `FiberContextFrame::last_thread`（`fiber.hpp:65`）导出成**线程↔G 映射表**，
  供 gdb 脚本把"当前 OS 线程"翻译成"当前 G"；
- **必须诚实声明的限制**：Fiber 的**用户栈**由 `context.cpp` 自己的后端切换，
  gdb 看到的仍然是 M 的**原生栈** —— 想看 Fiber 栈内容需要本模块提供的快照接口，
  而不是 gdb 的 `bt`。这一点必须写进文档，避免误用。

## 9. 阶段划分与依赖（建议顺序）

| 阶段 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **P0** | 只读快照接口（§4）+ 元数据注册（§2） | 无 | 能枚举、能命名 |
| **P1** | 序列化（text/ini/json）+ stdio/文件 sink | P0 | **`dump scheduler` 可用**（≥15 选项中的大部分） |
| **P2** | 事件采集（Observer 插件）+ 环形缓冲 + `--follow` | P1 | 时间线可用 |
| **P3** | 锁观测（D1/D2）+ 锁争用策略钩子（D3） | P0、`sync.cpp` 深入 | 锁场景可用 |
| **P4** | 控制面（迁移/插队/延迟替换），**默认关闭** | P0 | B 类场景可用 |
| **P5** | 安全点断点（B5） | P4 | 插件式断点可用 |
| **P6** | 传输插件（Stratum topic）+ 多机同步 | P1、§7.2 定案 | 多机可用 |
| **P7** | gdb 混合（映射导出） | P0 | 混合调试可用 |

**关键路径结论**：**P0 → P1 是最小可用集**，且**完全不需要触碰调度器热路径**
（除了 §4 的只读接口）。P3/P4/P5 才需要更深的侵入与更严的前置校验。
