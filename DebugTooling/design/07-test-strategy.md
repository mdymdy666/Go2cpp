# design · 07 测试策略与验收标准（第 11 轮，深化②）

> 对齐 `PROJECT_RULES.md` 第 3 节（严禁以冒烟测试作为验收）：压测 / 随机测试 / ≥5 个真实场景。
> **本文件是测试设计，不含实现。** 强调一点：调试工具的验收有**两个维度**，
> 除了"功能正确"，还必须证明"**对被观测系统的干扰可忽略**"。

## 0. 两个验收维度

| 维度 | 问题 | 判据归属 |
|---|---|---|
| **A. 功能正确性** | 能不能取到**正确**的数据？ | §1–§3 |
| **B. 观察者效应** | 开了调试之后，被观测系统**变了多少**？ | §4（**调试工具特有，项目规范未直接覆盖，需自定义**） |

B 维度是不可省的：调试通道一旦阻塞 worker，就会改变被观测对象的时序，
使"观测结果"本身失真（`scenarios/E-remote-and-tooling.md` §E2 已把它列为设计红线）。

## 1. 压测方案（量化指标 + 条件）

### 1.1 测什么、怎么量

| 指标 | 测量方式 | 目标 |
|---|---|---|
| 单次快照耗时 | `steady_clock` 包住 `snapshot_tasks()`，报 P50/P95/P99 | 规模相关，见 1.2 |
| dump 吞吐 | 每秒可完成的完整 dump 次数 | 现场排障够用即可（≥10 次/秒） |
| 快照内存 | 返回的 vector 大小（元素数 × sizeof） | 与 G 数线性，不得超线性 |
| **对被测系统吞吐的影响** | 同负载下"未启用调试" vs "启用"的吞吐差（%） | 见 §4 |
| 事件发射开销 | `emit_event` 的 ns/op（分三档：无观察者 / 空观察者 / 真实 sink） | 见 §4 |

### 1.2 压测条件矩阵（必须写进报告）

| 维度 | 取值 |
|---|---|
| G 数量 | 1,000 / 10,000 / 50,000 |
| P 数量 | 1 / 4 / 16 |
| 负载类型 | 纯 CPU 密集 Fiber / 通道收发 / 定时器密集 / 混合 |
| 事件速率 | 低（仅启停）/ 高（任务起止密集） |
| 快照并发 | 单线程 dump / 多线程并发 dump |

**依据**：项目规范要求"说明压测条件（并发数、数据规模、持续时间、硬件环境）"。
宿主与构建条件必须按 `docs/performance.md` 的既有要求标注（**build-bench / Release**、
宿主型号、多轮区间而非单次最好值）。

### 1.3 现成可复用的基准设施

- `benchmarks/` 下已有 5 个基准与 `channel_vs_queue_benchmark.cpp`（本会话新增）；
- **性能结论只能用 `build-bench`（Release）** —— 项目硬性要求，已在
  `docs/performance.md` 与 `benchmarks/` 的 CMake 段落实（`GO2CPP_BUILD_BENCHMARKS` + `-O2`）。

## 2. 随机测试

| # | 随机化对象 | 目的 |
|---:|---|---|
| 1 | G 数量与状态分布 | 验证快照在任意规模/状态下不崩、不漏 |
| 2 | 过滤组合（`--state` 随机子集、`--min-depth` 随机阈值） | 验证过滤逻辑与计数一致 |
| 3 | **并发竞态**：多线程同时 dump + 系统高负载 | 验证分片遍历不丢节点、不死锁（**这是 R1 的最大风险点**） |
| 4 | 元数据注册/缺失随机混合 | 验证"未注册"与"无来源"的呈现不被混淆 |
| 5 | 名称/描述含特殊字符（引号、换行、非 UTF-8、超长） | 验证 ini/json **转义正确**（否则输出不可解析） |
| 6 | CLI 参数模糊输入（非法组合、缺参、超大值） | 验证不崩、报错清晰 |
| 7 | 锁等待者随机取消/超时 | 验证 D1/D2 快照与真实等待数一致 |

**要求**：随机测试必须**可复现**（固定种子 + 记录种子）；失败时能回放。

## 3. 真实场景（≥5 个，必须覆盖全部待验证功能）

> 说明：调试工具的"真实场景"就是**真实的调试行为**，而非业务功能；
> 因此下面每个场景都以"要回答的调试问题"为单位。

| # | 场景 | 覆盖的功能 | 期望结果 |
|---:|---|---|---|
| 1 | **现场排障**：长跑进程周期性 dump 到文件，事后分析"谁卡住了" | A 类全部 + C1/C4 序列化与重定向 | 能从文件看出阻塞的 M（`processor_detached`/`blocking_task`）与等待中的 G |
| 2 | **性能归因**：与 `build-bench` 联合，观察 P/M 分布、`steal_pops`、`fiber_resume_ns` | A5/A6/A8 | 指标差分能指出瓶颈在本地队列还是偷取 |
| 3 | **多插件并行**：同时启用 stdio + 文件 + 环形缓冲 + topic | P3/P4（DebugSink 多实例） | 四路互不干扰；任一路阻塞不影响其余（各自独立队列） |
| 4 | **跨进程/多机汇聚**：两个进程（或两台机器）通过 topic 汇聚时间线 | E2/E3 | 能排出**偏序**；若时钟方案为双时间戳，需在图上标注方案 |
| 5 | **gdb 混合**：gdb 附加进程 + dump 导出 thread↔G 映射 | E4 | 能把 gdb 里的 OS 线程翻译成 G；**并验证"gdb 看不到 Fiber 栈"这一声明属实** |
| 6 | **控制面演练**：默认关闭时零影响 → 开启后迁移/插队/断点生效 → 回滚 | B3/B4/B5 + C 组全部 | 见 §5 的破坏性测试判据 |

**每个场景必须记录**：模拟了什么真实用法、输入、期望结果、**实际结果**（不许只写"通过"）。

## 4. 零开销证明（本文件的核心）

### 4.1 为什么必须做

`SchedulerObserver` 的回调**在 worker 线程上同步执行**（`scheduler.cpp:1104-1122`）。
如果没有量化证明，就无法回答使用者最关心的问题：「**开了这个调试模块，我的程序会慢多少？**」

### 4.2 三档对照实验（必须都测）

| 档 | 配置 | 说明 |
|---|---|---|
| **档 0（基线）** | 完全不链接调试模块 / 不安装观察者 | 基线 |
| **档 1（空观察者）** | 安装一个 `OnEvent` 什么都不做的观察者 | 测出"事件机制本身的固定开销" |
| **档 2（真实 sink）** | 安装"写入有界环形缓冲"的 sink，独立线程消费 | 测出"真实使用"的开销 |

**每档都必须跑同一负载**（例如：SPSC 通道 5 万次收发、或 N 次 Fiber 切换），
用 `build-bench`（Release），**多轮取区间**（min/median/max），并按 `docs/performance.md`
的要求标注宿主与参数。

### 4.3 微基准：单独测 `emit_event`

依据 `scheduler.cpp:1104-1122`，无观察者时的路径是：

```
判空时间戳 → 加 observer_mutex → 拷贝 shared_ptr → 解锁 → if (!current) return
```

→ 可写一个微基准直接测这三档的 ns/op：
**不调用 `emit_event`** / **observer 为空** / **observer 非空但空函数** / **observer 非空且入队**。
**这个微基准不需要启动调度器**，成本极低，应该最早做（P0 阶段就能给出结论）。

### 4.4 最坏停顿（比平均开销更重要）

- 调试通道最怕的不是"平均慢一点"，而是"**偶发卡住 worker**"；
- 必须测量 **sink `Write` 调用的最大单次耗时**（P99.9 与 max），
  并**强制约束为有界操作**（只做入队，不做格式化/IO）；
- 同样要测**消费者线程被阻塞时**发布端的行为：应为"入队成功或按策略丢弃"，
  **绝不阻塞**，且丢弃计数可观测。

### 4.5 建议的验收阈值（**需实测校准，不要直接当承诺**）

| 档 | 建议阈值 |
|---|---|
| 档 0 → 档 1（空观察者） | 端到端吞吐差异 **< 2%** |
| 档 0 → 档 2（真实 sink） | 端到端吞吐差异 **< 5%** |
| sink `Write` 单次 | P99.9 **< 5 µs**，max **< 20 µs** |
| 背压场景 | 发布端**零阻塞**，丢弃计数准确 |

> **诚实声明**：上述数字是**建议起点**，必须用实测结果校准后才可写进文档；
> 在拿到数据之前**不得对外宣称"零开销"**。这也符合 `PROJECT_RULES.md` 第 0 节
> （不许声称未经验证的事）。

## 5. 验收标准与失败判据

### 5.1 功能验收

- 34 个场景逐条有"验证方式"（见 `scenarios/verification-matrix.md`）；
- 每个接口的**失败语义**按 `design/06-interface-signatures.md` 实现并测试。

### 5.2 破坏性测试（C 组控制面，必须做）

| # | 测试 | 判据 |
|---:|---|---|
| 1 | **默认关闭时的零影响** | 所有 C 接口不可用（返回错误/编译期不存在），且**系统行为与未编译该模块时一致**（用同一基准对比） |
| 2 | 迁移前置不满足 | 对**正在执行**的 G 调 `migrate` → 返回 false 且**不做任何改动**（幂等失败） |
| 3 | 迁移回滚 | 迁移后再迁回，队列归属与可运行性恢复 |
| 4 | 插队 | 目标不在同一 P 队列时**报错而非静默失败**；开启后顺序确实改变 |
| 5 | 断点 | 命中后 G **停在安全点**（不是任意行）；恢复后行为正确；**未开启时零影响** |
| 6 | 锁选择器饥饿保护 | 构造"某 G 反复被跳过"的场景，验证"超限强制 FIFO"生效 |
| 7 | 观察者抛异常 | 插件抛异常**不得**影响 worker 生命周期（依据：`scheduler.cpp:1104-1122` 的异常隔离） |

### 5.3 失败判据（任一即不通过）

- 快照在并发下**丢失非终态 G**（与 `runnable_count()` 交叉校验不符）；
- 关闭调试时**可测量**地改变系统吞吐（超出 §4.5 阈值）；
- C 组操作在前置不满足时**改变了任何状态**；
- 插件异常**穿出**调度器边界；
- dump 输出**无法被标准 ini/json 解析器解析**（转义错误）。
