# scenarios · E 远程、多机与工具链（6 个场景详细设计）

> E 类回答"能不能跨进程、跨机器、与 gdb 协同"，以及"最终以什么形态交付"。
> 共同前提：调试通道**必须可丢弃、默认关闭**，绝不能拖慢运行时。

## E1 · 基础通道（stdio / 文件 / 环形缓冲）

- **目的**：最朴素的可用形态——直接打印、写文件、内存留痕。
- **现状**：❌ 项目**没有任何调试输出统一出口**（项目规范明确要求「调试输出与日志要有统一入口，
  不散落裸 `printf`」，所以不能靠散落的 printf 实现）。
- **设计要点**：

| 通道 | 关键约束 |
|---|---|
| stdio | 管道场景下单条记录**必须原子写出**（否则多线程输出会交错）；`--color=auto` 时需检测 TTY |
| 文件 | 原子性（临时文件 + rename）、多进程不互相覆盖（文件名含 host/pid/时间戳）、可选轮转 |
| 环形缓冲（内存） | **写入非阻塞**（供 `SchedulerObserver` 回调直接调用）、容量有界、溢满时**计数丢弃**而非阻塞 |

- **与观察者回调的关系（决定性）**：`emit_event` 在 **worker 线程上同步执行回调**
  （`scheduler.cpp:1104-1122`），所以回调里**只能做"入队到环形缓冲"**，
  格式化与写文件必须由**独立消费线程**完成。
- **风险**：低。

## E2 · 插件式 topic 传输（Stratum 式）

- **目的**：把调试事件/快照发布到 topic，供其他进程/机器订阅。
- **现状**：❌ 完全没有。
- **设计取向（**只定义接口，不绑定具体实现**）**：

| 问题 | 设计 |
|---|---|
| 最小契约 | 本模块只依赖「**发布一条 message 到某个 topic**」和「**订阅**」两个动作；具体传输由外部（如 Stratum）适配 |
| topic 命名 | `go2cpp.debug.<host>.<pid>.scheduler.<name>.<kind>`，`kind ∈ {events, snapshot, locks, metadata}` |
| 消息 | 每条 message 带 `schema`（版本）、`source`（host/pid/scheduler）、`seq`（单机单调序号）、`timestamp`（双时间戳，见 E3） |
| **背压** | **必须可丢弃**：有界队列 + 丢弃计数 + 周期上报「已丢弃 N 条」；**绝不阻塞发布端** |
| 内存 | 单条 message 有大小上限；超限截断并标注（例如调用栈只保留前 N 帧） |
| 安全/开关 | 默认关闭；开启需显式配置；支持"只读、不含参数与局部值"的脱敏模式 |
- **为什么必须可丢弃**：调试通道一旦阻塞，就会把 worker 线程拖住，
  直接改变被观测对象的时序（观察者效应）。**这是设计红线。**
- **风险**：中（协议设计需与 Stratum 的实际契约对齐，本轮未接触到 Stratum 代码 → 不计细节）。

## E3 · 多机同步调试（含**时钟前提问题**）

- **目的**：多台机器上的进程，同一时刻的联合快照与联合时间线。
- **现状**：❌ 完全没有。
- **⚠️ 必须先解决的前提（第 3 轮已发现）**：
  `SchedulerEvent::timestamp` 是 **`std::chrono::steady_clock`**（`scheduler.hpp:130-137`），
  其注释明确「**不能直接转换为墙上时间**，但适合计算耗时和排序」。
  → **不同机器的 steady_clock 原点不同，跨机不可比** ✗
- **可选方案（需使用者定方向，不能替使用者写死）**：

| 方案 | 做法 | 优点 | 代价 / 限制 |
|---|---|---|---|
| A. 双时间戳 | 每条记录同时带 `steady_ns` 与 `wall_unix_ns`（记录时刻同时取两个时钟） | 实现简单、可离线对齐 | 受 NTP 跳变影响；跨机精度取决于时钟同步质量 |
| B. 单机序号 + 逻辑时钟 | 每台机器只保证**机内**顺序（`seq`），跨机用因果关系或 Lamport 时钟 | 不依赖时钟同步 | 只能给**偏序**，无法给"绝对同时" |
| C. 外部同步信号 | 调试时广播一个"同步脉冲"，各机记录本地 `steady` 时刻 | 精度高（不依赖系统时钟） | 需要额外通道；只对**当时在线**的进程有效 |
| D. 不统一 | 明确声明"**本工具不做跨机时间对齐**"，只提供各机独立视图 | 诚实、零成本 | 无法做真正的联合时间线 |
- **建议**：**A 作为基础（必做）+ D 作为诚实兜底**，B/C 作为可选增强；
  无论选哪个，**输出必须标注所用方案**，否则使用者会误读时间线。
- **另一层"同步"问题**：所谓"多机同步调试"若指**协同断点**（一台机器暂停、其他机器跟随），
  则需要**控制面**参与（B5 的安全点断点），且必须面对"其他机器可能正在持锁"的复杂度 →
  **本轮不承诺该能力**，只记录为后续方向。

## E4 · 与 gdb 混合调试（线程 ↔ G 映射）

- **目的**：把"gdb 看到的 OS 线程"与"调度器看到的 G"对上。
- **现状**：❌ 无导出机制；但**数据已具备**。
- **可用的数据源**：
  - `FiberExecutionBinding`（`fiber.hpp:36-48`）：`scheduler_token` / `task_id` / `machine_id` /
    `processor_id` / `managed`；
  - `FiberContextFrame::last_thread`（`fiber.hpp:65`）：`std::thread::id`；
  - `Fiber::id()`（`fiber.hpp:199-201`）：Fiber 唯一调试编号，**不复用**。
- **设计**：导出一张**映射表**（例如 `/tmp/go2cpp-debug/<pid>/thread-map.txt` 或一个 topic），
  形如 `thread_id → {machine_id, task_id, fiber_id, depth}`，供 gdb 脚本查表。
- **⚠️ 必须诚实声明的限制（这条最重要）**：
  gdb 看到的**始终是 M 的原生栈**；Fiber 的用户栈由 `context.cpp` 的后端切换，
  **gdb 的 `bt` 看不到 Fiber 的 C++ 调用链**。
  → 想看 Fiber 栈，必须用本模块的 `context_snapshot()`，**不是** gdb。
  → 两者是**互补**：gdb 停任意行、看原生栈；本模块看 GMP 结构与 Fiber 逻辑栈。
- **风险**：中（thread::id 的字符串化、跨平台差异）。

## E5 · 录制与回放（事件序列持久化）

- **目的**：把一次运行的事件序列存下来，事后分析或复现问题。
- **现状**：❌ 无。
- **设计要点**：
  - **格式**：建议"一行一条 JSON（ndjson）"或长度前缀的二进制；**带 schema 版本**；
  - **有界**：录制必须限流/限大小（否则长跑进程会写满磁盘）；
  - **回放**：回放只重建**视图**（时间线、统计），**不能重建运行时状态** ——
    GMP 的状态依赖真实调度，事件流不足以恢复栈。**这一点必须写明**，避免使用者误以为能"重放执行"。
- **风险**：低-中。

## E6 · 工具形态（向上提供什么）

- **目的**：确定最终交付形态，指导编码走向。
- **形态与优先级**：

| 形态 | 用途 | 优先级 | 备注 |
|---|---|---|---|
| **库 API**（`go2cpp::debug`） | 嵌入式、自定义 sink | **P0** | 其它形态都基于它 |
| **CLI**（`Go2Cpp dump scheduler ...`） | 现场排障、脚本化 | **P0** | 使用者明确要求的形态（20 个选项见 `design/02-dump-cli.md`） |
| **gdb 脚本片段** | 混合调试 | P1 | 依赖 E4 的映射导出 |
| **HTTP 端点** | 远程查看、面板集成 | P2 | **需评估是否引入 HTTP 依赖**（项目已有 `http.hpp`，但要确认是否愿意让调试模块依赖它） |
| **topic 发布器** | 多机（Stratum） | P2 | 依赖 E2 的契约 |

- **输出格式约定**：所有形态共享同一套 schema（`design/02-dump-cli.md`），
  保证 CLI 输出与库输出**逐字段一致**。
- **风险**：低。

## E 类共同结论

1. **E1 是基础**，其关键约束来自"观察者回调在 worker 线程同步执行"——必须非阻塞入队；
2. **E3 的时钟问题是硬前提**，四个方案各有代价，**必须由使用者定方向**（我给出建议 A+D）；
3. **E4 必须诚实声明 gdb 看不到 Fiber 栈**，否则使用者会误用；
4. **E5 必须声明回放不能重建运行时**；
5. **E2 的设计红线是"绝不阻塞发布端"**（背压可丢弃）。
