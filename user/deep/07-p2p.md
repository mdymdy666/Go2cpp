### 1.2 总架构图

```
                 信令（IM / 自建 TCP / LoopbackSignaling）
        ┌───────────────────────┐          ┌───────────────────────┐
        │ A: SerializeCandidates│          │ B: ParseCandidates    │
        └───────────┬───────────┘          └───────────┬───────────┘
                    │ 文本候选列表                      │
                    ▼                                   ▼
   GatherCandidates()                           AddRemoteCandidate()
     ├─ EnumerateLocalAddresses → host            │ 去重 + Finalize + 排序
     ├─ StunClient::Binding → srflx               │
     └─ RelayClient::Allocate → relay             │
                    │                               │
                    └──────────────┬────────────────┘
                                   ▼
                         Connect(timeout)
                    ┌──────────────┴──────────────┐
                    │ 1 信令交换（≤ timeout/2）    │
                    │ 2 分 direct / relay 目标     │
                    │ 3 直连检查（≤ 70% 总预算）   │
                    │ 4 中继检查（剩余 30%）       │
                    └──────────────┬──────────────┘
                        成功          │          失败
                         ▼            │           ▼
              Connected / Relayed     │        Failed
                         │            │
                         ▼            │
   Send/Recv ── 12B G2PD 帧 ──────────┘
     │ 直连：直接 sendto(peer)
     │ 中继：16B G2TR + body → relay server → peer
     ▼
   Recv：每轮 MaybeSendKeepalive + PeerTimedOut
         数据帧/keepalive/STUN 在同一 socket 上多路复用

服务端：
  StunServer  ── poll 线程 ── Binding Request → Success/Error（可 CHANGE-REQUEST 换 IP/端口）
  RelayServer ── poll 线程 ── 16B G2TR 控制面 + 每 allocation 一个 relay fd + ExpireAllocations
```

边界：
- **一个 `P2PChannel` = 一个 UDP socket**；STUN/TURN/数据/keepalive 全在这个 socket 上多路复用。
- `P2PChannel` 不是线程安全的；只允许「一发送线程 + 一接收线程」并发，统计/状态有锁。
- `RelayClient` 控制面串行；数据面 `SendTo` 之间也必须串行（共用 send scratch）。
- 服务端各一条 poll 线程；`StunServer` 可绑 4 个 socket 支持换 IP/端口。

### 1.3 复杂场景一：一次成功的打洞（Full Cone / 同网段）

1. A、B 各自构造 `P2PChannel`（`p2p_channel.cpp:236`）。没有注入 transport 时创建
   `UdpTransport` 并 `Start`；失败把错误存进 `m_error`（`p2p_channel.cpp:238-246`）。
2. A 调 `GatherCandidates()`（`p2p_channel.cpp:250`）：清空旧候选，枚举本机地址
   （`EnumerateLocalAddresses`），每个地址一个 `kHost` 候选（`p2p_channel.cpp:270-293`）。
3. 对每个 `stun_servers` 调 `StunClient::Binding(gather_timeout)`（`p2p_channel.cpp:295-311`）；
   成功得到 `kSrflx` 候选，`base` 设为本机地址或映射地址。
4. 若 `enable_relay && turn_server.valid()`：`EnsureRelay()` + `Allocate()`，成功得到 `kRelay`
   候选（`p2p_channel.cpp:313-326`）；失败只记 error，不影响 host/srflx。
5. `FinalizeCandidate` 给每个候选补 foundation/priority（`candidate.cpp:213-221`），
   `SortCandidatesByPriority` 降序（`candidate.cpp:239-245`）。
6. A 通过 `Signaling::Send(SerializeCandidates(...))` 发出候选；B 收到后
   `ParseCandidates` → `AddRemoteCandidate`（`p2p_channel.cpp:875-915`）。
   双方都先 Send 再 Recv，所以一端先调用不会死锁。
7. A 调 `Connect(0)` → 使用 `connect_timeout`（`p2p_channel.cpp:358-364`）；状态先发布
   `Connecting`（`p2p_channel.cpp:376`）。
8. 信令交换 deadline = `min(总deadline, started + timeout/2)`（`p2p_channel.cpp:387-394`）；
   失败直接 `SetFailed`。
9. 远端候选分 `direct_targets` / `relay_targets`（`p2p_channel.cpp:401-407`），
   `SortEndpointsByRemotePriority` 按远端 priority 排序（`p2p_channel.cpp:412-415`）。
10. `TryDirect`（`p2p_channel.cpp:922`）：每隔 `check_interval` 向每个 target 发
    `BuildBindingRequestWire`，把 transaction id 放进 `PendingChecks`（`p2p_channel.cpp:928-936`）。
11. B 也同时发检查包。A 收到 `kRequest`：回 Success 并 `Establish(source, false)`
    （`p2p_channel.cpp:957-967`）；或收到匹配 `PendingChecks` 的 `kSuccessResponse` →
    `Establish(source, false)`（`p2p_channel.cpp:968-972`）。
12. `Establish`（`p2p_channel.cpp:1070-1080`）：发布 `Connected` 或 `Relayed`，记录 peer、
    重置 keepalive 时间、清 pending。
13. 数据面：`Send` 组 12B `G2PD` 帧（`p2p_channel.cpp:440-470`），`SendDirect` 直接
    `transport->SendTo(peer)`；`Recv` 每轮先 `MaybeSendKeepalive` + `PeerTimedOut`
    （`p2p_channel.cpp:496-506`）。
14. 失败路径：所有 target 都超时 → `SetFailed("连接超时：直连与中继均未成功…")`
    （`p2p_channel.cpp:428-432`）；状态变 `Failed`，`LastError()` 可读。

### 1.4 复杂场景二：对称 NAT / 直连失败 → TURN 中继

1. A 的 `GatherCandidates` 得到 host + srflx + relay；B 只得到 host + srflx（未开 relay 或
   Allocate 失败）。
2. A 的 `Connect` 看到远端有 relay 候选、本地 `enable_relay=true` → `can_use_relay=true`；
   直连预算 = 70% 总超时（`p2p_channel.cpp:416-421`）。
3. `TryDirect` 向 B 的 host/srflx 发检查包。对称 NAT 下，B 的 NAT 为每个目标分配不同外部端口，
   A 的检查包到达的端口不是 B 预期的映射端口 → B 收不到；B 的包也到不了 A。
4. 直连 deadline 到期，`TryDirect` 返回 false（`p2p_channel.cpp:424-426`）。
5. A 进入 `TryRelay(relay_targets, deadline, started)`（`p2p_channel.cpp:426-431`）。
6. `TryRelay` 先 `EnsureRelay()`（`p2p_channel.cpp:661-671`，懒创建 + 原子发布裸指针）；
   未分配则 `Allocate()`（`p2p_channel.cpp:985-991`）。`Allocate` 走 16B `G2TR`
   `kAllocateRequest`，服务端 `HandleAllocate` 建 allocation + 绑定 relay fd
   （`turn_server.cpp:251-281`）。
7. 服务端返回 `kAllocateResponse`，body 带 relay 端点和 lifetime；客户端 `m_relayed` 更新，
   `m_lifetime_ms` 存下（`turn_client.cpp:144-180`）。
8. A 通过 `relay->SendTo(B的relay候选)` 发 Binding Request（`p2p_channel.cpp:998-1010`）。
   `RelayClient::SendTo` 组 16B 头 + 端点 + payload，一次 `sendto` 给 relay server
   （`turn_client.cpp` 的 `SendTo`；协议见 `relay_protocol.hpp:16-35`）。
9. 服务端 `HandleSendIndication` 解析目标端点，用对应 allocation 的 relay fd 转发给 B；
   B 收到的是来自 relay 地址的 `kDataIndication`（`turn_server.cpp:390-424`）。
10. B 若也走 relay（或能直连 relay），回 Binding Success；A 的 `TryRelay` 收到
    `kSuccessResponse` 且 `pending.Contains(tid)` → `Establish(source, true)`
    （`p2p_channel.cpp:1047-1051`）。
11. `Establish` 发布 `Relayed`；之后 `Send` 走 `SendViaRelay`（`p2p_channel.cpp:807-818`），
    `Recv` 走 `RecvViaRelay`（`p2p_channel.cpp:821-833`）。
12. 失败路径：`Allocate` 失败 → `SetError("中继分配失败: …")` 并返回 false
    （`p2p_channel.cpp:985-991`）；中继检查也超时 → `Failed`。
13. **生命周期坑**：allocation 到期由服务端 `ExpireAllocations` 关闭（`turn_server.cpp:456-470`），
    而 `P2PChannel` 没有任何 `Refresh` 调用（Q04）。长连接会在默认 60s 后静默断流。
14. `Close()` 只 `Release()` 不销毁 `RelayClient`，避免与在途 `Send/Recv` 竞争
    （`p2p_channel.cpp:646-656`）；对象留到 `Impl` 析构。

关键不变量：
- `Connect()` 必须双方并发；单边调用必然超时（NAT 只放行内部发过包的目标）。
- keepalive 由 `Recv()` 驱动；只发不收必须周期性 `Recv(0ms)`。
- `P2PConfig::signaling` 是非拥有裸指针，生命周期必须长于 channel。
- 候选交换是文本协议；`Candidate::Parse` 对非法输入整体失败。
- 对称 NAT 只能走中继；中继无鉴权/无权限表，只能部署在可信网络。

| # | 不变量 | 证据 | 破法后果 |

## 第二部分 · 分：逐块细讲

### 2.1 Endpoint 与传输抽象

**职责**：把 IPv4/IPv6 地址、端口、sockaddr 转换、哈希、解析封装起来。

- `Endpoint`（`include/go2cpp/p2p/endpoint.hpp:46`）：`AddressString()`、`Port()`、`ToString()`、
  `IsUnspecified()`、`IsLoopback()`、`sockaddr_ptr()`、`sockaddr_length()`。
- `EndpointHash`（`endpoint.hpp:129`）：给 `unordered_map` 用；TURN 的 allocation 表按 client
  endpoint 索引。
- `ResolveEndpoint(host, port, ...)`（`endpoint.hpp:142`）：getaddrinfo 封装，支持域名。
- `DatagramTransport`（`transport.hpp:40`）：`SendTo/RecvFrom/LocalEndpoint` 纯虚；
  `UdpTransport`（`transport.hpp:87`）是默认实现，`UdpTransportConfig`（68）控制绑定/缓冲区。
- 注入 transport 的用途：测试 `MockNat`、共享 socket、模拟丢包。注入后 `bind_endpoint` 被忽略，
  本地端点取 `transport->LocalEndpoint()`（`p2p_channel.hpp:106-112`）。

**失败路径**：解析失败、绑定失败、`sendto` 返回 EAGAIN（`UdpTransport` 内部 poll/重试）。
**误用**：把 `Endpoint` 当字符串比较；忽略 IPv6 的 scope id；在 `SendTo` 并发时共用缓冲。

### 2.2 STUN 消息与编解码

**职责**：RFC 5389 子集的线格式：20B 头 + TLV 属性，支持 XOR-MAPPED-ADDRESS、CHANGE-REQUEST、
ERROR-CODE、SOFTWARE。

**关键数据结构**：
- `StunClass`（`stun_message.hpp:104`）：request/indication/success/error。
- `StunAttribute`（112）：type/length/value。
- `StunMessage`（125-171）：method、class、transaction_id、attributes；提供
  `MakeBindingRequest/Success/Error`、`Find`、`AddAttribute/AddU32/AddString/AddAddress`、
  `GetU32/GetAddress/GetMappedAddress/GetErrorCode`。
- `StunAttributeView`（175）/`StunMessageView`（187）：零拷贝解析视图，热路径用。
- `ParseStunMessageView`（222）、`BuildBindingRequestWire`（232）、`BuildBindingSuccessWire`（242）、
  `ParseStunMessage`（273）。

**关键规则**：
- transaction id 12B，响应必须与请求一致（`stun_client.cpp:105-108`）。
- XOR-MAPPED-ADDRESS 的 IPv4 掩码用 magic cookie，IPv6 再加 transaction id
  （`StunMessage::AddAddress` 注释）。
- `CHANGE-REQUEST` 是 32 位标志：bit2 换 IP、bit1 换端口（`kStunChangeIp/kStunChangePort`）。
- 长度字段必须与 datagram 剩余长度严格相等，防截断/拼接。

**失败路径**：magic/长度/属性越界 → 解析失败；method/tid 不匹配 → 丢弃继续等；ERROR-CODE →
`StunExchangeResult` 带错误。**误用**：把 `StunMessageView` 的指针存起来跨包使用。

### 2.3 STUN 客户端与 NAT 类型探测

**职责**：发 Binding 请求，拿映射地址；按 RFC 3489 判定 NAT 类型。

- `StunClient`（`stun_client.hpp:44`）：构造时绑定 transport + server；`Exchange` 序列化、
  发送、循环收包直到超时（`stun_client.cpp:56-130`）。
- `Binding`（`stun_client.hpp` 内联/实现）：普通 Binding。
- `BindingWithChange(flags, timeout)`（`stun_client.cpp:210-215`）：带 CHANGE-REQUEST。
- `NatType`（73）、`NatDetectionConfig`（85）、`NatDetectionResult`（99）、
  `NatTypeDetector`（130）/`Detect`（`stun_client.cpp:238`）。

**探测顺序（不可改）**：
```
Test I  普通 Binding → 映射 = 本机? → OpenInternet
Test II change IP+port → 有响应? → FullCone
Test III change port   → 有响应? → RestrictedCone
Test IV 向 alternate 发普通 Binding → 映射变了? → Symmetric
        否则 → PortRestrictedCone
单服务器 → Unknown（不猜）
```
**关键点**：Test IV 必须最后（`stun_client.cpp:266-270`），否则会污染过滤表。

**失败路径**：Test I 失败 → `Unknown` + detail；没有 alternate → 跳过 II/III/IV；Test IV 无响应 →
仍按 PortRestricted 处理（代码的保守选择）。

### 2.4 候选与优先级

**职责**：表示 host/srflx/prflx/relay，按 RFC 8445 算 priority，文本编解码。

- `CandidateType`（`candidate.hpp:42`）：host=0、srflx=1、prflx=2、relay=3（线格式值）。
- `CandidateTypePreference`：host=126、prflx=110、srflx=100、relay=0（`candidate.hpp:8-14`）。
- `Candidate`（66）：type、endpoint、base、foundation、priority、component。
- `FinalizeCandidate`（88/`candidate.cpp:211-221`）：补 foundation/priority；
  `ComputeCandidatePriority`（`candidate.cpp:132-137`）：
  `(type_pref<<24) | (local_pref<<8) | (256-component)`。
- `SortCandidatesByPriority`（94/`candidate.cpp:239-245`）：稳定降序。
- `SerializeCandidates`（`candidate.cpp:246`）：首行 `g2p2-candidates/1`，每行 `cand ...`。
- `ParseCandidates`（`candidate.cpp:256`）：逐行 `Candidate::Parse`；任一行非法 → 整体失败？

**注意**：`MakeFoundation` 用 FNV-1a，但 offset basis 是 `1469598103934665603`
（标准值少一位，`candidate.cpp:23-26`），注释说是历史线格式兼容。foundation 只用于诊断/相等性，
不参与选路；不要「顺手修正」。

**失败路径**：priority=0 会被 `FinalizeCandidate` 重算；重复地址+类型被 `AddRemoteCandidate`
忽略；非法行导致解析失败。

### 2.5 P2PChannel 状态机与数据面

**状态**：`P2PState`（`p2p_channel.hpp:65`）：Idle → Gathering → Connecting → Connected/Relayed
→ Failed → Closed。

**关键流程**：
- `GatherCandidates`（`p2p_channel.cpp:250-338`）：清空 → host → srflx → relay →
  `FinalizeCandidate` + 排序 → 发布 Idle。
- `Connect`（358-433）：状态检查 → `Connecting` → 信令 → 分目标 → 直连 → 中继 → `Failed`。
- `TryDirect`（922-976）：重发检查 + 收包；入站请求直接 Establish；响应匹配 tid。
- `TryRelay`（978-1055）：Allocate → 通过 relay 发检查 → 入站请求/响应 Establish。
- `Send`（435-471）：12B `G2PD` 帧（magic/ver/type/length/sequence），`kP2PMaxPayload=1200`。
- `Recv`（474-583）：`MaybeSendKeepalive` → `PeerTimedOut` → `RecvDirect/RecvViaRelay` →
  STUN 分支 → 帧解析 → keepalive/ACK → 数据。
- `Establish`（1070-1080）：发布状态、peer、清 pending、重置 keepalive。
- `Close`（646-656）：置 Closed，`Release()`，不销毁 relay。

**数据帧**：12B 头：`"G2PD" | ver(1) | type(1) | length(2) | sequence(4)`；type 1=data、
2=keepalive、3=keepalive-ack；length 必须与剩余长度严格相等。

**失败路径**：未连接 Send/Recv 返回 false/0；长度 0 或 >1200 Send 失败；对端静默超过
`peer_timeout` → `Failed`；畸形帧 → `dropped_packets`。

### 2.6 中继（简化 TURN）

**线格式**（`src/p2p/relay_protocol.hpp:16-35`）：16B 头：`"G2TR" | version(1) | type(1) |
body_len(2,BE) | request_id(4,BE) | reserved(4)=0`；body 里端点是
`family(1) | port(2) | address(4/16)`。不是 RFC 5766：无鉴权、无 MESSAGE-INTEGRITY、无
ChannelData、无权限表。

**服务端**（`RelayServer`，`turn.hpp:79`）：
- `HandleAllocate`（`turn_server.cpp:251-281`）：已有 client → 顺延 expires；否则建 allocation
  （绑定新 UDP socket，relay 端点 = advertised IP + 本地端口）。
- `HandleRefresh`（284-295）：顺延 `expires`，回 `kRefreshResponse` 带 lifetime。
- `HandleRelease`（298-308）：关 fd、erase。
- `HandleSendIndication`（311-330）：解析目标端点，用 allocation 的 fd 转发。
- `ExpireAllocations`（456-470）：到点 `close(fd)` + erase，**与流量无关**。

**客户端**（`RelayClient`，`turn.hpp:128`）：
- `Allocate`（`turn_client.cpp:144-180`）：重试 `allocate_attempts`，解析 lifetime/relay 端点。
- `Refresh`（183-212）：更新 `m_lifetime_ms`；**当前没有 `P2PChannel` 调用者**。
- `Release`（213-233）：best effort。
- `SendTo`/`RecvFrom`：数据面加 16B 头；`m_send_buffer` 复用避免堆分配。

**失败路径**：allocation 满（`kAllocationLimit`）、地址非法、请求超时、allocation 过期。
**误用**：把中继当可靠/安全通道；不在 lifetime 内 Refresh（Q04）。

### 2.7 TCP 同时打开

- `TcpPuncher::Bind(local)`（`tcp_punch.hpp:52`）：建 socket、绑端口、监听/复用。
- `Connect(remote, timeout)`（`tcp_punch.hpp:72`）：双方同时向对方端口发起 connect；
  单边调用会收到 RST 并重试到超时。
- `Send/Recv`：连上后是字节流；`Recv` 返回 0 表示超时。
- 仅 IPv4；平台/NAT 组合敏感，测试失败记 SKIP 而不是 FAIL。

**误用**：把它当普通 TCP 客户端；在一端先 Connect 再等对端。

### 2.8 信令

- `Signaling`（`signaling.hpp:38`）：`Send(payload)` / `Recv(payload, timeout)`，只要求
  「可靠、有序、双向」；不规定消息边界格式。
- `LoopbackSignaling`（55）：进程内共享邮箱，`CreatePair()` 返回互通的 A/B。
- `P2PChannel::ExchangeCandidates`（`p2p_channel.cpp:870-915`）：先 Send 再循环 Recv；
  每次 Recv 最多 100ms，直到 deadline；解析失败只记 error 继续。
- 候选文本首行 `g2p2-candidates/1`，改格式必须两端同步。

**失败路径**：Send 失败、通道关闭（Recv<0）、等待超时、解析失败。**误用**：把
`P2PConfig::signaling` 指向栈对象/短生命周期对象（非拥有裸指针）。
