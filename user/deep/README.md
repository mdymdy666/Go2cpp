# Go2Cpp 深入学习文档（user/deep/）

> 这套文档面向「要接手改代码的人」，不是交接摘要，也不是 API 手册。
> 目标：读完能画出数据流、说清每一步落在哪个 `文件:行`、知道哪条不变量一破就出 bug。

## 一、与 `user/docs/` 的分工

| 目录 | 定位 | 读者 | 篇幅 | 是否允许只给结论 |
|---|---|---|---|---|
| `user/docs/` | 交接摘要：模块是什么、API、边界、已知限制 | 第一次接触模块的人 | 每篇 200–400 行 | 允许 |
| `user/deep/` | 深入教程：从入口到内核路径、逐函数拆、状态机、失败路径 | 要改这块代码的人 | 每篇 500–800 行 | **不允许**，必须给行号与步骤 |

`deep/` 不重复 `docs/` 的「模块介绍」，而是回答三个问题：

1. **它怎么跑起来**：入口在哪、谁调用、状态怎么变、阻塞时走哪条路；
2. **它为什么这样写**：数据结构与锁的选择、失败路径的取舍；
3. **改坏了会怎样**：不变量、已知限制、典型误用与后果。

## 二、铁律（每篇都必须遵守）

1. **不信任何文档数字**。项目迭代极快，一小时可能优化多轮；文档里的 ns/吞吐都可能过时或从未有出处。
   文中若给性能，必须写成「2026-11-03 本机实测：…（12 vCPU 未绑核，3 轮；换环境要重测）」。
2. **行号必须真实**。写完逐条 `sed -n 'N,Mp'` 复核；编造行号视为不合格。
3. **代码片段 5–15 行**，只贴关键几行，不整函数复制。
4. **先总后分**：第一部分必须让读者建立全局图，第二部分才逐块下钻。
5. 只改本篇目标文件，不 commit。

## 三、每篇的固定结构（规格模板）

```markdown
# <模块名> · 深入学习

## 第一部分 · 总：这个模块怎么跑起来
### 1.1 入口点清单
表格：入口（类/函数/宏）| 文件:行 | 谁调用它 | 它触发什么 | 返回什么
要求覆盖所有对外入口（含默认参数、编译开关、环境变量）。

### 1.2 总架构图（ASCII）
必须画出：层次（用户 → API → 核心 → 运行时/内核）、线程/Fiber 边界、
队列在哪、锁保护哪段、数据流方向、回调在哪里跳出去。

### 1.3 复杂场景 ≥10 步详解
至少 2 个场景，每个 ≥10 步。每步写：
「谁调用谁 → 状态怎么变 → 落到哪个 文件:行 → 失败/阻塞时走哪条路」。

### 1.4 关键不变量
5–10 条「只要这条破了就一定出 bug」的清单，每条给 文件:行 与破法后果。

## 第二部分 · 分：逐块细讲
每个子模块一节：职责 / 关键数据结构（字段级 + 行号）/ 关键函数逐步拆 /
状态机（表格或 ASCII）/ 失败路径与已知限制 / 典型误用与后果。
```

## 五、写作与复核流程

1. 先读 `src/` 与 `include/` 的真实实现，再读 `docs/`（只作线索，不作证据）；
2. 列出入口 → 画数据流 → 找锁与队列 → 写场景；
3. 每写一个 `文件:行`，立刻 `sed -n` 看一眼；
4. 用 `grep -n` 统计引用，确保没有指向已漂移的行；
5. 性能数字要么现场跑，要么不写。

## 六、篇幅与难度约定

- 每篇 500–800 行；第一部分 ≈ 40%，第二部分 ≈ 60%。
- 至少 2 个 ≥10 步场景；至少 8 条不变量；每个子模块至少 1 条「典型误用」。
- 不写「显然」「众所周知」；每个结论后面要么有行号，要么有实测条件。

## 八、常见反例（这样写不合格）

1. **只罗列 API 签名**：没有「谁调用、状态怎么变、失败走哪」。
2. **只贴架构图不标边界**：看不出 G 在哪切、M 在哪睡、锁保护哪段。
3. **场景写成流程口号**：「然后调度器调度它」——没有行号、没有状态、没有失败分支。
4. **引用历史报告数字**：「文档说 122 ns」——没有当场实测条件。
5. **行号从旧文档抄**：源码一改就漂移，必须自己 `sed` 复核。
