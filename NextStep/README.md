# NextStep：Go 常用标准库 / 第三方库 → Go2Cpp 的下一步行动

> 目标：把「Go 代码近 1:1 转译为 C++」这件事拆成**以模块为单位**的行动计划，
> 每个模块给出：Go 侧范围、当前 Go2Cpp 覆盖度、缺口、依赖、工作量、**计划产出时间**。
> 本目录由定时任务（每 15 分钟一轮，截至 2026-10-15 22:00）渐进填充。

## 为什么需要它

Go2Cpp 现有 27 个公开模块，覆盖的是 **runtime 语义**（goroutine/channel/context/调度/IO/epoll）。
但真实 Go 代码里出现频率最高的是**标准库**（`fmt`/`strings`/`errors`/`encoding/json`/`net/http`…）
与**第三方库**（Web 框架、ORM、日志、配置）。转译要落地，这些必须逐个有对应物或明确边界。

## 方法与判据（先检索，再断言）

1. **复用优先**：先找成熟开源实现（许可证兼容、可移植），只在「找不到 / 不兼容 / 接口无法适配」时自研，
   并写明理由（项目规范第 2 节）。
2. **频率 × 覆盖度定优先级**：
   - 高频 + 已有覆盖 → 补边界与示例（低成本、直接提升可用性）
   - 高频 + 无覆盖 → 优先开发（收益最大）
   - 低频 + 依赖重（如 `net/http` 全生态）→ 只做最小可用子集并显式声明边界
3. **每个模块都必须能回答**：Go 侧 API 清单 → Go2Cpp 落点（哪个模块/新模块）→ 测试方案（大数据量/随机/多场景）→ 计划产出时间。

## 与 `ArchitectureDiagram` 的关系

架构报告（`../ArchitectureDiagram/`）回答「**现在是什么**」；
本目录回答「**接下来做什么、什么时候做**」。
两者共用同一套模块分组（G1~G9），因此 `roadmap.md` 里的每个批次都能直接指向架构图中对应节点。
